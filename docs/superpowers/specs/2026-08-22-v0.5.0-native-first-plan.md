## 0. 이 계획이 바로잡는 방향

devbox를 만드는 첫 번째 이유는 개발자가 자주 쓰는 기능을 찾고, 내려받고, 별도 앱을
실행하고, 다시 파일이나 클립보드로 데이터를 옮기는 반복을 줄이는 데 있다. 외부 도구와
경쟁한다는 이유만으로 기능을 제외해서도 안 되고, 반대로 이미 존재하는 모든 도구를
설치해 주는 package manager가 되어서도 안 된다.

v0.5.0은 다음 원칙으로 두 극단을 피한다.

1. **반복 작업은 devbox 안에서 끝낸다.** P1·P2 기능은 기능의 대상 자체가 외부 시스템인
   경우(WSL, Git, 원격 API, container engine 등)를 제외하면 인터넷과 별도 설치를 요구하지
   않는다.
2. **라이브러리는 기능의 일부로 번들할 수 있다.** 허용 가능한 라이선스이고 크기·보안·
   업데이트 경로를 검토한 Rust/TypeScript 라이브러리와 소형 sidecar는 devbox 설치물에
   포함할 수 있다.
3. **대형 전문 도구는 보완재다.** 전체 IDE, 범용 DB GUI, container desktop처럼 규모가 큰
   도구는 설치 감지·공식 설치·열기 연동을 선택적으로 제공할 수 있지만 native 기능의
   기본 버튼이나 유일한 경로가 될 수 없다.
4. **앱끼리 데이터를 넘길 때 사용자에게 운반을 시키지 않는다.** devbox가 송신자와
   수신자를 모두 제어하면 versioned `applink`, one-time handoff, read-only snapshot을 사용한다.
5. **필요한 범위만 소유한다.** 외부 도구의 제한적인 라이선스 때문에 필수 기능을 직접
   제공해야 할 때는 해당 코드를 포함하거나 모방하지 않고 공개 규격·관찰 가능한 동작에
   기반해 필요한 하위 기능만 독립 구현한다.

### 0.1 우선순위의 의미

| 우선순위 | 의미 | v0.5.0 처리 |
|---|---|---|
| P1 | 보안·공통 계약·이미 확정된 주요 기능. 후속 작업의 선행 조건 | 먼저 완료, 미완료 시 RC 진입 불가 |
| P2 | 순서만 유동적인 필수 후속 기능 | 전부 완료, 앱 간에는 병렬 진행 가능 |
| P3 선택 | 검토 후 v0.5.0에 넣기로 선택한 보강·신규 앱 | 릴리스 범위에 포함. 임의 탈락 금지 |
| 보류/제외 | 책임 중복·규모·안전·유지비 때문에 이번 범위에서 하지 않음 | 외부 도구 연결로 몰래 대체하지 않음 |

P3는 중요도가 P1·P2보다 낮다는 뜻이지 “시간이 남으면 한다”는 뜻이 아니다. 이 문서에서
선택된 P3를 v0.5.0에서 빼려면 별도 범위 변경 결정을 기록한다.

## 1. 개발 지침 — 네이티브 우선과 외부 도구

### 1.1 기능 평가 순서

기능을 새로 검토할 때 다음 순서로 판단한다.

1. 개발자가 얼마나 자주 수행하고, 현재 몇 번의 앱 전환·다운로드·파일/클립보드 전달이
   필요한지 기록한다.
2. 기존 devbox 앱의 책임에 자연스럽게 들어가는지 확인한다.
3. Rust/TypeScript와 번들 가능한 라이브러리로 오프라인 구현이 가능한지 확인한다.
4. 별도 앱으로 만들 만큼 입력·상태·수명주기·사용 흐름이 독립적인지 확인한다.
5. 이미 설치된 전문 도구를 활용하면 더 깊은 기능을 얻을 수 있는지 **보조 경로로만** 본다.
6. 구현하지 않는다면 외부 도구의 존재가 아니라 책임 중복, 안전, 크기, 유지비 중 실제
   사유를 기록한다.

### 1.2 오프라인 계약

- P1·P2의 UI는 runtime download 성공 여부에 따라 숨겨지거나 비활성화되지 않는다.
- 앱 시작과 로컬 데이터 처리에는 network call을 넣지 않는다.
- 원격 API 요청, Git remote, 앱 업데이트처럼 기능의 본질이 network인 경우에만 연결을
  요구한다. 같은 기능의 로컬 대상은 오프라인에서 동작해야 한다.
- WSL 기능은 설치된 WSL, Git 기능은 설치된 Git, container adapter는 설치된 engine을
  작업 대상으로 삼을 수 있다. 대상이 없으면 native 진단과 설치 안내를 표시하되 다른
  기능까지 막지 않는다.
- Code Pad의 LSP는 선택 기능이다. 편집·저장·preview·Quick Open은 LSP와 무관하게 동작한다.
- 외부 전문 도구가 없거나 WinGet이 없거나 인터넷이 차단돼도 P1·P2와 외부 도구 이외의
  P3는 동일하게 동작한다.

### 1.3 번들 의존성 기준

각 runtime 의존성 PR은 다음 표를 채운다.

| 항목 | 필수 내용 |
|---|---|
| 목적 | 어떤 사용자 기능을 가능하게 하는지 |
| 대안 | 자체 구현·다른 라이브러리·외부 도구 연결과 비교 |
| 출처 | 공식 저장소와 배포 원본 |
| 고정 | 버전, lockfile, binary면 SHA-256·서명 |
| 라이선스 | 앱 배포·수정·고지 의무 |
| 크기 | 설치 파일과 메모리 증가 실측 |
| 보안 | advisory, 입력 상한, sandbox/권한 경계 |
| 오프라인 | 설치 후 network 없이 동작하는지 |
| 유지보수 | 업데이트 감시 주체와 제거 전략 |

- MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, Zlib, Unicode-3.0은 자동 허용 후보다.
- MPL, LGPL, CDDL과 dual-license의 제한 조합은 PR에서 수동 검토한다.
- GPL, AGPL, SSPL, source-available, proprietary runtime은 기본 설치물에 포함하지 않는다.
- 라이선스가 제한적인 도구의 기능을 자체 구현하더라도 코드를 복사하거나 reverse-engineered
  비공개 protocol에 의존하지 않는다.
- `deny.toml`과 `THIRD_PARTY_NOTICES.md`를 추가하고 Cargo·pnpm license 검사를 CI에 넣는다.
- v0.5.0에서 새 sidecar는 도입하지 않는다. 아래 선택 기능은 모두 정적 라이브러리 또는
  앱 내부 Rust 로직으로 구현 가능하다.

### 1.4 외부 전문 도구의 역할

Devbox Manager의 `Related Tools`는 다음만 제공한다.

- 설치 여부와 감지 근거
- 공식 사이트·공식 라이선스 링크
- 사용자가 확인한 뒤 실행하는 WinGet 설치
- 설치된 executable 실행 또는 현재 path/file 열기

자동 설치, background update, 광범위한 package search, 일괄 제거, 외부 도구 설정 파일의
무단 수정은 하지 않는다. PowerToys, Windows Terminal, VS Code, Bruno, DBeaver/DB Browser,
GitHub Desktop, Podman/Docker Desktop 정도의 제한된 전문 보완재만 다룬다. 각 앱의 native
동작을 primary action으로 유지하고 외부 도구 열기는 secondary action으로 둔다.

## 2. 공통 아키텍처와 공개 계약

### 2.1 app catalog schema v2

`apps/catalog.json`의 `schemaVersion`을 `2`로 올리고 각 앱에 capability를 선언한다. 모든
카탈로그 사본에는 저장소가 단조 증가시키는 `catalogRevision`을 함께 기록한다.

```json
{
  "schemaVersion": 2,
  "catalogRevision": 1,
  "apps": [
    {
      "id": "api-playground",
      "accepts": ["handoff:api-request/v1"],
      "produces": ["handoff:api-request/v1"]
    }
  ]
}
```

기본 target은 `path`, `workspace`, `query`, `profile`이고 구조화 payload는
`handoff:<kind>/v<n>`, snapshot은 `snapshot:<producer>/<kind>/v<n>` 형식의 문자열로
표현한다.

catalog의 optional `actions`는 `actionId`, `actionVersion`, label, target과 versioned
payload kind만 선언하는 정적 entry다. 실행 시점의 profile/job/query 상태나 secret은 catalog에
넣지 않으며, 동적 상태는 §2.4 snapshot 계약으로만 발행한다.

- v1 문서나 `accepts`/`produces`가 없는 항목은 빈 배열로 읽는다.
- Manager가 설치·업데이트 때 `%LOCALAPPDATA%\devbox\catalog.json`을 tmp+rename으로 쓴다.
- build-time 사본과 runtime 사본의 freshness는 `catalogRevision`으로 결정한다. 유효하고
  build-time revision 이상인 runtime 사본은 사용하고, 더 오래됐거나 revision이 없거나
  손상된 runtime 사본은 무시하고 build-time 사본으로 폴백한다. 같은 revision이면 runtime
  사본을 사용한다. Manager는 현재 사본보다 낮은 revision을 원자적으로 덮어쓸 수 없다.
- runtime 사본이 없거나 손상되면 각 앱의 build-time 사본을 사용한다.
- catalog schema, build/runtime 사본 읽기, capability filter는 새 순수 `crates/catalog`가
  담당한다. Manager와 메뉴를 가진 앱이 공동 소비한다.
- `crates/launch::installed_targets(kind)`는 `crates/catalog` 결과 중 실제 executable이
  해석되는 앱만 반환한다. `crates/applink`는 argv 계약에만 집중해 `launch`와 순환 의존하지
  않는다.
- install root와 executable 해석은 `crates/launch`만 담당한다. 각 앱이 registry나 설치
  디렉터리를 다시 구현하지 않는다.
- catalog와 custom install root의 선행 locator 계약은 고정 위치의
  `%LOCALAPPDATA%\devbox\install-roots\v1\registry.json`이다. registry에는
  `schemaVersion`, 단조 증가하는 `registryRevision`, 기록 당시의 `catalogRevision`, `rootId`,
  canonical `path`, app-owned manifest 경로와 갱신 시각만 기록하고, tmp+rename으로 갱신한다.
  catalog 변경만으로 기존 root를 무효화하지 않으며 `catalogRevision`은 provenance와 app-id
  검증에만 사용한다. `crates/launch`는 이 versioned registry와
  manifest를 먼저 해석하며, v0.4.x 고정 위치는 migration 기간의 read-only fallback으로만
  읽는다. unresolved environment variable, root/home/workspace, symlink/reparse 탈출과
  manifest에 없는 executable은 거부한다. Manager의 custom root UI·이동·제거 구현은 이
  계약을 먼저 충족한 뒤에 시작한다.
- catalog는 devbox 앱 전용이다. 외부 전문 도구 catalog와 섞지 않는다.

### 2.2 applink protocol v2

현재 `OpenTarget::Path`, `Profile`, `Workspace`, `Query`에 다음 변형을 추가한다.

```rust
Handoff { kind: String, id: String }
```

- `PROTOCOL_VERSION`은 2로 올린다.
- v1 argv와 맨 앞 위치 path는 계속 읽는다.
- 구버전 수신자가 모르는 flag를 받아도 평소 화면으로 열리고 crash하지 않는다.
- cold start와 이미 실행 중인 instance 모두 `PendingOpen`에 넣고 frontend가 pull한다.
- 실행 중 수신은 창 복원·focus 후 event와 pending pull을 함께 사용하되 동일 request를
  두 번 적용하지 않는다.

### 2.3 one-time handoff

handoff envelope은 다음 의미 필드를 가진다.

```text
protocolVersion, id, kind, sourceApp, targetApp?, createdAt, expiresAt, payload
```

- ID는 충돌 예측이 어려운 128-bit random 값이다.
- 기본 TTL은 10분, 직렬화 상한은 10MiB다.
- `CreateNew` 의미로 생성하고 완성된 JSON만 원자적으로 노출한다.
- target app이 지정된 payload는 다른 앱이 소비하지 않는다.
- schema·kind·source·target·size·expiry를 확인한 뒤 읽는다.
- 성공한 consume은 즉시 삭제한다. 처리 실패는 TTL까지 남겨 재시도할 수 있게 하고 오류를
  발신자/수신자에 표시한다.
- 만료·손상 파일은 별도 quarantine 없이 지우며 secret 값을 error에 포함하지 않는다.
- 10MiB를 넘는 binary는 handoff root에 복제하지 않고 사용자가 선택한 파일 또는 app-owned
  임시 파일의 canonical path·size·digest를 전달한다.

one-time 소비는 단순한 read-then-delete가 아니다. 동시 실행과 consumer crash를 고려해 다음
상태를 사용한다.

```text
pending --atomic claim(consumer+lease)--> claimed --ack--> consumed/deleted
   ^                                      |
   └----------- restore/nack --------------┘
```

- producer는 `pending/<id>.json`을 create-new + atomic rename으로 노출한다. consumer의
  `claim`은 exclusive rename/claim record로 소유자와 짧은 lease를 기록해 두 consumer가
  같은 payload를 동시에 처리하지 못하게 한다.
- 성공한 처리만 `ack`할 수 있고, ack는 claim token을 확인한 뒤 삭제한다. validation 또는
  import 실패는 `restore`로 pending에 원자적으로 되돌려 TTL 안에서 재시도한다. consumer가
  죽으면 lease expiry 후 복구할 수 있다. 만료·손상 payload는 안전한 오류만 남기고 삭제한다.
- claim/ack/restore는 target, kind, schema, id와 consumer token을 매번 검증한다. duplicate
  claim/ack, wrong target, crash recovery, concurrent consumer는 계약 테스트로 고정한다.
- 기본 claim lease는 60초이며 `expiresAt`을 넘길 수 없다. 처리에 더 긴 시간이 필요하면 같은
  token으로 상한 내 갱신하고, 만료 token의 ack/restore는 거부한다.

표준 kind:

| kind | 발신 | 수신 | payload 목적 |
|---|---|---|---|
| `api-request/v1` | Webhook Lab, Toolbox, API Playground | API Playground | method, URL, templated headers/body |
| `webhook-fixture/v1` | API Playground, Webhook Lab | Webhook Lab | local response fixture 초안 |
| `knowledge-draft/v1` | Life Log, Launcher | Knowledge | 제목·본문·태그 초안 |
| `log-source/v1` | Run Manager, WSL Desktop | Log Lens | source adapter 설정과 검증된 path/id |
| `toolbox-text/v1` | Launcher, API Playground | Developer Toolbox | 입력 text와 추천 transformer |

모든 payload는 secret 원문을 금지한다. API request는 `${SECRET_NAME}` 참조만 전달한다.

### 2.4 snapshot bus 정리

snapshot은 producer가 소유한 지속 상태의 read-only 요약이며 command 전달에 사용하지 않는다.

| snapshot | producer | consumer | 내용 |
|---|---|---|---|
| `life-log/projects/v1` | Life Log | Workbench | 관찰된 프로젝트와 최근 활동 |
| `knowledge-base/activity/v1` | Knowledge | Life Log | 작성·수정 수와 노트 식별자 |
| `wsl-desktop/runtime/v1` | WSL Desktop | Workbench, Life Log | terminal·container·구조화 port |
| `run-manager/status/v1` | Run Manager | Workbench, Life Log, Launcher | job/service 상태와 최근 실행 |
| `workbench/profiles/v1` | Workbench | Launcher | recent profile/workspace action metadata |
| `repo-manager/repositories/v1` | Repo Manager | Launcher | repository/worktree action metadata |
| `run-manager/jobs-services/v1` | Run Manager | Launcher | job/service action metadata |
| `everything-plus/saved-queries/v1` | Everything+ | Launcher | query/filter action metadata |
| `wsl-desktop/profiles/v1` | WSL Desktop | Launcher | profile/layout action metadata |

- Workbench의 Life Log DB 직접 조회를 삭제한다.
- Life Log의 자체 snapshot reader를 `crates/integration`으로 교체한다.
- `discover()`는 `<common_root>/integration/*/v*/summary.json`을 스캔한다.
- 한 producer의 손상 JSON은 나머지 producer 발견을 막지 않는다.
- snapshot에는 데이터 freshness, producer version, schema version, generated time을 포함한다.
- secret, Authorization, Cookie, raw environment value는 저장하지 않는다.
- 한 producer는 version별 `summary.json` 하나만 소유한다. 여러 snapshot kind가 필요하면
  envelope의 `data.views`에 kind별 versioned view를 함께 넣고 한 번에 atomic replace한다.
  예를 들어 WSL Desktop은 `runtime`과 `profiles`, Run Manager는 `status`와 `jobs-services`를
  같은 producer summary에 발행한다. consumer는 catalog의
  `snapshot:<producer>/<kind>/v<n>` capability로 해당 view만 선택하며, producer가 같은 파일을
  kind별 writer로 서로 덮어쓰지 않는다.

### 2.5 공용 코드

- `packages/context-menu`: position, keyboard navigation, focus restore, submenu, separator,
  disabled/danger 표현만 제공한다. 항목 정의는 앱이 소유한다.
- `crates/catalog`: catalog v1/v2 type, parser, runtime/build-time fallback, capability filter를
  제공한다. executable 설치 판정과 process launch는 포함하지 않는다.
- `crates/logs`: Log Lens가 두 번째 소비자가 되는 시점에 Run Manager의 순수 log parsing,
  timestamp/level/source 정규화만 추출한다. 실행·파일 IO·UI state는 각 앱에 남긴다.
- `crates/window-state`: 일반 창의 bounds/maximized/monitor 정보를 저장하고 DPI·monitor 변경 시
  화면 안으로 clamp한다. Launcher처럼 transient window는 제외한다.
- document extraction, launcher index, Related Tools는 소비자가 하나이므로 앱 내부에 둔다.

### P1-01. 문서·의존성 정책

**산출물**

위 세 항목은 문서에 적혀 있다고 완료된 것이 아니다. 현재 저장소에는 `deny.toml`과
`THIRD_PARTY_NOTICES.md`가 없고, `.github/workflows/ci.yml`에도 Cargo·pnpm license gate가
없으므로 **별도 dependency-gate PR**로 먼저 추가한다. gate가 main에 들어오기 전에는 새
runtime dependency PR을 merge하지 않는다.

| gate | 구현할 작업 | merge 전 확인 |
|---|---|---|
| Cargo | `deny.toml`에 license/ban/source/advisory allowlist와 lockfile 검사를 고정 | `cargo deny check` 결과와 예외 만료일 |
| notices | `THIRD_PARTY_NOTICES.md`를 lockfile 기준으로 생성·갱신 | crate 버전·license·source·digest가 설치물과 일치 |
| pnpm | workspace package의 license/third-party 목록과 frozen lockfile을 검사하는 CI job 추가 | transitive license와 새 package의 목적/대안 기록 |
| Windows | packaged build가 gate 산출물(notices 포함)을 누락하지 않는지 smoke 확인 | v0.5.0 RC에서 재실행 |

의존성 검토 PR에는 다음 경계도 반드시 결정·테스트한다.

- YAML parser(`js-yaml` 후보)는 문서 크기, alias/anchor 수, nesting depth, duplicate key와
  custom tag 처리 정책을 고정한다. OpenAPI local/URL import 모두 같은 상한과 오류 격리를
  사용하며 parser가 임의 object prototype을 만들지 않게 한다.
- ULID는 canonical Crockford Base32·대문자/소문자 표시·batch 상한을 명시한다. HMAC는
  지원 algorithm(최소 SHA-256, 필요 시 SHA-384/SHA-512), raw/hex/base64 key 입력 형식,
  key·input 상한, 출력 encoding을 PR에서 고정하고 key는 저장·로그·history에 남기지 않는다.
  JWT verify는 허용 algorithm(HS 계열의 정확한 목록), `alg=none` 거부, key의 최소 길이와
  raw/hex/base64 범위를 명시하며 PEM/RSA/EC 키를 범위 밖으로 두는지 결정한다.
- QR PNG/image clipboard는 matrix 생성 crate와 PNG encoder의 license/source/digest를
  별도로 검토한다. dimension·memory 상한, save 경로의 canonical 검증, image clipboard가
  지원되지 않거나 실패한 Windows에서의 명시적 text/PNG-file fallback을 테스트하며,
  사용자 확인 없는 자동 clipboard 저장은 하지 않는다.
- global shortcut은 `tauri-plugin-global-shortcut` 후보의 version/license/Windows 등록
  동작을 검토한다. 등록 충돌을 감지해 사용자 설정으로 변경하고 기존 단축키를 조용히
  빼앗지 않으며, 등록 실패 시 앱 내부 action은 계속 동작해야 한다.

**완료 조건**

- 외부 도구의 존재만으로 기능을 제외하지 않는다는 문장이 규약에 있다.
- P1·P2 runtime offline 계약과 optional external tool 경계가 명시돼 있다.

### P1-02. API Playground secret history 결함

**문제**

현재 저장소는 DB transaction이 아니라 프론트 `localStorage`를 사용한다. `App.tsx`의
`apip-history`에 실행된 `effectiveReq`를 그대로 쓰고, `lib/collections.ts`의
`apip-collections`에는 사용자가 저장한 `ApiRequest` 전체가 들어간다. 따라서 resolved
secret이 History뿐 아니라 Collection의 auth/header에도 남을 수 있다. `buildCurl()`도
현재 Bearer/API key/Basic 값을 평문으로 만든다. 이 사실을 SQLite migration 전제로 문서화하지
않고 구현 계약의 기준으로 삼는다.

**v0.4.2 선행 보안 핫픽스**

이 결함은 v0.4.1 안정판에도 있으므로 v0.5.0 완료까지 기다리지 않고 v0.4.2에서 P1-02 전체를
먼저 완성한다. backend-only resolve, History/Collection v2 persistence와 migration, curl·응답·
오류 redaction을 일부만 적용한 채 안정판을 게시하지 않는다. 코드 PR에서 API Playground 앱
버전을 0.3.2로 올리고, 별도 release-preparation PR과 Windows hotfix smoke 뒤 `v0.4.2` tag를
게시한다. 이 hotfix는 v0.5.0 범위를 축소하는 별도 구현이 아니라 P1-02를 선행 완료하는 보안 gate다.

**구현**

- `RequestTemplate`, `ResolvedRequest`, `PersistedHistoryRequest`를 분리한다.
- secret resolve는 전송 직전 backend 메모리에서만 수행하고 resolved 값은 frontend state,
  clipboard, persistence, log로 반환하지 않는다.
- History v2에는 `${SECRET_NAME}`/`{{SECRET_NAME}}` 참조가 남은 template과 고정 마스킹 값만
  저장한다. URL/query/header/body/auth/response/error 및 redirect의 각 hop을 같은 redaction
  함수로 처리한다.
- `apip-history` v1은 안전성을 증명할 수 없으므로 **내용을 변환하거나 raw backup을 만들지
  않는다.** 최초 실행 시 UI에서 즉시 격리해 렌더링·검색·재전송 대상에서 제외하고 빈 v2
  History를 기록한다. 그 뒤 원래 key를 삭제하고 read-back이 성공한 경우에만
  `apip-history-v1-migrated` marker를 기록한다. 삭제·read-back·marker 기록 중 하나라도
  실패하면 marker를 기록하지 않고 raw key를 UI에서 계속 격리한 채 다음 실행에서 삭제를
  재시도한다(fail-closed). raw key를 backup/rollback key로 복제하는 것은 금지한다.
- migration 순서는 `raw 격리 → 빈 v2 store 기록 → raw key 삭제 → raw key
  read-back 부재 확인 → marker 기록`으로 고정한다. v2 기록이 실패하면 raw key를
  삭제하지 않고 다음 실행에서 재시도하며, rollback이 필요할 때도 sanitized replacement만
  대상으로 한다.
- Collection(`apip-collections`)은 사용자 자산이므로 보존한다. 이미 reference인 auth와
  header는 보존하고, 직접 입력된 Authorization/Cookie/Set-Cookie/API-key 계열과 auth
  username/password/token/api value는 확인 가능한 environment reference로 바꾸거나 고정
  마스킹과 `requiresSecretReview` 표시로 안전 변환한다. 변환할 수 없는 원문은 별도
  backup에 남기지 않는다. sanitized replacement를 먼저 기록한 뒤 원래 key를 교체·삭제하고,
  backup/rollback은 sanitized replacement에만 허용한다.
- `curl`은 기본적으로 Authorization/Cookie/API key와 auth 값을 masking해 표시·복사한다.
  사용자가 별도 reveal/copy를 명시하고 확인한 경우에만 일회성 원문을 만들며 persistence와
  history에는 저장하지 않는다.
- 실패·timeout·redirect도 예외가 아니다. 모든 redirect `Location`과 최종 URL을 redaction하고,
  cross-origin redirect에는 Authorization/Cookie를 전달하지 않는다. 네트워크 오류 문자열,
  response header/body, UI error, telemetry/log(현재는 telemetry 없음)에도 secret이 없어야 한다.
- persistence 직전 serialized output에 현재 secret 원문, known secret fingerprint와
  sensitive literal이 발견되면 write를 거부하고 안전한 오류만 표시한다.
- migration 결과와 제거 범위를 한 번 알리고 schema version/marker를 기록한다. 새 v2 safe
  replacement가 실패하면 기존 sanitized replacement만으로 rollback하고 raw 원문 복구는 하지
  않는다.

**완료 조건**

- request 성공·실패·timeout·redirect·history rename/copy 및 curl reveal/copy 모든 경로에서
  secret이 localStorage와 로그에 나타나지 않는다.
- raw History는 migration 실패 시에도 UI에서 즉시 격리되고, 삭제 성공 전에는 marker가
  생기지 않아 다음 실행에서 재시도된다. raw backup은 존재하지 않는다.
- Collection 직접 auth/header literal은 reference 또는 masking으로 바뀌고, 변환 불가 원문은
  어느 backup에도 남지 않는다.
- v0.4.2 hotfix에 localStorage fixture, redirect/error, cross-origin auth stripping,
  persistence rejection, fail-closed retry 테스트가 있으며 같은 구현과 fixture가 v0.5.0에서
  회귀 없이 유지된다.

## 4. P2 — 순서가 유동적인 필수 후속 작업

### P2-01. applink protocol v2와 handoff

- §2.2·§2.3 계약과 atomic claim/ack/restore store를 구현하고 round-trip/expiry/concurrency
  tests를 만든다.
- P2 첫 end-to-end 흐름은 Webhook Lab → API Playground로 한다. 이어서 Life Log → Knowledge를
  별도 P2 PR로 붙인다.
- Toolbox → API handoff는 Toolbox의 P3 integration PR에서 붙인다. Run/WSL → Log Lens는
  Log Lens bootstrap/receiver가 먼저 완성된 뒤 P3 producer PR로 연결한다. Run Manager의
  자체 log search는 P2 범위를 그대로 유지한다.
- 수신 앱 미설치·구버전·payload 만료·손상·중복 소비는 clipboard로 자동 fallback하지 않고
  재생성/설치/업데이트 선택지를 표시한다.

### P2-02. Port Manager — command와 안전한 identity

- Windows listener는 full command line, executable path, PID, process start time을 표시한다.
- WSL listener는 distro, protocol, address/port, PID, command, `/proc/<pid>/stat` start tick을
  보존한다.
- kill 직전에 endpoint와 process identity를 다시 조회한다. 재사용된 PID면 중단한다.
- container source는 engine/container id를 표시하고 process kill 대신 WSL Desktop의 명시적
  stop action으로 handoff한다.

### P2-03. Developer Toolbox — 도구 확장

- UUID v4·v7, ULID 생성. batch count와 대/소문자·hyphen format을 지원한다.
- HTML entity encode/decode, URL component encode/decode를 text tool로 제공한다.
- HMAC 생성·검증은 algorithm/key/input/output encoding을 명시한다.
- JWT decode 결과에는 “검증되지 않음”을 표시하고 signature verify가 성공해야 verified로
  표현한다.
- Lorem generator와 Markdown table formatter를 추가한다.
- QR generator는 text/URL/Wi-Fi preset, size, quiet zone, error correction, SVG/PNG
  save/copy를 제공한다. camera scan과 동적 QR 서비스는 제외한다.
- QR은 MIT/Apache-2.0의 pure-Rust [`qrcode`](https://github.com/kennytm/qrcode-rust)를
  설치물에 포함한다.

### P2-04. API Playground — OpenAPI

- OpenAPI 3.0/3.1 JSON·YAML local file과 URL을 읽는다.
- server 선택, path parameter, query/header/cookie, request body example을 request 초안으로
  변환한다.
- unsupported `$ref`, circular reference, auth scheme은 operation 단위 오류로 격리한다.
- import가 기존 collection을 덮어쓰지 않고 preview 후 새 collection 또는 merge를 선택한다.
- URL import는 network 기능이지만 local file import는 완전 오프라인으로 동작한다.

### P2-05. API Playground — GraphQL

- endpoint, query, variables JSON, operationName을 독립 입력으로 제공한다.
- 기존 headers/auth/environment/secret/history를 재사용한다.
- request body는 GraphQL over HTTP 표준 JSON으로 구성한다.
- response의 `data`와 `errors`를 함께 보여 주고 HTTP 오류와 GraphQL 오류를 구분한다.
- introspection explorer, schema cache, subscription, code generation은 v0.5.0에서 제외한다.

### P2-06. API Playground — SSE

- GET/POST와 기존 auth/header/body를 지원한다.
- `event`, multiline `data`, `id`, `retry`, comment를 streaming parser로 처리한다.
- pause는 rendering만 멈추고 buffer 상한을 유지하며 stop은 network task를 취소한다.
- 최대 10,000 event 또는 20MiB에서 오래된 항목부터 제거하고 제거 수를 표시한다.
- reconnect는 사용자가 켠 경우에만 server retry 값을 상한 내에서 적용한다.
- event/history/export에 secret masking을 적용한다.

### P2-07. API Playground — WebSocket

- ws/wss, custom headers/auth, text/binary send, ping/pong, close code/reason을 지원한다.
- connection state를 connecting/open/closing/closed/error로 구분한다.
- binary는 hex/text preview와 file save를 제공하고 임의 실행은 하지 않는다.
- message buffer도 10,000개 또는 20MiB 상한을 사용한다.
- MIT의 [`tokio-tungstenite`](https://github.com/snapview/tokio-tungstenite)를 설치물에
  포함한다. TLS는 rustls와 native root를 사용하고 certificate verification 해제는 제공하지 않는다.
- Socket.IO, STOMP, GraphQL subscription은 제외한다.

### P2-08. Everything+ — content index

- UTF-8/UTF-16 text, source code, Markdown 내용을 FTS5에 넣는다.
- PDF는 MIT [`lopdf`](https://github.com/J-F-Liu/lopdf), XLS/XLSX/ODS는 MIT pure-Rust
  [`calamine`](https://github.com/tafia/calamine), DOCX는 기존 MIT ZIP + MIT
  [`quick-xml`](https://github.com/tafia/quick-xml)로 text만 추출한다.
- 파일 기본 상한 20MiB, 추출 text 2,000,000자, processing 10초를 적용한다.
- `content_status`, `extractor_version`, `truncated`, `indexed_at`, `error_code`를 저장한다.
- extractor version 변경 시 해당 format만 증분 재색인한다.
- encrypted/password document는 `unsupported_encrypted`, scan-only PDF는 `no_text`, 손상 파일은
  `extract_error`로 남기고 filename search는 계속 제공한다.
- ZIP entry 수·압축 해제 합계·XML nesting·shared string을 제한해 zip bomb/OOM을 막는다.
- OCR, macro 실행, 서식, image, old binary DOC/PPT는 제외한다.

### P2-09. Knowledge — capture와 image

- `Ctrl+Alt+K` global quick capture를 기본값으로 하고 충돌 시 설정 변경을 안내한다.
- capture는 inbox target, title, body, tags preview 후 저장한다.
- clipboard는 명시적 user action에서 현재 값만 읽고 history를 저장하지 않는다.
- image paste/drop은 vault `assets/` 아래 content hash 이름으로 저장하고 relative Markdown
  link를 삽입한다.
- vault boundary, same-name collision, partial write를 방어하고 실패 시 문서를 변경하지 않는다.

### P2-10. Life Log — export와 로컬 요약

- date range를 Markdown, JSON, CSV로 export한다.
- session, Git, Run Manager, Knowledge source를 사용해 결정론적 daily/weekly digest를 만든다.
- 모든 문장·수치는 source와 집계 규칙을 펼쳐 볼 수 있어야 한다.
- Knowledge 전송은 `knowledge-draft/v1`을 사용하고 수신 화면에서 preview 후 저장한다.
- cloud/local LLM을 호출하거나 개인 활동 원문을 외부로 보내지 않는다.

### P2-11. Devbox Manager — 설치 root와 안전한 제거

- P1에서 정의한 versioned install-root locator를 먼저 읽고 쓴다. custom root의 변경은
  locator registry와 app-owned manifest를 함께 atomic update한다. 낮은 `registryRevision`은
  무시하지만 catalog revision이 올랐다는 이유만으로 기존 root를 무효화하지 않는다.
- custom install root의 canonical path, 권한, free space, 기존 install 충돌을 사전 검사한다.
- app binary 제거와 user data 제거를 분리하고 기본값은 user data 보존이다.
- remove target은 catalog와 install manifest에 동시에 기록된 app-owned path만 허용한다.
- root, home, workspace, unresolved environment variable, symlink/reparse point 탈출을 거부한다.
- 실패한 제거는 남은 파일과 복구 방법을 정확히 표시한다.

### P2-12. Code Pad — managed LSP의 오프라인 경로

- LSP catalog에 official source, version, license, SHA-256, archive layout을 고정한다.
- 이미 받은 archive/runtime cache를 network 없이 재사용한다.
- 사용자가 local archive를 선택해 동일 digest 검증 후 import할 수 있다.
- install 실패가 editor start/save/preview/Quick Open을 막지 않는다.
- runtime별 상태, 설치 source, last verification, 오류를 UI에 표시한다.

### P2-13. Run Manager — log search와 handoff contract

- stdout/stderr, text/regex, level, source, time range filter를 제공한다.
- result navigation은 원래 line number와 stream을 보존한다.
- running service log의 검색이 writer를 block하지 않는다.
- Log Lens가 아직 없는 동안에도 선택 source의 `log-source/v1` payload contract를 검증한다.
  실제 Log Lens producer 연결은 P3 Log Lens bootstrap 뒤의 integration PR에서 수행한다.

### P2-14. Workbench — project environment와 사전 검사

- project `.env` 파일을 선택하되 variable name/source/conflict만 profile에 저장한다.
- value preview는 masking하고 secret은 `crates/secrets` reference로만 주입한다.
- Start Workspace 전에 required app, WSL distro, working directory, port conflict, service
  dependency를 검사한다.
- 실패 단계·이미 실행 중이던 resource·Workbench가 시작한 resource를 구분한다.

### P2-15. Webhook Lab — fixture와 API handoff

- captured request를 masking된 fixture로 저장하고 response rule 초안으로 변환한다.
- request를 `api-request/v1`으로 API Playground에 보낸다.
- localhost bind 기본, LAN 공개 경고, body/history/rate 상한을 유지한다.
- Authorization/Cookie/API key는 raw copy 확인을 제외하면 항상 masking한다.

### P2-16. Repo Manager — 일상 Git 흐름

- commit graph/history/detail, commit/working tree diff를 제공한다.
- selected stage/unstage와 commit을 지원한다.
- fetch, fast-forward-only pull, current branch push를 지원한다.
- credential은 Git credential helper에 맡기고 devbox가 저장하지 않는다.
- dirty tree, detached HEAD, upstream 없음, diverged branch, in-progress rebase/merge를 사전
  감지하고 destructive recovery를 자동 실행하지 않는다.
- force push, reset, clean은 제공하지 않는다.

## 5. P3 — 선택 확정 보강

### P3-01. `devbox-launcher` 0.1.0 신규 앱

**책임**: 범용 OS launcher가 아니라 devbox 앱과 devbox가 알고 있는 작업 context의 진입점.

**식별자**

- app id: `devbox-launcher`
- product name: `DevboxLauncher`
- bundle identifier: `com.devbox.devboxlauncher`
- 기본 shortcut: `Ctrl+Alt+Space`, conflict 시 사용자 설정

**검색 대상**

- catalog app/action
- versioned Workbench profiles snapshot (`snapshot:workbench/profiles/v1`)
- versioned Repo Manager repositories/worktrees snapshot (`snapshot:repo-manager/repositories/v1`)
- versioned Run Manager jobs/services snapshot (`snapshot:run-manager/jobs-services/v1`)
- versioned Everything+ saved queries snapshot (`snapshot:everything-plus/saved-queries/v1`)
- versioned WSL Desktop profiles snapshot (`snapshot:wsl-desktop/profiles/v1`)
- Knowledge capture action
- Developer Toolbox transformer는 snapshot이 아니라 catalog action이다

**동적 source 계약**

- 위 snapshot은 producer가 `%LOCALAPPDATA%\devbox\integration\<app-id>\v1\summary.json`
  에 atomic replace로 발행한다. 각 envelope은 `schemaVersion`, `producer`, `producerVersion`,
  `generatedAt`, `data.views`를 가지며 각 view는 자체 `schemaVersion`, `freshnessMs`, `entries`를
  가진다. entry에는 안정적인 id, 표시 label, target/action kind, versioned payload만 둔다.
  app DB/localStorage를 Launcher가 직접 읽거나 producer별 private schema를 해석하지 않는다.
- `entries`는 profile/repository/worktree/job/service/query의 실행에 필요한 최소 id와
  display metadata만 포함하고 secret, environment value, raw log, full query result를 넣지
  않는다. snapshot schema가 바뀌면 새 `v<n>`을 발행하고 Launcher는 지원하는 version만
  소비한다.
- freshness가 만료된 source는 결과에 stale 표시를 붙이되 다른 source 검색을 막지 않는다.
  손상·권한 오류 source도 격리하고 진단 가능한 안전한 오류만 표시한다. snapshot action은
  실제 실행 전에 대상 앱 설치 여부와 payload version을 다시 확인한다.
- Developer Toolbox transformer와 Knowledge capture는 catalog의 static action entry로
  선언한다. Toolbox action은 transformer id만 전달하고, 사용자가 선택한 text는 preview 후
  `toolbox-text/v1` handoff로 일회성 전달한다. current clipboard는 명시적 action 동안만
  읽고 snapshot/catalog에 저장하지 않는다.

**동작**

- app launch/focus, profile/workspace/query open, Run task 실행을 applink로 전달한다.
- current clipboard/selected text는 action 실행 전 preview하며 저장하지 않는다.
- target app이 없으면 Manager의 해당 app 설치 화면을 연다.
- action index는 snapshot freshness를 표시하고 stale source 하나가 전체 검색을 막지 않는다.
- window는 shortcut으로 toggle되고 focus loss 시 닫히는 transient UI다.

**제외**: 범용 file/web/Windows setting 검색, arbitrary shell command, clipboard history,
PowerToys plugin host.

### P3-02. `log-lens` 0.1.0 신규 앱

**식별자**

- app id: `log-lens`
- product name: `LogLens`
- bundle identifier: `com.devbox.loglens`

**source**

- local file와 directory pattern
- Run Manager stdout/stderr handoff

- native action이 항상 primary이고 external open은 설치된 경우의 secondary action이다.
- package manager, 자동 update/uninstall, 앱 기능 대체로 확장하지 않는다.

## 7. PR 지도와 의존 순서

### 7.1 작업 파동

```text
Wave 0  docs/native-first + dependency policy
   └─► Wave 1  API secret fix (v0.4.2 hotfix)
   └─► Wave 2  crates/catalog + catalog v2 + revision/install-root locator + runtime catalog
                 ├─► inbound receivers
                 ├─► context-menu installed targets
                 └─► applink v2 + handoff
                       ├─► Webhook/API + Life Log/Knowledge handoff
                       ├─► Devbox Launcher bootstrap
                       └─► Log Lens bootstrap
Wave 3  snapshot cleanup ─► Workbench/Launcher/Log Lens integration
Wave 4  WSL terminal UX/profile
Wave 5  remaining P1 app features
Wave 6  P2 app features (prerequisite 충족 후 앱 간 순서 자유)
Wave 7  P3 existing-app enhancements
Wave 8  Log Lens + Devbox Launcher
Wave 9  version bumps + Windows RC + v0.5.0
```

handoff integration의 release 순서는 위 wave 안에서도 고정한다.

```text
P2  handoff core + atomic claim/ack/restore
 ├─► P2 Webhook Lab → API Playground
 └─► P2 Life Log → Knowledge
P3  Devbox Launcher/Log Lens bootstrap + catalog/snapshot consumers
 ├─► P3 Developer Toolbox → API Playground
 └─► P3 Run Manager/WSL Desktop → Log Lens producers
```

Toolbox·Run·WSL의 기존 native 기능은 각 P2/P1 범위를 유지하고, 위 표는 앱 간 연결 PR의
순서만 나타낸다.

### 7.2 PR 분리 규칙

- 기능 하나 = PR 하나다. GraphQL/SSE/WebSocket, PDF/DOCX/XLSX extractor는 각각 별도 PR이다.
- 공용 package/crate 도입과 13개 앱 적용은 한 mega-PR로 묶지 않는다.
- DB migration은 그것을 요구하는 기능 PR 안에 포함하고 upgrade fixture를 함께 둔다.
- 앱 version은 해당 앱의 v0.5.0 마지막 기능 PR 또는 release preparation PR에서 세 원본을
  함께 올린다.
- 모든 branch는 `docs/<scope>`, `fix/<app>/<scope>`, `feat/<app>/<scope>`, 공용 기능은
  `feat/workspace/<scope>` 또는 `feat/crates/<scope>`를 사용한다.

대표 branch:

```text
docs/v0.5.0-native-first-plan
fix/api-playground/secret-history
feat/crates/catalog
feat/workspace/catalog-capabilities
feat/crates/applink-handoff
feat/packages/context-menu
feat/wsl-desktop/workspace-profiles
feat/api-playground/sse
feat/everything-plus/pdf-content-index
feat/devbox-launcher/core
feat/log-lens/local-tail
```

### 7.3 v0.5.0 issue·milestone 원장

코드 PR을 만들기 전에 GitHub `v0.5.0` milestone과 저장소 내 issue/PR 원장을 만든다. 현재
열린 v0.4.1 Windows acceptance [issue #176](https://github.com/jihoon22-lee/devbox/issues/176)은
post-release 추적 항목으로 유지하고 v0.5.0 feature issue에 섞지 않는다.

원장에는 기능별로 다음 필드를 한 행씩 기록한다.

| 필드 | 규칙 |
|---|---|
| issue/PR | 기능 하나와 PR 하나를 1:1로 연결하고 번호를 기록 |
| priority/area | `P1`·`P2`·`P3`, 앱·crate·package·integration 라벨을 함께 부여 |
| prerequisite | catalogRevision/install-root locator, snapshot schema, handoff claim 등 선행 issue 번호 |
| acceptance | 관련 설계 §, 자동 테스트, Windows smoke checkpoint와 expected evidence |
| state | `planned → in-progress → code-review → CI → merged → Windows-verified` 순서 |
| release | 앱 목표 version, v0.4.2 hotfix 선행 여부, v0.5.0 포함 여부 |

P1·P2·선택 P3의 모든 행은 milestone에 들어가야 하며, dependency gate·catalog/install
locator·handoff core·신규 앱 bootstrap도 각각 독립 행으로 만든다. 상태를 수동으로 “완료”로
바꾸지 않고 PR 링크, CI run, smoke evidence를 남긴다. 기능을 P3에서 빼거나 release를
미루려면 원장에 이유·영향·새 milestone을 기록하는 별도 범위 변경 issue를 먼저 merge한다.

### 8.2 PR 완료 정의

모든 code PR은 영향 범위와 무관하게 저장소 규약의 다음 검증을 통과한다.

```bash
source ~/.cargo/env
cargo test
cargo check
pnpm build
```

관련 fixture/unit test, `.github/scripts/check-catalog.sh`, GitHub Actions Linux/Windows job도
통과해야 main으로 merge한다. 실제 Tauri 실행·installer 검증은 Windows에서 수행한다.

### 8.3 Windows RC 수동 검증

Windows 수동 검증은 최종 RC 한 번에 몰지 않고 다음 checkpoint마다 packaged build와
evidence를 남긴다. 각 checkpoint의 blocking failure는 다음 단계로 넘기지 않는다.

| checkpoint | 시점/대상 | 최소 smoke | evidence |
|---|---|---|---|
| W0 | v0.4.1 baseline, 첫 code PR 전 | issue #176의 남은 packaged/runtime 항목과 13개 앱 cold start | Windows build ID, 환경, 결과/미실행 사유 |
| H1 | v0.4.2 release 전 | backend-only secret resolve, raw History fail-closed 삭제, Collection 안전 변환, curl·응답·오류 redaction | sanitized localStorage fixture, API 0.3.2 packaged 실행, 평문 부재 evidence |
| W1 | 나머지 P1 merge 후 | catalogRevision/runtime fallback, install-root locator, single-instance/context menu, WSL clipboard/profile 기본 경로 | locator/catalog revision, 화면·로그 evidence |
| W2 | P2 core 후 | handoff claim/ack/restore와 Webhook→API·Life Log→Knowledge, API stream/document 경계, custom root install/remove | producer/consumer IDs, concurrent/crash retry 결과, packaged logs |
| W3 | P3 bootstrap 후 | Launcher source별 stale/corrupt 격리, Log Lens local source, catalog action, Toolbox→API 및 Run/WSL→Log Lens 연결 | source schema/revision, focus/handoff, failure recovery evidence |
| W4 | v0.5.0 RC | 15개 앱 전체 cold start, second-instance focus, installer/upgrade/rollback, multi-monitor/DPI/IME/긴 path | signed checklist와 release candidate artifact |

- 외부 전문 도구와 WinGet이 없는 Windows VM, network 차단 상태에서 모든 P1·P2 core flow.
- WSL/Git/container engine은 각각 “설치됨/없음” 환경을 분리한다.
- v0.4.1 packaged-runtime acceptance issue #176 시나리오 재실행.
- 15개 앱 cold start, second-instance focus, applink/handoff, window restore.
- 한글/공백/긴 path, IME, clipboard 권한 거부, multi-monitor/DPI 변화.
- v0.4.1 data upgrade: API History localStorage fail-closed migration, Collection sanitized
  replacement, Everything reindex, user data 보존.
- external tool catalog가 offline에서 반복 오류나 core 기능 비활성화를 만들지 않는지 확인.

### 8.4 release gate

1. P1, P2, 선택 P3의 모든 issue/PR이 merge됐다.
2. 목표 version이 Cargo.toml·tauri.conf.json·package.json에서 일치한다.
3. catalog, workspace, release matrix가 15개 앱에 대해 일치한다.
4. license notices와 dependency review가 최신이다.
5. GitHub Actions와 Windows RC acceptance가 통과했다.
6. 전용 worktree와 local/remote feature branch가 규약대로 정리됐다.
7. 그 뒤에만 `v0.5.0` tag와 release artifact를 게시한다.

## 9. 명시적 가정과 변경 통제

- v0.4.1은 안정판 기준선이며 v0.5.0 개발은 현재 13개 앱 동작을 회귀시키지 않는다.
- `v0.5.0`은 umbrella release tag이며 모든 앱 version을 0.5.0으로 맞추지 않는다.
- Data Inspector는 v0.5.0에서 별도 앱이 아니다.
- Devbox Launcher와 Log Lens는 책임과 수명주기가 기존 앱과 달라 별도 앱으로 만든다.
- P1·P2 core 기능을 external tool install/launch로 대체하지 않는다.
- 계획에 없는 runtime dependency, sidecar, telemetry, cloud service는 별도 설계 승인 없이
  추가하지 않는다.
- 일정 압박이 생겨도 선택 P3를 조용히 탈락시키지 않는다. release scope 변경 문서에서
  이유·영향·새 목표 release를 확정한다.
- 이 문서와 하위 설계가 충돌하면 이 문서의 product scope와 native-first 원칙이 우선하고,
  세부 protocol/알고리즘은 해당 하위 설계를 개정해 일치시킨다.

### 10.1 공통 범위 대조

- 기존 13개 앱: P1 context menu.
- 일반 persistent window: P3 `crates/window-state`; Launcher 등 transient window 제외.
- catalog를 소비하는 앱: v1/v2 fallback과 runtime/build-time fallback.

- 신규 두 앱: Cargo·pnpm·catalog·CI·release·Manager 등록을 동일 app bootstrap PR에서 수행.
