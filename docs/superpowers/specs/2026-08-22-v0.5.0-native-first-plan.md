## 0. 이 계획이 바로잡는 방향

devbox를 만드는 첫 번째 이유는 개발자가 자주 쓰는 기능을 찾고, 내려받고, 별도 앱을
실행하고, 다시 파일이나 클립보드로 데이터를 옮기는 반복을 줄이는 데 있다. 외부 도구와
경쟁한다는 이유만으로 기능을 제외해서도 안 되고, 반대로 이미 존재하는 모든 도구를
설치해 주는 package manager가 되어서도 안 된다.

v0.5.0은 다음 원칙으로 두 극단을 피한다.

1. **반복 작업은 devbox 안에서 끝낸다.** P1·P2 기능은 기능의 대상 자체가 외부 시스템인
   경우(WSL, Git, 원격 API, container engine 등)를 제외하면 인터넷과 별도 설치를 요구하지
   않는다.
2. **라이브러리는 기능의 일부로 번들할 수 있다.** 허용 가능한 라이선스이고 크기·보안·
   업데이트 경로를 검토한 Rust/TypeScript 라이브러리와 소형 sidecar는 devbox 설치물에
   포함할 수 있다.
3. **대형 전문 도구는 보완재다.** 전체 IDE, 범용 DB GUI, container desktop처럼 규모가 큰
   도구는 설치 감지·공식 설치·열기 연동을 선택적으로 제공할 수 있지만 native 기능의
   기본 버튼이나 유일한 경로가 될 수 없다.
4. **앱끼리 데이터를 넘길 때 사용자에게 운반을 시키지 않는다.** devbox가 송신자와
   수신자를 모두 제어하면 versioned `applink`, one-time handoff, read-only snapshot을 사용한다.
5. **필요한 범위만 소유한다.** 외부 도구의 제한적인 라이선스 때문에 필수 기능을 직접
   제공해야 할 때는 해당 코드를 포함하거나 모방하지 않고 공개 규격·관찰 가능한 동작에
   기반해 필요한 하위 기능만 독립 구현한다.

### 0.1 우선순위의 의미

| 우선순위 | 의미 | v0.5.0 처리 |
|---|---|---|
| P1 | 보안·공통 계약·이미 확정된 주요 기능. 후속 작업의 선행 조건 | 먼저 완료, 미완료 시 RC 진입 불가 |
| P2 | 순서만 유동적인 필수 후속 기능 | 전부 완료, 앱 간에는 병렬 진행 가능 |
| P3 선택 | 검토 후 v0.5.0에 넣기로 선택한 보강·신규 앱 | 릴리스 범위에 포함. 임의 탈락 금지 |
| 보류/제외 | 책임 중복·규모·안전·유지비 때문에 이번 범위에서 하지 않음 | 외부 도구 연결로 몰래 대체하지 않음 |

P3는 중요도가 P1·P2보다 낮다는 뜻이지 “시간이 남으면 한다”는 뜻이 아니다. 이 문서에서
선택된 P3를 v0.5.0에서 빼려면 별도 범위 변경 결정을 기록한다.

## 1. 개발 지침 — 네이티브 우선과 외부 도구

### 1.1 기능 평가 순서

기능을 새로 검토할 때 다음 순서로 판단한다.

1. 개발자가 얼마나 자주 수행하고, 현재 몇 번의 앱 전환·다운로드·파일/클립보드 전달이
   필요한지 기록한다.
2. 기존 devbox 앱의 책임에 자연스럽게 들어가는지 확인한다.
3. Rust/TypeScript와 번들 가능한 라이브러리로 오프라인 구현이 가능한지 확인한다.
4. 별도 앱으로 만들 만큼 입력·상태·수명주기·사용 흐름이 독립적인지 확인한다.
5. 이미 설치된 전문 도구를 활용하면 더 깊은 기능을 얻을 수 있는지 **보조 경로로만** 본다.
6. 구현하지 않는다면 외부 도구의 존재가 아니라 책임 중복, 안전, 크기, 유지비 중 실제
   사유를 기록한다.

### 1.2 오프라인 계약

- P1·P2의 UI는 runtime download 성공 여부에 따라 숨겨지거나 비활성화되지 않는다.
- 앱 시작과 로컬 데이터 처리에는 network call을 넣지 않는다.
- 원격 API 요청, Git remote, 앱 업데이트처럼 기능의 본질이 network인 경우에만 연결을
  요구한다. 같은 기능의 로컬 대상은 오프라인에서 동작해야 한다.
- WSL 기능은 설치된 WSL, Git 기능은 설치된 Git, container adapter는 설치된 engine을
  작업 대상으로 삼을 수 있다. 대상이 없으면 native 진단과 설치 안내를 표시하되 다른
  기능까지 막지 않는다.
- Code Pad의 LSP는 선택 기능이다. 편집·저장·preview·Quick Open은 LSP와 무관하게 동작한다.
- 외부 전문 도구가 없거나 WinGet이 없거나 인터넷이 차단돼도 P1·P2와 외부 도구 이외의
  P3는 동일하게 동작한다.

### 1.3 번들 의존성 기준

각 runtime 의존성 PR은 다음 표를 채운다.

| 항목 | 필수 내용 |
|---|---|
| 목적 | 어떤 사용자 기능을 가능하게 하는지 |
| 대안 | 자체 구현·다른 라이브러리·외부 도구 연결과 비교 |
| 출처 | 공식 저장소와 배포 원본 |
| 고정 | 버전, lockfile, binary면 SHA-256·서명 |
| 라이선스 | 앱 배포·수정·고지 의무 |
| 크기 | 설치 파일과 메모리 증가 실측 |
| 보안 | advisory, 입력 상한, sandbox/권한 경계 |
| 오프라인 | 설치 후 network 없이 동작하는지 |
| 유지보수 | 업데이트 감시 주체와 제거 전략 |

- MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, Zlib, Unicode-3.0은 자동 허용 후보다.
- MPL, LGPL, CDDL과 dual-license의 제한 조합은 PR에서 수동 검토한다.
- GPL, AGPL, SSPL, source-available, proprietary runtime은 기본 설치물에 포함하지 않는다.
- 라이선스가 제한적인 도구의 기능을 자체 구현하더라도 코드를 복사하거나 reverse-engineered
  비공개 protocol에 의존하지 않는다.
- `deny.toml`과 `THIRD_PARTY_NOTICES.md`를 추가하고 Cargo·pnpm license 검사를 CI에 넣는다.
- v0.5.0에서 새 sidecar는 도입하지 않는다. 아래 선택 기능은 모두 정적 라이브러리 또는
  앱 내부 Rust 로직으로 구현 가능하다.

### 1.4 외부 전문 도구의 역할

Devbox Manager의 `Related Tools`는 다음만 제공한다.

- 설치 여부와 감지 근거
- 공식 사이트·공식 라이선스 링크
- 사용자가 확인한 뒤 실행하는 WinGet 설치
- 설치된 executable 실행 또는 현재 path/file 열기

자동 설치, background update, 광범위한 package search, 일괄 제거, 외부 도구 설정 파일의
무단 수정은 하지 않는다. PowerToys, Windows Terminal, VS Code, Bruno, DBeaver/DB Browser,
GitHub Desktop, Podman/Docker Desktop 정도의 제한된 전문 보완재만 다룬다. 각 앱의 native
동작을 primary action으로 유지하고 외부 도구 열기는 secondary action으로 둔다.

## 2. 공통 아키텍처와 공개 계약

### 2.1 app catalog schema v2

`apps/catalog.json`의 `schemaVersion`을 `2`로 올리고 각 앱에 capability를 선언한다. 모든
카탈로그 사본에는 저장소가 단조 증가시키는 `catalogRevision`을 함께 기록한다.

```json
{
  "schemaVersion": 2,
  "catalogRevision": 1,
  "apps": [
    {
      "id": "api-playground",
      "accepts": ["handoff:api-request/v1"],
      "produces": ["handoff:api-request/v1"]
    }
  ]
}
```

기본 target은 `path`, `workspace`, `query`, `profile`이고 구조화 payload는
`handoff:<kind>/v<n>`, snapshot은 `snapshot:<producer>/<kind>/v<n>` 형식의 문자열로
표현한다.

catalog의 optional `actions`는 `actionId`, `actionVersion`, label, target과 versioned
payload kind만 선언하는 정적 entry다. 실행 시점의 profile/job/query 상태나 secret은 catalog에
넣지 않으며, 동적 상태는 §2.4 snapshot 계약으로만 발행한다.

- v1 문서나 `accepts`/`produces`가 없는 항목은 빈 배열로 읽는다.
- Manager가 설치·업데이트 때 `%LOCALAPPDATA%\devbox\catalog.json`을 tmp+rename으로 쓴다.
- build-time 사본과 runtime 사본의 freshness는 `catalogRevision`으로 결정한다. 유효하고
  build-time revision 이상인 runtime 사본은 사용하고, 더 오래됐거나 revision이 없거나
  손상된 runtime 사본은 무시하고 build-time 사본으로 폴백한다. 같은 revision이면 runtime
  사본을 사용한다. Manager는 현재 사본보다 낮은 revision을 원자적으로 덮어쓸 수 없다.
- runtime 사본이 없거나 손상되면 각 앱의 build-time 사본을 사용한다.
- catalog schema, build/runtime 사본 읽기, capability filter는 새 순수 `crates/catalog`가
  담당한다. Manager와 메뉴를 가진 앱이 공동 소비한다.
- `crates/launch::installed_targets(kind)`는 `crates/catalog` 결과 중 실제 executable이
  해석되는 앱만 반환한다. `crates/applink`는 argv 계약에만 집중해 `launch`와 순환 의존하지
  않는다.
- install root와 executable 해석은 `crates/launch`만 담당한다. 각 앱이 registry나 설치
  디렉터리를 다시 구현하지 않는다.
- catalog와 custom install root의 선행 locator 계약은 고정 위치의
  `%LOCALAPPDATA%\devbox\install-roots\v1\registry.json`이다. registry에는
  `schemaVersion`, 단조 증가하는 `registryRevision`, 기록 당시의 `catalogRevision`, `rootId`,
  canonical `path`, app-owned manifest 경로와 갱신 시각만 기록하고, tmp+rename으로 갱신한다.
  catalog 변경만으로 기존 root를 무효화하지 않으며 `catalogRevision`은 provenance와 app-id
  검증에만 사용한다. `crates/launch`는 이 versioned registry와
  manifest를 먼저 해석하며, v0.4.x 고정 위치는 migration 기간의 read-only fallback으로만
  읽는다. unresolved environment variable, root/home/workspace, symlink/reparse 탈출과
  manifest에 없는 executable은 거부한다. Manager의 custom root selector는 이 계약을 소비해
  empty-root pointer 전환만 수행하고, 기존 설치 migration·binary/user-data 제거는 별도 #309
  경계로 남긴다. locator 계약을 충족하지 못한 상태에서 path를 임의로 이동·삭제하는 구현은
  허용하지 않는다.
- catalog는 devbox 앱 전용이다. 외부 전문 도구 catalog와 섞지 않는다.

### 2.2 applink protocol v2

현재 `OpenTarget::Path`, `Profile`, `Workspace`, `Query`에 다음 변형을 추가한다.

```rust
Task { id: String }
Install { app_id: String }
Handoff { kind: String, id: String }
```

- `PROTOCOL_VERSION`은 2로 올린다.
- v1 argv와 맨 앞 위치 path는 계속 읽는다.
- 구버전 수신자가 모르는 flag를 받아도 평소 화면으로 열리고 crash하지 않는다.
- cold start와 이미 실행 중인 instance 모두 `PendingOpen`에 넣고 frontend가 pull한다.
- 실행 중 수신은 창 복원·focus 후 event와 pending pull을 함께 사용하되 동일 request를
  두 번 적용하지 않는다.
- `Task`와 `Install`은 payload를 운반하지 않으며 수신 앱이 현재 저장소/catalog를 다시
  확인한다. handoff envelope 모양은 바뀌지 않는다.

### 2.3 one-time handoff

handoff envelope은 다음 의미 필드를 가진다.

```text
protocolVersion, id, kind, sourceApp, targetApp?, createdAt, expiresAt, payload
```

- ID는 충돌 예측이 어려운 128-bit random 값이다.
- 기본 TTL은 10분, 직렬화 상한은 10MiB다.
- `CreateNew` 의미로 생성하고 완성된 JSON만 원자적으로 노출한다.
- target app이 지정된 payload는 다른 앱이 소비하지 않는다.
- schema·kind·source·target·size·expiry를 확인한 뒤 읽는다.
- 성공한 consume은 즉시 삭제한다. 처리 실패는 TTL까지 남겨 재시도할 수 있게 하고 오류를
  발신자/수신자에 표시한다.
- 만료·손상 파일은 별도 quarantine 없이 지우며 secret 값을 error에 포함하지 않는다.
- 10MiB를 넘는 binary는 handoff root에 복제하지 않고 사용자가 선택한 파일 또는 app-owned
  임시 파일의 canonical path·size·digest를 전달한다.

one-time 소비는 단순한 read-then-delete가 아니다. 동시 실행과 consumer crash를 고려해 다음
상태를 사용한다.

```text
pending --atomic claim(consumer+lease)--> claimed --ack--> consumed/deleted
   ^                                      |
   └----------- restore/nack --------------┘
```

- producer는 `pending/<id>.json`을 create-new + atomic rename으로 노출한다. consumer의
  `claim`은 exclusive rename/claim record로 소유자와 짧은 lease를 기록해 두 consumer가
  같은 payload를 동시에 처리하지 못하게 한다.
- 성공한 처리만 `ack`할 수 있고, ack는 claim token을 확인한 뒤 삭제한다. validation 또는
  import 실패는 `restore`로 pending에 원자적으로 되돌려 TTL 안에서 재시도한다. consumer가
  죽으면 lease expiry 후 복구할 수 있다. 만료·손상 payload는 안전한 오류만 남기고 삭제한다.
- claim/ack/restore는 target, kind, schema, id와 consumer token을 매번 검증한다. duplicate
  claim/ack, wrong target, crash recovery, concurrent consumer는 계약 테스트로 고정한다.
- 기본 claim lease는 60초이며 `expiresAt`을 넘길 수 없다. 처리에 더 긴 시간이 필요하면 같은
  token으로 상한 내 갱신하고, 만료 token의 ack/restore는 거부한다.

표준 kind:

| kind | 발신 | 수신 | payload 목적 |
|---|---|---|---|
| `api-request/v1` | Webhook Lab, Toolbox, API Playground | API Playground | method, URL, templated headers/body |
| `webhook-fixture/v1` | API Playground, Webhook Lab | Webhook Lab | local response fixture 초안 |
| `knowledge-draft/v1` | Life Log | Knowledge | 제목·본문·태그 초안. Launcher는 이를 clipboard text로 만들지 않음 |
| `log-source/v1` | Run Manager, WSL Desktop | Log Lens | source adapter 설정과 검증된 path/id |
| `toolbox-text/v1` | Launcher (receiver integration 후) | Developer Toolbox | 입력 text와 추천 transformer |

모든 payload는 secret 원문을 금지한다. API request는 `${SECRET_NAME}` 참조만 전달한다.

### 2.4 snapshot bus 정리

snapshot은 producer가 소유한 지속 상태의 read-only 요약이며 command 전달에 사용하지 않는다.

| snapshot | producer | consumer | 내용 |
|---|---|---|---|
| `life-log/projects/v1` | Life Log | Workbench | 관찰된 프로젝트와 최근 활동 |
| `knowledge-base/activity/v1` | Knowledge | Life Log | 작성·수정 수와 노트 식별자 |
| `wsl-desktop/runtime/v1` | WSL Desktop | Workbench, Life Log | terminal·container·구조화 port |
| `run-manager/status/v1` | Run Manager | Workbench, Life Log, Launcher | job/service 상태와 최근 실행 |
| `workbench/profiles/v1` | Workbench (후속 producer) | Launcher | recent profile/workspace action metadata |
| `repo-manager/repositories/v1` | Repo Manager (후속 producer) | Launcher | repository/worktree action metadata |
| `run-manager/jobs-services/v1` (`status/v1` 호환) | Run Manager | Launcher | job/service action metadata |
| `everything-plus/saved-queries/v1` | Everything+ | Launcher | query/filter action metadata |
| `wsl-desktop/profiles/v1` | WSL Desktop (후속 profile producer) | Launcher | profile/layout action metadata |

- Workbench의 Life Log DB 직접 조회를 삭제한다.
- Life Log의 자체 snapshot reader를 `crates/integration`으로 교체한다.
- `discover()`는 `<common_root>/integration/*/v*/summary.json`을 스캔한다.
- 한 producer의 손상 JSON은 나머지 producer 발견을 막지 않는다.
- snapshot에는 데이터 freshness, producer version, schema version, generated time을 포함한다.
- secret, Authorization, Cookie, raw environment value는 저장하지 않는다.
- 한 producer는 version별 `summary.json` 하나만 소유한다. 여러 snapshot kind가 필요하면
  envelope의 `data.views`에 kind별 versioned view를 함께 넣고 한 번에 atomic replace한다.
  예를 들어 WSL Desktop은 `runtime`과 `profiles`, Run Manager는 `status`와 `jobs-services`를
  같은 producer summary에 발행한다. consumer는 catalog의
  `snapshot:<producer>/<kind>/v<n>` capability로 해당 view만 선택하며, producer가 같은 파일을
  kind별 writer로 서로 덮어쓰지 않는다.
- Launcher의 profile/repository/saved-query path는 bounded consumer 계약이다. producer가 아직
  없으면 `missing`으로 해당 source만 격리하며, 기존 WSL runtime producer와 Life Log→Knowledge
  `knowledge-draft/v1` action을 제거하거나 대체하지 않는다.

의존성 검토 PR에는 다음 경계도 반드시 결정·테스트한다.

- YAML parser(`yaml@2.9.0`)와 JSON validator(`jsonc-parser@3.3.1`)는 문서 크기, alias/anchor 수,
  nesting depth, duplicate key와 custom tag 처리 정책을 고정한다. OpenAPI local/URL import 모두
  같은 parser 상한과 오류 격리를 사용하며 parser가 임의 object prototype을 만들지 않게 한다.
  URL source는 기존 native `reqwest`의 별도 timeout/redirect/response-size 경계에서만 읽는다.
- ULID는 canonical Crockford Base32·대문자/소문자 표시·batch 상한을 명시한다. HMAC는
  지원 algorithm(최소 SHA-256, 필요 시 SHA-384/SHA-512), raw/hex/base64 key 입력 형식,
  key·input 상한, 출력 encoding을 PR에서 고정하고 key는 저장·로그·history에 남기지 않는다.
  #288에서 고정한 HMAC wire contract는 다음과 같다.
  - `algorithm`은 exact lower-case `sha256`·`sha384`·`sha512`만 허용한다. `keyEncoding`과
    `messageEncoding`은 `utf8`, `hex`, padded RFC 4648 `base64`, unpadded RFC 4648
    `base64url` 중 하나이고, `outputEncoding`은 `hex`(lowercase), `base64`(padded),
    `base64url`(unpadded) 중 하나다. Hex는 대·소문자를 허용하지만 Base64 alphabet,
    padding, unused pad bit는 canonical 표현이어야 한다.
  - Generate 요청은 `{algorithm, key, keyEncoding, message, messageEncoding, outputEncoding}`
    이고 `hmac_generate`는 결과 tag 문자열만 반환한다. Verify 요청은 여기에 `expectedTag`를
    더하며 `hmac_verify`는 `boolean`만 반환한다. Verify의 malformed encoding은 고정 오류,
    canonical encoding을 만족하지만 tag 길이·내용이 다른 경우는 `false`다.
  - key/message 각각 decoded 1,000,000바이트·encoded text 2,100,000바이트, expected/result
    tag 128자 상한을 native와 browser에서 동일하게 검사한다. key는 비어 있지 않아야 하며
    message는 비어 있어도 된다. 모든 malformed/unknown/oversized 입력과 primitive exception은
    원문·secret·경로·플랫폼 세부사항을 포함하지 않는 고정 오류로 변환한다.
  - native는 RustCrypto `hmac 0.13.0`의 `Hmac<Sha256|Sha384|Sha512>`와 기존 `sha2`를
    사용하고 verify는 `Mac::verify_slice`의 constant-time 경계를 사용한다. 표준 `base64`
    crate는 encoding만 담당하며 수제 암호 primitive를 만들지 않는다. browser preview는
    Web Crypto `subtle.importKey`·`sign`·`verify`로 같은 계약을 수행한다. 두 경로 모두
    network, external generator, sidecar, persistence를 사용하지 않는다.
  - key/message는 request 처리 중 메모리와 현재 화면에만 있고 localStorage/history/log/telemetry
    또는 외부 API로 보내지 않는다. 생성 tag의 copy/save는 사용자가 명시한 output action만
    허용한다. UI는 operation·algorithm·encoding을 실행 중 잠그고 IME, duplicate action,
    stale response, unmount와 `role=status`/`role=alert`/label 포커스 계약을 fixture로 검증한다.
  JWT verify는 허용 algorithm(HS 계열의 정확한 목록), `alg=none` 거부, key의 최소 길이와
  raw/hex/base64 범위를 명시하며 PEM/RSA/EC 키를 범위 밖으로 두는지 결정한다. #289에서
  고정한 계약은 HS256·HS384·HS512만 허용하고 PEM/JWK/RSA/EC를 파싱하지 않는 것이다. key는
  raw UTF-8, hex, padded RFC 4648 Base64, unpadded Base64URL 중 하나를 명시하며 decoded
  key는 각각 1,000,000바이트 이하이고 HS256/384/512에 대해 최소 32/48/64바이트다. encoded
  key는 2,100,000바이트 이하이고, `none`, algorithm casing 변형, 다른 HMAC/비대칭 algorithm,
  unknown key encoding은 같은 고정 오류로 거부한다. compact token은 256KiB, header/payload
  segment는 각각 96KiB, JSON은 64KiB·depth 32·value/key node 10,000개·문자열 16KiB,
  formatted output은 256KiB로 제한한다. 세 segment는 unpadded canonical Base64URL이어야
  하며 non-zero pad bit, `=`, 잘못된 UTF-8/JSON, duplicate key, malformed `crit`와 알려지지
  않은 critical header는 부분 결과 없이 fail-closed한다. `alg`는 header에서만 읽고 요청이
  별도 algorithm을 덮어쓰지 않으며 서명은 알고리즘의 정확한 32/48/64바이트 길이를 요구한다.
- QR PNG/image clipboard는 matrix 생성 crate와 PNG encoder의 license/source/digest를
  별도로 검토한다. dimension·memory 상한, save 경로의 canonical 검증, image clipboard가
  지원되지 않거나 실패한 Windows에서의 명시적 text/PNG-file fallback을 테스트하며,
  사용자 확인 없는 자동 clipboard 저장은 하지 않는다.
- global shortcut은 `tauri-plugin-global-shortcut` 후보의 version/license/Windows 등록
  동작을 검토한다. 등록 충돌을 감지해 사용자 설정으로 변경하고 기존 단축키를 조용히
  빼앗지 않으며, 등록 실패 시 앱 내부 action은 계속 동작해야 한다.

**완료 조건**

### P1-02. API Playground secret history 결함

**문제**

현재 저장소는 DB transaction이 아니라 프론트 `localStorage`를 사용한다. `App.tsx`의
`apip-history`에 실행된 `effectiveReq`를 그대로 쓰고, `lib/collections.ts`의
`apip-collections`에는 사용자가 저장한 `ApiRequest` 전체가 들어간다. 따라서 resolved
secret이 History뿐 아니라 Collection의 auth/header에도 남을 수 있다. `buildCurl()`도
현재 Bearer/API key/Basic 값을 평문으로 만든다. 이 사실을 SQLite migration 전제로 문서화하지
않고 구현 계약의 기준으로 삼는다.

**v0.4.2 선행 보안 핫픽스**

이 결함은 v0.4.1 안정판에도 있으므로 v0.5.0 완료까지 기다리지 않고 v0.4.2에서 P1-02 전체를
먼저 완성한다. backend-only resolve, History/Collection v2 persistence와 migration, curl·응답·
오류 redaction을 일부만 적용한 채 안정판을 게시하지 않는다. 코드 PR에서 API Playground 앱
버전을 0.3.2로 올리고, 별도 release-preparation PR과 Windows hotfix smoke 뒤 `v0.4.2` tag를
게시한다. 이 hotfix는 v0.5.0 범위를 축소하는 별도 구현이 아니라 P1-02를 선행 완료하는 보안 gate다.

**구현**

- `RequestTemplate`, `ResolvedRequest`, `PersistedHistoryRequest`를 분리한다.
- secret resolve는 전송 직전 backend 메모리에서만 수행하고 resolved 값은 frontend state,
  clipboard, persistence, log로 반환하지 않는다.
- History v2에는 `${SECRET_NAME}`/`{{SECRET_NAME}}` 참조가 남은 template과 고정 마스킹 값만
  저장한다. URL/query/header/body/auth/response/error 및 redirect의 각 hop을 같은 redaction
  함수로 처리한다.
- `apip-history` v1은 안전성을 증명할 수 없으므로 **내용을 변환하거나 raw backup을 만들지
  않는다.** 최초 실행 시 UI에서 즉시 격리해 렌더링·검색·재전송 대상에서 제외하고 빈 v2
  History를 기록한다. 그 뒤 원래 key를 삭제하고 read-back이 성공한 경우에만
  `apip-history-v1-migrated` marker를 기록한다. 삭제·read-back·marker 기록 중 하나라도
  실패하면 marker를 기록하지 않고 raw key를 UI에서 계속 격리한 채 다음 실행에서 삭제를
  재시도한다(fail-closed). raw key를 backup/rollback key로 복제하는 것은 금지한다.
- migration 순서는 `raw 격리 → 빈 v2 store 기록 → raw key 삭제 → raw key
  read-back 부재 확인 → marker 기록`으로 고정한다. v2 기록이 실패하면 raw key를
  삭제하지 않고 다음 실행에서 재시도하며, rollback이 필요할 때도 sanitized replacement만
  대상으로 한다.
- Collection(`apip-collections`)은 사용자 자산이므로 보존한다. 이미 reference인 auth와
  header는 보존하고, 직접 입력된 Authorization/Cookie/Set-Cookie/API-key 계열과 auth
  username/password/token/api value는 확인 가능한 environment reference로 바꾸거나 고정
  마스킹과 `requiresSecretReview` 표시로 안전 변환한다. 변환할 수 없는 원문은 별도
  backup에 남기지 않는다. sanitized replacement를 먼저 기록한 뒤 원래 key를 교체·삭제하고,
  backup/rollback은 sanitized replacement에만 허용한다.
- `curl`은 기본적으로 Authorization/Cookie/API key와 auth 값을 masking해 표시·복사한다.
  사용자가 별도 reveal/copy를 명시하고 확인한 경우에만 일회성 원문을 만들며 persistence와
  history에는 저장하지 않는다.
- 실패·timeout·redirect도 예외가 아니다. 모든 redirect `Location`과 최종 URL을 redaction하고,
  cross-origin redirect에는 Authorization/Cookie를 전달하지 않는다. 네트워크 오류 문자열,
  response header/body, UI error, telemetry/log(현재는 telemetry 없음)에도 secret이 없어야 한다.
- persistence 직전 serialized output에 현재 secret 원문, known secret fingerprint와
  sensitive literal이 발견되면 write를 거부하고 안전한 오류만 표시한다.
- migration 결과와 제거 범위를 한 번 알리고 schema version/marker를 기록한다. 새 v2 safe
  replacement가 실패하면 기존 sanitized replacement만으로 rollback하고 raw 원문 복구는 하지
  않는다.

**완료 조건**

- request 성공·실패·timeout·redirect·history rename/copy 및 curl reveal/copy 모든 경로에서
  secret이 localStorage와 로그에 나타나지 않는다.
- raw History는 migration 실패 시에도 UI에서 즉시 격리되고, 삭제 성공 전에는 marker가
  생기지 않아 다음 실행에서 재시도된다. raw backup은 존재하지 않는다.
- Collection 직접 auth/header literal은 reference 또는 masking으로 바뀌고, 변환 불가 원문은
  어느 backup에도 남지 않는다.
- v0.4.2 hotfix에 localStorage fixture, redirect/error, cross-origin auth stripping,
  persistence rejection, fail-closed retry 테스트가 있으며 같은 구현과 fixture가 v0.5.0에서
  회귀 없이 유지된다.

이 view를 소비하지만 WSL/Docker 명령이나 producer 파일을 소유하지 않는다. producer는
`%LOCALAPPDATA%\\devbox\\integration\\wsl-desktop\\v1\\summary.json` 하나만 만들고, 기존
`crates/integration::Envelope::with_views`와 `write_atomic`을 사용한다. `profiles` 등 다른
view가 추가될 때도 kind별 writer가 파일을 서로 덮어쓰지 않고 하나의 complete envelope으로
교체한다.

**공개 wire shape**는 공용 envelope의 다음 view로 고정한다.

```json
{
  "schemaVersion": 1,
  "producer": "wsl-desktop",
  "producerVersion": "<Cargo package version>",
  "generatedAt": "<UTC, second precision>",
  "data": {
    "views": {
      "runtime": {
        "schemaVersion": 1,
        "freshnessMs": 0,
        "entries": [
          {
            "id": "Ubuntu",
            "name": "Ubuntu",
            "state": "running",
            "terminalCount": 2,
            "dockerAvailability": "available",
            "containers": [
              {
                "id": "0123456789abcdef",
                "name": "api",
                "state": "running",
                "portMappings": [
                  { "published": 8080, "target": 80, "protocol": "tcp" }
                ]
              }
            ]
          }
        ]
      }
    }
  }
}
```

- WSL에는 별도 숫자 distro ID가 없으므로 `id`와 `name`은 검증된 등록 이름으로 동일하게
  유지한다. entry는 running distro만 포함하며 `state`는 `running`으로 정규화한다. stopped
  distro는 목록·Docker·terminal 조회 대상에서 모두 제외하고, 조회를 위해 시작하지 않는다.
- `dockerAvailability`는 `available`, `missing`, `error`, `notQueried`만 허용한다. 성공한
  빈 Docker 출력은 `available` + 빈 `containers`, exit 127은 `missing`, 그 밖의 non-zero
  종료는 `error`다. timeout, stdout/stderr overflow, I/O 또는 malformed row는 수집 실패이므로
  `error` 결과로 위장하지 않고 last-good을 보존한다. `notQueried`는 future/fixture에서
  명시적으로 조회하지 않은 entry를 표현하는 예약 값이며, 정상 collector가 일부 distro를
  조용히 건너뛰는 데 사용하지 않는다.
- container는 hex `id`, 허용된 Docker name, 정규화된 lifecycle `state`, 구조화된
  `portMappings`만 가진다. state는 `created|dead|exited|paused|removing|restarting|running|unknown`
  중 하나이며 Docker의 raw status 문장을 저장하지 않는다. image, raw status/ports, command,
  labels, mount/volume/socket path, environment는 요청·파싱·snapshot 모두에서 제외한다.
- mapping은 `published`, `target`(각 1~65535), `protocol`(`tcp|udp|sctp`)만 가진다.
  `0.0.0.0:8080->80/tcp`, `:::8080->80/tcp`, `[::]:8080->80/tcp`처럼 주소만 다른 binding은
  같은 tuple로 dedupe하며, `80/tcp` exposed-only와 range/invalid protocol/port는 후보에서
  제외한다. mapping과 container는 ID/port tuple 기준으로 deterministic sort한다.

**수집 경계와 exact argv**는 다음으로 고정한다.

```text
wsl.exe --list --running --quiet
wsl.exe -d <validated-distro> -- docker ps -a --no-trunc --format \
  {{.ID}}\t{{.Names}}\t{{.State}}\t{{.Ports}}
```

`<validated-distro>`는 `crates/wsl::validate_distro_name`과 128-byte 상한을 통과한 단일
argv 요소다. shell, `bash -lc`, `sh -c`, 사용자 명령, cwd, PATH/env 확장, Docker start/stop/
restart는 사용하지 않는다. stdin은 null로 닫고 stdout/stderr를 각각 bounded reader로 동시에
drain해 pipe deadlock을 막는다. 한 child의 총 실행 시간은 5초로 고정하며 timeout/cancel과
overflow에서 child를 kill하고 wait한다. stderr는 오류 분류·로그·IPC·snapshot에 절대 반영하지
않는다. WSL 목록은 최대 4MiB, Docker raw stdout 4MiB, stderr 64KiB, line 16KiB까지만 읽는다.

**bounds와 fail-closed 규칙**은 parser와 serialization 직전에 이중 검증한다.

| 대상 | 상한/정책 |
|---|---|
| running distro | 64개, name 128 bytes, 중복/unsafe/control은 전체 수집 실패 |
| container | 256개/distro, 512개 전체, ID 64 bytes hex, name 256 bytes ASCII-safe |
| port mapping | 32개/container, 1,024개 전체, port 1~65535 |
| terminal | 256개/distro, session id/pane key/cwd/title/command는 집계에 사용하지 않음 |
| process output | stdout 4MiB, stderr 64KiB, line 16KiB, 5초 timeout |
| final file | `crates/integration` 공용 10MiB 상한, single `summary.json` |

상한 초과·중복 ID·malformed tab row·unsafe name·identity mismatch는 빈 배열로 축소하거나
일부만 발행하지 않는다. running distro 목록을 완전히 읽고 terminal count를 snapshot한 뒤
각 distro를 순차 조회하고 모든 결과를 정규화한 후에만 envelope을 직렬화한다. 하나라도
완성하지 못하면 `write_atomic`을 호출하지 않아 기존 `summary.json`을 보존한다. write 자체의
경로/link/size/JSON 검증 실패도 `crates/integration`의 atomic writer가 target을 교체하지
않도록 한다. 임시 파일은 공용 writer가 소유하며 성공 후 `summary.json` 하나만 남는다.

**writer lifecycle**은 producer당 하나다. 앱 setup은 Tauri async runtime에서 60초 주기
writer를 시작하고, initial publish는 같은 경로의 250ms debounce worker로 실행한다.
성공한 dashboard distro refresh, Docker refresh, terminal start, explicit close, PTY reader
cleanup은 동일 coordinator의 pending bit를 세워 하나의 worker로 합친다. worker가 실행 중일
때 새 trigger가 들어오면 다음 complete collection을 한 번만 추가하고, trigger 간 WSL/Docker
process를 병렬로 실행하지 않는다. snapshot 실패는 고정된 안전 메시지만 로그에 남기고
terminal I/O·기존 dashboard action·앱 startup을 막지 않는다.

**fixture와 검증 범위**는 producer PR에 포함한다.

- exact argv가 `--list --running --quiet`와 `docker ps -a --no-trunc --format` 외 명령·shell·
  mutation을 만들지 않는지 확인한다.
- UTF-8/UTF-16 decoded running list, 공백 이름, default marker, stopped 제외, duplicate/
  control/path-like/128-byte 초과 distro를 재현한다.
- empty Docker output, missing(exit 127), non-zero error, malformed row, duplicate ID,
  oversized stdout/stderr/line, unsafe name, unknown state를 각각 분류한다. malformed/timeout/
  overflow는 error availability가 아니라 last-good 보존으로 검증한다.
- IPv4/IPv6 duplicate binding, bracketed IPv6, exposed-only, range/invalid port·protocol,
  deterministic sort/dedupe와 32/1,024 mapping bounds를 fixture로 고정한다.
- terminal count가 distro별 0/256/257일 때와 stopped distro session이 공개 entry로 새지 않는지
  확인한다. session id·pane key·cwd·title·profile command가 JSON/로그에 없는지 검사한다.
- atomic first write/replacement, malformed collection 이후 byte-identical last-good, concurrent
  trigger의 single worker/partial JSON 부재, no temp residue를 확인한다.
- `apps/catalog.json` revision 6에 `snapshot:wsl-desktop/runtime/v1` capability가 있고,
  `crates/catalog` producer filter가 `wsl-desktop` 하나만 반환하는지 확인한다.

이 PR은 Workbench #281 consumer/UI/ProfileStore, WSL/Docker mutation·resource summary, Run
Manager service ID 추론, Log Lens adapter, raw runtime log/telemetry, profile schema와 stopped
distro startup을 포함하지 않는다. Windows packaged W1에서는 valid/missing Docker, empty list,
stopped distro, timeout/last-good, snapshot privacy 및 실제 integration path를 확인하고, WSL이
없는 Linux 개발 환경에서는 위 순수 parser/normalization/atomic fixture만 실행한다.

**2026-08-26 #265 구현 상태.** 기존 Base64 encode/decode 두 화면을 하나의 byte codec으로

무시하고 invalid alphabet·padding·non-zero pad bit의 1-based 원문 문자 위치를 표시한다.

  결과 상태를 항상 `unverified`로 시작한다. decode 성공은 서명 검증을 의미하지 않으며,

  호출하지 않는다. 파일명은 입력 filename이 아닌 SHA-256 lowercase content hash와 고정 extension으로

  경로 길이 초과는 native/frontend 양쪽에서 거부한다.

  publication(Unix hard-link와 parent directory `fsync`, Windows `MoveFileExW`의

  bytes의 collision·symlink·non-file·write/flush/publish 실패는 기존 target을 덮어쓰지 않고
  temp를 정리한 뒤 fixed error를 반환한다. 이 command는 note 원문이나 SQLite index를 직접
  수정하지 않는다.
- native 응답은 root-relative asset path, 현재 note directory에서 계산한 POSIX relative
  Markdown node, `reused`만 포함한다. nested note는 `../assets/...`를 사용하며 preview loader는
  parent segment를 normalize한 뒤 canonical root 내부에서만 읽는다. frontend는 native 응답
  path/Markdown shape를 재검증하고, 요청 시점의 note identity·editor document·selection을

  stale response, unmount, changed document, callback failure는 document insertion 없이 종료한다.
- secret, raw credential, original filename, absolute path, clipboard bytes와 OS/raw storage
  error를 log/history/snapshot/telemetry로 보내지 않는다. OCR, image transformation, external
  hosting/cloud sync, clipboard history, multiple-file partial insertion은 명시적 비범위다.
- 관련 fixture는 supported magic/dimension·malformed/size, unsafe/nested path, same-content

  fail-closed한다. 후보는 사용자가 미리 만든 canonical 빈 directory여야 하며 직접 항목은 4,096개,
  locator는 16 KiB, app-owned manifest는 1 MiB/256 rows, path는 4,096 bytes 이내다.
- active locator가 없을 때만 v0.4.x default root를 read-only fallback으로 사용한다. locator가
  존재하면 corrupt/unsafe locator, manifest, path를 legacy root로 우회하지 않는다. active manifest
  record 또는 `apps`·partial·기타 root artifact가 있으면 `existing-install` 상태를 반환하고
  기존 설치를 이동·병합·삭제하지 않는다. catalog revision은 locator provenance로만 기록하고
  catalog 상승만으로 기존 root를 무효화하지 않는다.
- locator가 없는 경우에도 versioned locator 경로의 이미 존재하는 parent component가
  symlink/reparse이면 legacy fallback을 사용하지 않는다. portable manifest executable은 raw path의
  모든 component와 canonical exact layout을 검증해 root 안으로 resolve되는 link 기반 우회를 거부한다.
- 사용자의 명시적 확인 뒤 `apply_install_root({path, expectedRegistryRevision})`가 동일한
  canonical/free-space/manifest/artifact 검사를 다시 수행하고 revision CAS·overflow를 확인한다.
  성공 시 후보에 `apps/`를 component별로 만들고 빈 app-owned `registry.json`은 `create_new`로
  독점 생성해 flush/sync한다. 그 사이 생긴 기존 파일은 대체하지 않으며, 완성된 후보를 가리키는
  locator registry를 publish하기 직전 direct entries·empty apps·manifest bytes를 다시 확인하고
  atomic replace한다. locator commit이 실패하면 이번 호출이 만든 빈
  항목만 rollback하고 기존 root, registry, binary, partial, user data는 건드리지 않는다.
- 적용 이후 install/current/rollback/launch/install-path는 locator의 active root를 사용한다.
  portable 설치 directory와 installer cache는 `create_dir_all`로 symlink/reparse를 따라가지 않고
  각 component를 생성·확인하며, download target과 `.partial` sibling도 regular-file slot인지
  확인한다. public DTO와 UI 오류는 raw path, credential, locator/manifest, OS error를 반사하지 않는다.
- download target과 `.partial`은 regular-file slot을 다시 검사하고 `.partial`을 `create_new`로
  열어 기존 중단 파일을 truncate하지 않는다. startup metadata sync는 present corrupt locator를
  default locator로 덮어써 복구하지 않으며, missing-only fallback과 root/manifest identity 규칙을
  Manager와 `crates/launch`가 공유한다.
- **#309 safe removal (후속 PR)** — app binary와 user data 제거를 분리하고 기본값은 user data
  보존한다. remove target은 catalog와 active install manifest에 동시에 기록된 app-owned path만
  허용한다. custom root removal, 기존 root migration/병합, root reset과 실패 후 사용자 복구 UI는
  #309가 별도 소유하며 #308에서 구현하거나 우회하지 않는다.

- follow, pause, wrap, text/regex, source/level/time/field filter, highlight, bookmark, selected
  export를 제공한다.
- 100,000 line 또는 64MiB ring buffer와 backpressure를 적용한다.
- saved view에는 source 설정과 filter만 저장하고 raw log를 복제하지 않는다.

**안전 경계**

- read-only이며 log line을 command로 실행하지 않는다.
- network ingest, ELK 대체, distributed trace, arbitrary WSL command, permanent full-text archive는
  제외한다.
- `journalctl`/container log는 미리 정의된 adapter argv만 사용한다.

**#321 bootstrap 구현 상태 (2026-08-28)**

- `apps/log-lens`는 0.1.0 native/browser parity bootstrap으로 등록됐다. local file/directory,
  fixed WSL file/journal, Docker/Podman container adapter의 argv를 검증하고 실행한다. Run
  Manager source는 `run-manager:<opaque-run-id>:<stdout|stderr>`만 검증하는 receiver boundary로
  시작했으며 #366/#463에서 producer claim/ack를, #472에서 fixed app-owned rotation reader를
  완성한다.
- app-local core가 plain/JSONL/logfmt와 best-effort timestamp/level을 bounded UTF-8 parser로
  처리하고, timestamp/source/sequence tie-break를 고정해 merge한다. 100,000 line·64MiB ring,
  16KiB line·8MiB explicit export cap, fixed error, no raw source path persistence를 적용한다.
- file identity/size cursor로 append·rotation·truncate를 구분하고, fixed adapter output은
  10초 deadline·64MiB cap·cancel token으로 종료한다. operation ID/generation single-flight와
  unmount guard가 stale result를 폐기하며, saved view는 source 설정과 filter만 memory에 둔다.
- focused Rust/frontend gate와 diff/static 검토 후 Windows W3 packaged smoke에서 WSL/Docker/
  Podman 설치·부재, packaged download/copy, IME/focus와 file identity parity를 확인해야 한다.
  Log parser는 두 번째 소비자가 생길 때만 `crates/logs`로 추출한다.

#### 공통 monitor/DPI 회귀 행렬

모든 대상 앱은 앱별 geometry 구현을 추가하지 않고 아래 pure contract/adapter 행렬을
공유한다.

1. 같은 monitor·scale에서 bounds와 maximized/normal 상태를 round-trip한다.
2. 같은 monitor의 DPI 변경에서 저장 work area 기준으로 physical-pixel position/size를
   변환한다.
3. 저장 monitor가 제거되면 primary, 없으면 첫 유효 monitor로 fallback한다.
4. 해상도 축소나 virtual-desktop origin 변경 시 current work area로 변환한 뒤 titlebar의
   최소 가시 영역을 남기도록 clamp한다.
5. maximized 중 monitor/DPI가 바뀌어도 native maximized rectangle이 마지막 normal bounds를
   덮어쓰지 않도록 normal geometry를 새 monitor/scale로 변환한다.
6. monitor enumeration이 실패하면 확인되지 않은 position을 native API에 적용하지 않고,
   잘못된 monitor snapshot만 제외한 안전한 default를 사용한다.

순수 fixture는 future schema, oversized/corrupt JSON, resolution shrink, first-valid-monitor
fallback을 재현하고, Windows W4 packaged smoke는 move → DPI/resolution → maximize → restart
→ close/tray/재실행과 Launcher transient negative case를 기록한다. 같은 행렬에 Log Lens
`main`을 포함하고, 향후 source picker/export/preview가 별도 Tauri window로 추가되더라도
state 파일을 만들지 않는지 확인한다.

### P3-04. Port Manager 보강

**PR boundary and acceptance:** #337 auto-refresh/pause, #338 endpoint diff, and #339
favorite/provenance are one grouped Port Manager PR because they share one snapshot state
model, native source adapters, fixtures, and screen-level rollback behavior. #313 workspace
preflight is not part of this slice despite any future grouped delivery discussion; its
mutation/security boundary remains separate. The Port Manager 0.2.2 version is not bumped
until the v0.5.0 release gate.

- **#337 refresh/pause.** The UI accepts only a 1–60 second interval and stores it in the
  app-owned preferences document. A manual pause stops future timer polls; an in-flight poll
  remains one promise and is never duplicated by timer/manual navigation. Request generation,
  mounted guards, and one stable snapshot commit protect rapid navigation. Native `list_ports`
  retains its shared 15-second child deadline, 2 MiB output cap, fixed adapters, and a Windows
  kill-on-close Job Object that terminates root and descendant helpers together. A successful
  listener kill waits out any pre-kill poll and then requires one fresh snapshot.
- **#338 endpoint diff.** The first successful snapshot establishes a baseline without a
  synthetic initial "new" flood. Later successful snapshots match a strong Windows FILETIME,
  WSL distro/PID/start-tick, or container engine/distro/ID identity. Exact identity+endpoint
  matches are reserved across the complete snapshot before an identity-only move fallback,
  then endpoint, state, process, and provenance fields are compared. An endpoint move is `changed`;
  an identity-less row uses its own endpoint fallback and is never paired with another process.
  Poll errors retain the baseline and clear only the now-untrusted diff presentation.
- **#339 favorites/provenance.** Port endpoint and process identity favorites are independent
  bounded lists; pinned is their union. The strict DTO has no command-line, executable-path,
  credential, or arbitrary path field. JSON is limited to 64 KiB and 256 entries per kind,
  rejects unknown fields, invalid endpoint/source combinations, duplicate entries, and unsafe
  endpoint text, then uses `crates/filesystem::atomic_write`. Windows, WSL+distro, and
  container+engine/distro/ID provenance is rendered in both row and detail panel.
- **Safety and verification.** Poll failure preserves the last stable rows and favorite state
  but fail-closes listener kill/handoff controls. Any allowed action still enters the #285
  endpoint+identity revalidation path; arbitrary PID kill and established-connection
  termination remain excluded. Fixtures cover pause/single-flight, poll failure, initial and
  subsequent lifecycle (new/closed/changed), atomic/strict preference rejection, provenance,
  Windows/WSL/container source shapes, a11y/focus/Unicode navigation, and stale selection.
  The packaged Windows W3 smoke remains a release gate for real netstat, WSL, and Docker
  provenance and permission failures.

  표시된 민감 key/token-shaped value를 위조 문서로 보고 거부하며, 가져온 secret은 빈
  placeholder와 `미설정` 상태로 local storage에 기록해 사용자가 다시 입력하도록 한다.

  32 KiB의 absolute local-drive directory만 직접 순회한다. 고정 executable 이름과 표준 설치
  layout을 regular file로 확인하고 모든 부모의 symlink/reparse point를 거부하며, lookup 직전
  동일 검사를 다시 수행해 lookup→spawn 사이의 PATH redirect를 줄인다. OS가 소유한
  `%LOCALAPPDATA%\\Microsoft\\WindowsApps`의 `wt.exe`·`winget.exe` alias만 고정 이름으로
  예외 허용하고 다른 reparse executable은 거부한다. 감지는 최대 고정
  catalog 크기만큼의 read-only metadata probe로 제한하며 경로·계정·OS 오류를 DTO에 넣지 않는다.
- Related Tools의 감지·설치·실행은 하나의 native single-flight lock을 공유한다. WinGet은
  환경변수 문자열이 아닌 Windows Known Folder/System Directory API로 확인한 OS 소유
  WindowsApps alias/System32 또는 동일 root 하위의 bounded PATH 후보만
  사용한다. `CreateProcessW`로 suspended 생성하고 Windows Job Object에 직접 할당한 뒤에만 resume하며,
  `KILL_ON_JOB_CLOSE`를 설정해 120초 timeout, process 오류, Manager 종료 시 root와 helper/installer
  tree를 함께 종료한다. Job Object handle의 signaled 상태를 zero-process 의미로 오인하지 않고
  accounting의 `ActiveProcesses`를 bounded polling해 0인 경우에만 성공을 발행한다. tree가 남아 있으면
  bounded reap 뒤 고정 실패/timeout을 반환한다. 생성·Job Object 할당·resume 중 하나라도 실패하면
  감시되지 않는 설치를 허용하지 않는다.
- frontend API는 native DTO가 정확히 고정 catalog metadata·허용 detection 상태·platform 지원 여부와
  일치하는 installed 상태인지 먼저 검증하며, action 결과의 tool id/status도 확인한다. non-Windows에서는
  WinGet control만 비활성화하고 공식·라이선스 링크는 네트워크가 있으면 계속 제공한다. process/OS 오류·경로·credential
  또는 임의 message는 렌더링하지 않고 고정된 사용자 메시지로 치환한다. install/launch의 늦은
  응답은 mount/action generation과 일치할 때만 상태를 갱신하고, Related Tools 영역은 명시적
  확인·busy/aria-busy·keyboard native button·live status/alert를 제공한다. 공식 URL은 2 KiB 이하로
  제한하고 동일한 HTTPS/공식 host 검사를 API와 render 경계에서 반복한다.

## 7. PR 지도와 의존 순서

### 7.1 작업 파동

```text
Wave 0  docs/native-first + dependency policy
   └─► Wave 1  API secret fix (v0.4.2 hotfix)
   └─► Wave 2  crates/catalog + catalog v2 + revision/install-root locator + runtime catalog
                 ├─► inbound receivers
                 ├─► context-menu installed targets
                 └─► applink v2 + handoff
                       ├─► Webhook/API + Life Log/Knowledge handoff
                       ├─► Devbox Launcher bootstrap
                       └─► Log Lens bootstrap
Wave 3  snapshot cleanup ─► Workbench/Launcher/Log Lens integration
Wave 4  WSL terminal UX/profile
Wave 5  remaining P1 app features
Wave 6  P2 app features (prerequisite 충족 후 앱 간 순서 자유)
Wave 7  P3 existing-app enhancements
Wave 8  Log Lens + Devbox Launcher
Wave 9  version bumps + Windows RC + v0.5.0
```

handoff integration의 release 순서는 위 wave 안에서도 고정한다.

```text
P2  handoff core + atomic claim/ack/restore
 ├─► P2 Webhook Lab → API Playground
 └─► P2 Life Log → Knowledge
P3  Devbox Launcher/Log Lens bootstrap + catalog/snapshot consumers
 ├─► P3 Developer Toolbox → API Playground
 └─► P3 Run Manager/WSL Desktop → Log Lens producers
```

Toolbox·Run·WSL의 기존 native 기능은 각 P2/P1 범위를 유지하고, 위 표는 앱 간 연결 PR의
순서만 나타낸다.

### 7.2 PR 분리 규칙

- 기준은 이슈 번호가 아니라 사용자에게 하나로 보이는 기능 경계다. 같은 앱·사용자 흐름에서
  구현 기반, 상태 모델, migration/reindex, 보안·자원 제한과 fixture를 공유하는 형식별
  변형은 여러 이슈를 한 PR로 묶을 수 있다. PR 본문은 포함 이슈별 acceptance와 검증을
  구분하고 각각 `Closes` 처리한다.
- 독립 rollback·배포가 필요하거나 권한/비밀/외부 mutation 등 위험 경계가 다른 기능,
  선행 관계가 있는 기능, 한 번에 리뷰하기 과도한 기능은 계속 별도 PR로 유지한다.
  GraphQL/SSE/WebSocket은 독립 transport라 분리하고, XLS/XLSX/ODS는 하나의 spreadsheet
  extractor PR로 묶되 DOCX는 별도 container/parser 경계로 유지한다.
- 공용 package/crate 도입과 무관한 앱별 기능은 한 mega-PR로 묶지 않는다. 다만 #323–#336처럼
  이미 선행 PR(#322)에서 확정된 공용 계약을 모든 대상 앱에 같은 방식으로 적용하고 동일한
  rollback·회귀 행렬을 공유하는 cross-app 기능은 하나의 PR로 처리한다.
- DB migration은 그것을 요구하는 기능 PR 안에 포함하고 upgrade fixture를 함께 둔다.
- 앱 version은 해당 앱의 v0.5.0 마지막 기능 PR 또는 release preparation PR에서 세 원본을
  함께 올린다.
- 모든 branch는 `docs/<scope>`, `fix/<app>/<scope>`, `feat/<app>/<scope>`, 공용 기능은
  `feat/workspace/<scope>` 또는 `feat/crates/<scope>`를 사용한다.

대표 branch:

```text
docs/v0.5.0-native-first-plan
fix/api-playground/secret-history
feat/crates/catalog
feat/workspace/catalog-capabilities
feat/crates/applink-handoff
feat/packages/context-menu
feat/wsl-desktop/workspace-profiles
feat/api-playground/sse
feat/everything-plus/pdf-content-index
feat/devbox-launcher/core
feat/log-lens/local-tail
```

### 7.3 v0.5.0 issue·milestone 원장

코드 PR을 만들기 전에 GitHub `v0.5.0` milestone과 저장소 내 issue/PR 원장을 만든다. 현재
열린 v0.4.1 Windows acceptance [issue #176](https://github.com/jihoon22-lee/devbox/issues/176)은
post-release 추적 항목으로 유지하고 v0.5.0 feature issue에 섞지 않는다.

원장에는 기능별로 다음 필드를 한 행씩 기록한다.

| 필드 | 규칙 |
|---|---|
| issue/PR | 사용자 기능 경계별 PR 번호와 포함 issue N개를 기록하고, issue별 acceptance를 구분 |
| priority/area | `P1`·`P2`·`P3`, 앱·crate·package·integration 라벨을 함께 부여 |
| prerequisite | catalogRevision/install-root locator, snapshot schema, handoff claim 등 선행 issue 번호 |
| acceptance | 관련 설계 §, 자동 테스트, Windows smoke checkpoint와 expected evidence |
| state | `planned → in-progress → code-review → CI → merged → Windows-verified` 순서 |
| release | 앱 목표 version, v0.4.2 hotfix 선행 여부, v0.5.0 포함 여부 |

P1·P2·선택 P3의 모든 행은 milestone에 들어가야 하며, dependency gate·catalog/install
locator·handoff core·신규 앱 bootstrap도 각각 독립 행으로 만든다. 상태를 수동으로 “완료”로
바꾸지 않고 PR 링크, CI run, smoke evidence를 남긴다. 기능을 P3에서 빼거나 release를
미루려면 원장에 이유·영향·새 milestone을 기록하는 별도 범위 변경 issue를 먼저 merge한다.

### 8.2 PR 완료 정의

모든 code PR은 영향 범위와 무관하게 저장소 규약의 다음 검증을 통과한다.

### 8.3 Windows RC 수동 검증

Windows 수동 검증은 최종 RC 한 번에 몰지 않고 다음 checkpoint마다 packaged build와
evidence를 남긴다. 각 checkpoint의 blocking failure는 다음 단계로 넘기지 않는다.

| checkpoint | 시점/대상 | 최소 smoke | evidence |
|---|---|---|---|
| W0 | v0.4.1 baseline, 첫 code PR 전 | issue #176의 남은 packaged/runtime 항목과 13개 앱 cold start | Windows build ID, 환경, 결과/미실행 사유 |
| H1 | v0.4.2 release 전 | backend-only secret resolve, raw History fail-closed 삭제, Collection 안전 변환, curl·응답·오류 redaction | sanitized localStorage fixture, API 0.3.2 packaged 실행, 평문 부재 evidence |
| W1 | 나머지 P1 merge 후 | catalogRevision/runtime fallback, install-root locator, single-instance/context menu, WSL clipboard/profile 기본 경로 | locator/catalog revision, 화면·로그 evidence |
| W2 | P2 core 후 | handoff claim/ack/restore와 Webhook→API·Life Log→Knowledge, API stream/document 경계, custom root install/remove | producer/consumer IDs, concurrent/crash retry 결과, packaged logs |
| W3 | P3 bootstrap 후 | Launcher source별 stale/corrupt 격리, Log Lens local source, catalog action, Toolbox→API 및 Run/WSL→Log Lens 연결 | source schema/revision, focus/handoff, failure recovery evidence |
| W4 | v0.5.0 RC | 15개 앱 전체 cold start, second-instance focus, installer/upgrade/rollback, multi-monitor/DPI/IME/긴 path | signed checklist와 release candidate artifact |

- 외부 전문 도구와 WinGet이 없는 Windows VM, network 차단 상태에서 모든 P1·P2 core flow.
- WSL/Git/container engine은 각각 “설치됨/없음” 환경을 분리한다.
- v0.4.1 packaged-runtime acceptance issue #176 시나리오 재실행.
- 15개 앱 cold start, second-instance focus, applink/handoff, window restore.
- 한글/공백/긴 path, IME, clipboard 권한 거부, multi-monitor/DPI 변화.
- v0.4.1 data upgrade: API History localStorage fail-closed migration, Collection sanitized
  replacement, Everything reindex, user data 보존.
- external tool catalog가 offline에서 반복 오류나 core 기능 비활성화를 만들지 않는지 확인.

### 8.4 release gate

1. P1, P2, 선택 P3의 모든 issue/PR이 merge됐다.
2. 목표 version이 Cargo.toml·tauri.conf.json·package.json에서 일치한다.
3. catalog, workspace, release matrix가 15개 앱에 대해 일치한다.
4. license notices와 dependency review가 최신이다.
5. GitHub Actions와 Windows RC acceptance가 통과했다.
6. 전용 worktree와 local/remote feature branch가 규약대로 정리됐다.
7. 그 뒤에만 `v0.5.0` tag와 release artifact를 게시한다.

## 9. 명시적 가정과 변경 통제

- v0.4.1은 안정판 기준선이며 v0.5.0 개발은 현재 13개 앱 동작을 회귀시키지 않는다.

- Data Inspector는 v0.5.0에서 별도 앱이 아니다.
- Devbox Launcher와 Log Lens는 책임과 수명주기가 기존 앱과 달라 별도 앱으로 만든다.
- P1·P2 core 기능을 external tool install/launch로 대체하지 않는다.
- 계획에 없는 runtime dependency, sidecar, telemetry, cloud service는 별도 설계 승인 없이
  추가하지 않는다.
- 일정 압박이 생겨도 선택 P3를 조용히 탈락시키지 않는다. release scope 변경 문서에서
  이유·영향·새 목표 release를 확정한다.
- 이 문서와 하위 설계가 충돌하면 이 문서의 product scope와 native-first 원칙이 우선하고,
  세부 protocol/알고리즘은 해당 하위 설계를 개정해 일치시킨다.
