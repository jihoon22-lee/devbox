## 목적과 최상위 결정

v0.8.0은 기존 15개 독립 앱을 **Devbox Workspace / Devbox API Studio / Devbox Knowledge / Devbox Control Center** 네 제품으로 완전히 전환하는 단일 공개 릴리스다. 사용자에게는 한 번에 전환하되 구현·검증은 통합 작업 묶음으로 진행한다.

이 이슈는 전체 방향·의존성·PR 묶음·릴리스 판단의 원장이다. **요구사항 명세 #542**는 수용 기준의 원장이고, **WP01~WP09 #543~#551**은 실행 계획이다. **이슈 수와 PR 수는 독립적이며, 계획서·명세서를 올렸다는 이유로 문서 전용 PR을 추가하지 않는다.**

마일스톤: [v0.8.0 — 4-product consolidation](https://github.com/jihoon22-lee/devbox/milestone/3)

검토 기준: 2026-09-05, main [`e5147fa3dbc501ea4cecfc2c277ff90976b2e100`](https://github.com/jihoon22-lee/devbox/commit/e5147fa3dbc501ea4cecfc2c277ff90976b2e100). 구현 시작 시 이후 변경을 확인하고 baseline을 갱신한다. 문서 검토는 코드 실행·실기 PASS를 뜻하지 않는다. 현재는 계획 등록 단계이며 구현 PR·테스트 실행·릴리스는 미실행이다.

## 1. 변경하지 않는 제품 목표

| 제품 | 흡수 대상 / 책임 |
|---|---|
| Workspace | Workbench, Repo Manager, Code Pad, Run Manager, Port Manager, Log Lens, WSL Desktop. Project/worktree → edit → run → port/log/problem → commit/session 종료 |
| API Studio | API Playground, Webhook Lab, Developer Toolbox. request/protocol/webhook/mock/transform/history |
| Knowledge | Knowledge, Life Log. Notes/Daily/Activity/Search, 프로젝트 기록과 선택적 요약 |
| Control Center | Devbox Manager. 제품·component 설치/업데이트/이전/복구/환경/전역 설정 |
| 공통 내부 기능 | Launcher는 전역 overlay, Everything+는 검색 엔진과 전체 검색 surface. 둘 다 독립 제품으로 배포하지 않음 |

독립 설치/다운로드/시작 메뉴/제품 카드에 기존 앱을 남기지 않는다. Terminal/Editor/Logs의 보조 창은 허용하되 소유 제품의 surface로 취급한다. 제품 수를 줄인다는 이유로 system-wide ports, standalone file editor/search/log, scheduled jobs 등 프로젝트 밖 기능을 삭제하지 않는다.

화면·제품 경계와 실행 수명주기·데이터 소유·권한 경계를 구분한다. Runtime, Terminal, Search, Activity, LSP, Webhook, Process Action, Launcher는 **논리적 책임**이며 실제 프로세스/패키지 수를 8개로 강제하지 않는다. 항상 켜진 daemon을 늘리는 대신 권한·수명주기·장애 격리가 필요한 곳만 별도 실행한다. Runtime의 secret/owned process 관리와 외부 process 종료 책임은 합치지 않는다.

## 2. 마지막 검토에서 보완한 사항

1. **Migration을 WP08까지 미루지 않는다.** WP01에서 일관된 snapshot/journal 계약을 만들고, WP02~06이 자기 데이터 importer와 회귀 fixture를 포함한다. WP07도 Launcher preference mapping을 포함한다. WP08은 이미 검증한 importer들을 전체 설치·복구 흐름으로 조립한다.
2. **identifier 유지와 원본 보존의 충돌을 제거한다.** 기존 anchor identifier 재사용은 후보일 뿐이다. 같은 data root를 사용하더라도 v0.8 전용 namespace/store를 사용해야 하며 legacy DB에 in-place schema upgrade를 해서는 안 된다. installer identity·single-instance·DPAPI 검증 뒤 확정한다.
3. **SQLite `.db` 단독 복사를 금지한다.** WAL/SHM·writer 동시성·cross-store 기준점을 고려한 consistent backup을 사용한다. 살아 있는 DB의 파일 digest를 그대로 불변 기준으로 삼지 않는다. 기록할 digest는 획득 완료된 backup artifact 기준이다. 현행 Data Inspector의 immutable checkpoint reader는 migration backup 대체물이 아니다.
4. **'원자적 업데이트'의 의미를 명확히 한다.** 여러 exe·registry·DB·외부 vault 전체가 OS transaction인 것처럼 취급하지 않는다. stage → validate → quiesce → activation → health-check → commit/recover 상태기계, journal, 이전 generation 유지와 write barrier로 실패 복구를 보장한다. rollback이 v0.8에서 새로 작성한 데이터까지 v0.7로 역변환한다는 뜻은 아니다.
5. **9개 PR은 검토 예산이지 기능당 규칙이 아니다.** frontend/backend/tests/docs/importer를 같은 묶음에서 검토하고, 기계적 이동과 의미 변경은 commit으로 구분한다. API별·앱별·crate별 PR 분할을 기본으로 하지 않는다.
6. **공용 플랫폼 과설계를 제한한다.** 필요한 v1 계약과 실제 소비자만 만든다. Feature Manifest는 제품 카탈로그의 feature section에 둘 수 있으며 별도 registry/crate/daemon을 항목마다 만들지 않는다. 기존 `SecretReference`, AppLink, 공용 crate를 재사용한다. route 개발 모드·scaffolder는 최소 템플릿과 validator 수준으로 시작한다.
7. **UI의 버튼 숨김은 보안 경계가 아니다.** Tauri command/capability, backend authorization, IPC peer/session identity, replay/size/timeout 검증을 함께 적용한다. 같은 Windows 사용자 프로세스 분리만으로 완전한 OS sandbox가 된다고 주장하지 않는다.
8. **terminal의 무리한 UI 이식은 피한다.** v0.8에는 Workspace route·프로젝트 공유·보조 창·Quick Summon 통합이 필수다. 실행 중 PTY를 renderer 간 옮기는 임의 docking framework까지 필수화하지 않는다.
9. **index DB 전체를 캐시로 버리지 않는다.** Knowledge 사용자 templates와 Everything+ roots/exclusions/saved queries는 보존해야 한다. table/파일 단위로 원본·파생·일시 데이터를 분류한다. WebView localStorage 설정도 별도 이전 대상으로 조사한다.
10. **기존의 작은 기능과 엄격한 정책을 보존한다.** Windows LSP 명시적 설치/cache, WSL resource·container 관리, terminal 입력·복원, Manager package-only setup을 누락하지 않는다. HMAC 등 비영속·공유금지 도구를 generic artifact로 우회하지 않는다. 세부 경계는 #544~#550에 기록했다.

## 3. v0.8 필수 보강과 범위 제한

필수: Project Registry, worktree-aware context, `.devbox/project.json` + local overlay, Development Session, Unified Problems/runtime topology, WSL-native LSP v1, global Command/Shortcut Registry, federated search, source-owned ArtifactRef/SecretRef, Operations/Review 공통 UX, 선택한 session summary → Knowledge, suite migration/recovery.

- project manifest의 task/toolchain/hook는 가져왔다고 실행하지 않는다. root/worktree와 manifest revision에 대한 신뢰·실행 미리보기를 요구한다.
- 새 WSL LSP는 선택 distro의 검증된 설치 executable을 사용한다. WSL 자동 패키지 설치나 범용 remote development를 만들지 않는다. 기존 Windows LSP의 명시적 설치·검증 cache 기능은 보존한다.
- 검색은 기존 인덱스를 연합한다. 하나의 거대 SQLite·embedding index로 합치지 않는다.
- API/로그/노트 원문과 secret은 전역 registry·경로·recent history로 전파하지 않는다.
- timeout, bounded payload/queue, 취소 가능 여부, stale/partial 결과, provenance를 공통 상태로 다룬다.
- Launcher와 필수 shell은 작게 유지하고 editor/xterm/protocol/diagram/graph는 필요 시 로딩한다.

비범위: 외부 plugin marketplace, OCR/semantic search, cloud sync, AI 자동 분석, SSH/Dev Container 전체 관리, GitHub PR/Actions 제품 통합, 자동 dependency upgrade, secret portable export, Launcher의 임의 shell 실행.

### PR 운영 규칙

- 위 9개를 기본 budget으로 한다. 요구사항/세부 이슈가 늘어도 PR은 자동으로 늘지 않는다. 실제 검토가 더 쉬워지면 인접 묶음을 합쳐도 된다. 표는 초기 권장 매핑이며 이슈 하나당 PR 하나를 강제하는 규칙이 아니다.
- 더 쪼개야 할 때는 이슈 댓글에 **독립적 데이터 손실/보안/복구 위험 또는 리뷰를 불가능하게 하는 구조적 이유**와 변경된 매핑을 기록한다. '기능 하나니까', '파일이 많으니까', '테스트/문서니까'만으로 분할하지 않는다.
- 반대로 PR 수를 맞추려고 서로 무관한 고위험 migration/process/installer 변경을 무조건 한 번에 합치지도 않는다.
- draft PR 하나 안에서 이동/핵심 계약/제품 연결/importer/tests/docs를 여러 commit으로 개발한다. 일반 보정은 열린 PR에서 흡수하고 준비 전 반복적인 전체 리뷰 요청을 피한다.
- review packet: semantic 변경 요약, pure moves 목록, 데이터·authority 변경표, 요구사항 ID/legacy parity 매핑, CI/실기 증거, 알려진 제한과 rollback. 생성물은 별도 commit으로 분리한다.
- CI는 affected graph를 활용하되 root/lockfile/미분류/검증기 변경은 full로 닫는다. full suite package acceptance를 모든 작은 commit에서 반복하지 않고 각 위험 gate와 최종 candidate에 집중한다.
- 여러 이슈를 닫는 PR, 여러 PR에 걸쳐 유지되는 이슈 모두 허용한다. 이 메인 이슈와 요구사항 명세 #542는 구현 PR의 `Closes` 대상으로 삼지 않는다. 전체 수용 검증 때 닫는다.
- 과거 '기능 하나당 PR' 규칙과 충돌하는 부분은 **v0.8에 한정해 본 통합 묶음 정책을 우선**하며 B01에서 CONVENTIONS/AGENTS에 명시한다. 기존 안전/CI 규칙은 완화하지 않는다.
- 계획 이슈 11개가 구현 PR 11개를 의미하지 않는다. 메인/명세의 문서 반영은 B01과 해당 작업 PR에 포함하며 결과 기록만을 위한 PR을 기본 계획에 더하지 않는다.

B02/B03/B04는 B01 계약 확정 뒤 병렬 개발할 수 있다. 공용 파일의 writer는 한 묶음으로 제한하고 긴 stacked branch를 기본 전략으로 삼지 않는다. B08의 설치/identifier/backup 위험조사는 B01에서 수행하며, 후보 package는 B02부터 hidden test topology로 검증한다. 최종 조립이 B08이라는 이유로 Windows 검증을 그때 처음 시작하지 않는다.

## 6. 배포·호환성·버전 결정

- v0.7 stable은 유지한다. 개발 중 legacy shell을 비교용으로 유지할 수 있으나 같은 파일에 구·신 writer를 동시에 붙이지 않는다. 공용 로직을 양쪽이 참조하고 복사본 두 개를 계속 고치지 않는다.
- final v0.8에는 네 제품만 공개한다. 구 앱 binary를 `Legacy` 옵션으로 다시 배포하지 않는다. compatibility는 구 데이터 reader·유효한 route alias·test fixture로 한정한다. 삭제된 exe를 직접 호출하는 외부 사용자 script의 자동 redirect는 보장하지 않는다.
- suite 0.8.0 lockstep을 기준으로 하되 component API/schema version은 별도로 명시한다. portable와 installer가 같은 shared component/data에 무작정 합류하지 않게 install/session namespace와 handshake를 검증한다.
- 권장 배포: Suite installer 1 + 제품별 portable ZIP 4 + release manifest + notices, **7개를 목표**로 한다. 이는 Tauri가 자동 지원한다고 확인된 사실이 아니라 구현 설계다. 실제 required signature/metadata 등이 있으면 B08에서 asset 계약을 명시적으로 수정하고 B09는 확정 manifest로 검증한다. 사용자-visible 제품 수 4는 변하지 않는다.
- Suite 설치 항목 하나는 목표이며 기존 anchor 설치와 제거 충돌을 B01/B08에서 검증한다. 구현 제약이 확인되면 숨겨진 제품 구성요소 수준의 설치 구조 대안을 기록하되 legacy 사용자 앱을 노출하지 않는다.
- exact-main private candidate → runtime/installer/migration acceptance → 같은 source의 stable 승격 → fresh-download 검증. 명시 요청 없는 public RC는 만들지 않는다.

## 7. 최종 gate

G0 기반: 현행 15-app parity inventory·권한/데이터/설치 위험·새 test topology 검증.

G1 제품: 각 product 기능 parity, importer, Windows/WSL smoke, lazy loading, 실패/취소/복구 검증.

G2 suite: task→port→log→problem→file, webhook→request→transform→note, Activity→Daily, global search/shortcut/고립 실행, cold/hot launch 검증.

G3 전환: v0.7 전체/부분/installer+portable, WAL, 손상/누락/낮은 디스크/잠금/중단·재개, secret, conflict, stopped/missing distro, rollback 및 신규 사용자 데이터 보존.

G4 공개: old binary dependency 0, legacy public product 0, 모든 필수 요구사항 PASS, exact-main 후보와 공개 asset name/size/digest 일치. 성능 기준은 B01 baseline과 예산을 정하고 B09에서 결과를 보고한다. 측정 없이 PASS 또는 '더 빠름'을 선언하지 않는다.

세부 수용 기준은 #542의 **R01~R26**, end-to-end 검증은 **S01~S08**을 사용한다. 각 WP의 체크는 계획 등록 상태에서는 모두 미완료다.

## 실행 계획

### 1. 소유권·store 분리

### 2. Notes/Daily parity

### 3. Activity와 날짜 context

calendar/timeline/day/week/month/app usage/Git counts/export/source diagnostics를 Activity route에 옮긴다. date 선택과 Daily note를 같은 context로 연결하되 note가 없다고 자동 생성하지 않는다.

Project Registry와 source의 old project ID를 매핑하고 unmapped/offline 프로젝트도 표시한다. 동일 repo 여러 worktree activity가 중복 합산되지 않게 source provenance/aggregation key를 정한다. 날짜 경계는 current system-local 계약을 보존하고 timezone 변경/DST/partial-day를 설명한다.

session summary는 WP06 event/provider를 받아 결정론적인 preview로 작성한다. 실패 run 수·commit·선택 문제 요약 등 허용 metadata만 제공하며 raw command/log/window title/secret을 자동 삽입하지 않는다. WP06 전에는 fixture adapter로 계약을 검증한다. preview 승인 후 exclusive/identity-checked note 생성 또는 명시적 append를 수행한다.

### 4. Search engine와 사용자 surface

Everything+의 filename/content/regex/filter, document extractor, roots/exclusion/index status, saved search를 Search owner로 이전한다. 노트 FTS와 파일 FTS를 물리적으로 합치지 않는다.

Search source API는 source/root identity, bounds, cancellation, generation, partial/stale/unsupported 상태를 반환한다. 최신 query만 UI를 갱신한다. 결과는 opener에게 opaque ref를 전달하고 실행 직전 file identity를 재검증한다. Search service 자체에 file mutation/process 실행을 부여하지 않는다.

Knowledge의 Search에서는 Notes / Current Project / All Indexed Files를 제공하고 full filter/root/index 설정에 접근할 수 있게 한다. 파일색인 root와 note vault가 겹치면 owner/source를 표시하고 단순 이름만으로 dedupe하지 않는다. Windows native watcher/WSL polling, nested roots, deleted root ID 미재사용, sensitive exclusion, bounded extraction을 보존한다. WP07에 federated provider를 인계한다.

### 5. migration 상세

schema inventory를 table/파일 단위로 `authoritative / derived / transient`로 분류한다.

- 이전: vault binding, templates/settings, capture preferences, Life Log 활동 이력/privacy/source/project mapping, search roots/exclusions/saved queries/filter 정의.

- 미이전: live collector handle, watcher queue, in-memory query/result/operation. 중단·복원 상태는 명시적으로 표시.

legacy vault index 파일을 새 Knowledge가 바로 in-place migrate하지 않는다. old namespace와 새 owner store를 분리하고 필요한 사용자 table만 consistent snapshot에서 import한다. 같은 vault를 구·신 writer가 동시에 편집하지 않게 active owner/quiesce 정책을 적용한다. 사용자 Markdown/이미지 bytes와 상대 links는 이동하지 않는다.

### 2. Tasks & Services parity

cron schedule/활성화/편집/중복실행 정책, jobs/services/history/filter, task import/trust, DAG/sequence/parallel, health/restart/backoff/receipt를 이전한다. enable-state와 현재 execution-state를 구분한다.

각 start/retry/stop 요청은 operation/generation ID를 가진다. 중복 클릭·timeout 후 재시도·renderer reload로 같은 occurrence를 두 번 실행하지 않는다. retry_waiting stop은 backoff를 취소하고 restart는 새 generation으로 처리한다. 삭제/설정 변경 중 active run·stop-transition·unknown state gate를 보존한다.

WP06이 사용할 ownership/borrowed-reference/lease 모델을 여기서 준비한다. 세션이 이미 실행 중인 service를 참조했다는 이유로 소유권을 빼앗지 않는다. active owner가 불확실하면 자동 재연결·종료 대신 degraded/review 상태로 둔다.

### 3. Runtime 관찰과 동작

native/WSL/container listener, 상세, filters/favorites/pause/refresh diff/provenance를 이전한다. polling은 single-flight·bounded이고 실패는 last-good baseline을 지우지 않는다. identity와 source를 포함한 deterministic topology를 만든다.

`Task/Service → Operation → Run → ProcessIdentity / Endpoint / Health / LogSources`를 typed ID로 연결한다. metadata source가 stale/missing이어도 native listener와 다른 source를 실패시키지 않는다. expected/declared/verified, partial/truncated를 UI에 표시한다.

owned service stop/restart는 Runtime owner로, unowned process stop은 Process Action Broker로, container stop은 검증된 container action owner로 전달한다. 실행 직전에 endpoint/process creation identity/target/run revision을 다시 확인한다. PID 재사용·process replacement·stale selection은 거부한다. '문제 해결' 버튼이 임의 포트 owner를 자동 종료하지 않는다.

### 4. Logs와 진단 provider

plain/JSONL/logfmt, deterministic merge, follow/filter/search/bookmark/saved view/export, source reconnect를 이전한다. fixed WSL cat/journalctl 및 container logs argv만 허용하고 arbitrary command reader로 확대하지 않는다.

**현재 Run adapter의 고정 legacy Run app-data root 의존을 제거**한다. 새로운 Runtime-owned log descriptor/run identity로 회전 segment와 logical cursor를 해석한다. UI나 handoff가 임의 log path를 owner에게 지시하지 못하게 한다. rotation/truncation/deleted run/late read를 generation으로 처리한다.

saved view는 source 설정과 filter만 보존한다. WSL file descriptor와 ephemeral Webhook capture를 몰래 영속화하지 않는다. view load는 disconnected 상태이며 명시적 reconnect 전에 I/O를 시작하지 않는다. Toolbox로 보내기는 현재 source generation의 명시적 선택만 bounded/redacted Artifact로 전달한다. all-visible 자동 확장·clipboard fallback은 금지한다.

Problem matcher는 검증한 project-relative file/range와 source/run revision을 발행한다. 전체 Problems UI와 terminal/LSP/dependency 집계는 WP06이 담당한다. raw logs를 Problem/Activity snapshot에 복사하지 않는다.

### 5. 데이터 이전과 활성화 정책

WP01 harness로 job/service/task/cron/restart/trust metadata, run history와 필요한 persistent log mapping, runtime favorites/settings, Log Lens saved views를 조사·import한다. 원본 Run DB의 WAL/일관된 snapshot과 로그 retention/rotation 기준점을 함께 기록한다.

실행 중 process는 단순 PID 저장으로 새 owner에 입양하지 않는다. cutover 전 old owner quiesce와 사용자 검토가 필요하다. 기존 definition의 활성화 의도를 기록하되 migration/import 시작이 cron/service를 자동 실행하거나 구·신 scheduler가 같은 occurrence를 claim하게 하지 않는다. 새 owner의 명시적 activation 정책은 WP08과 연결한다.

secret은 actual platform Sealer/entropy 조건에 맞춰 이전하거나 reconnect required로 표시한다. 명령·cwd·env는 소유 store에만 유지하고 shared journal/지원 bundle에는 원문을 남기지 않는다. ephemeral rings/process handles는 이전하지 않는다. saved view/source/run ID mapping, orphan/missing logs, existing destination conflict, 반복 import를 검증한다.

## 구현 단계

### 1. Launcher Host와 command dispatch

기존 Launcher core의 bounded index와 검증을 Catalog v3 Product/Route/Command에 연결한다. UI는 product executable 문자열을 조합하지 않고 command ID + typed context + revision을 요청한다. backend가 current target/installed state/authority/identity를 확인한다.

cold/hot route를 단일 처리 경로로 연결하고 이미 열린 draft·active context를 무조건 덮어쓰지 않는다. 명시적 외부 deep link/custom URL을 등록할 경우 외부 입력은 비신뢰이며 자동 실행/secret access를 허용하지 않는다. custom URL scheme 자체는 필수 구현 수단이 아니다. OS protocol/argv/history에는 원문 payload 대신 opaque 식별자만 전달한다.

### 2. global shortcut와 설치 namespace

Launcher 표시, Terminal Quick Summon, Knowledge Quick Capture, 현재 프로젝트 열기를 한 registration owner가 관리한다. 중복·등록 실패·이전 조합 복구·일시적 비활성화·owner 종료를 처리한다. 활성 modal/IME composition/텍스트 편집과 terminal SIGINT를 가로채지 않는다.

suite install과 여러 portable가 동시에 있을 때 어느 owner가 활성인지 표시하고, 등록된 선택된 installation namespace에만 command를 전달한다. 다른 버전/다른 portable의 DB·PTY를 잘못 열지 않도록 handshake/lease/버전 검증을 한다. registry record가 있다는 것만으로 임의 binary를 실행하지 않는다.

Control Center가 아직 최종 구현 전이어도 제품 내 fallback으로 shortcut 진단·변경이 가능하도록 공용 설정 surface를 만든다. Control Center는 WP08에서 이 surface를 배치한다. host 시작은 명시 설정/사용자 진입점에 따르고 조용히 여러 startup entry를 추가하지 않는다.

### 3. federated search 조립

Commands / Projects / Repositories·Worktrees / Tasks·Services / Recent Runs / Indexed Files / Notes / Saved Queries source를 연결한다. source-owned store를 유지하며 all-in-one DB를 만들지 않는다. metadata-only source와 content query source를 구분한다.

query generation·debounce·cancel·deadline·per-source/result cap을 적용한다. 느리거나 unavailable한 source가 다른 결과를 막지 않는다. source/provenance/freshness/partial/truncated와 exact target identity를 표시한다. 이름이 같아도 서로 다른 project/root/product의 결과를 합치지 않는다.

파일→Editor, log→Logs, note→Knowledge, task/run→Workspace, transform→API Studio의 문맥적 action을 제공한다. 검색 결과의 경로를 그대로 실행하지 않고 owner가 현재 파일/row/revision을 재검증한다. 검색 query/본문/snippet을 background recent/history에 자동 영속화하지 않는다. 사용자가 명시적으로 저장한 검색은 기존 Saved Query 정책을 따른다.

### 4. 제품 간 Artifact workflow

API/Log/Editor의 명시적 선택→허용된 Transform, exportable 결과→Knowledge draft, session summary→Daily preview, file/problem/run navigation을 연결한다. Artifact owner, revision, size/sensitivity, generation, expiry/claim/ack/restore와 destination policy를 검증한다.

API의 저장하지 않는 protocol session, Toolbox HMAC 입력/결과, ephemeral Webhook raw header 등 **원래 공유 금지인 데이터는 공통 handoff로 우회하지 않는다**. stale selection과 source 삭제는 명확히 거부한다. 전송 실패 시 사용자 원본/draft를 보존하고 clipboard fallback 또는 같은 side effect 자동 replay는 하지 않는다.

다른 제품이 설치되지 않았으면 설치 안내 또는 명시적 지원되는 local export를 제공한다. action이 작동한 것처럼 메시지로만 성공 처리하지 않는다. 수신 preview 취소 후 손실 없는 재시도와 중복 저장 방지를 검증한다.

### 5. Operations/Review 일관성

각 owner의 operation progress/state를 공용 화면에 projection한다. start/end/failure/cancel_requested/cancelled/uncancellable phase를 구분한다. 작업이 취소 불가 단계인데 성공 취소로 표시하지 않는다. notifications는 중복을 줄이고 관련 route로 연결한다.

Review는 대상·변경 내용·위험·현재 revision을 동일한 형식으로 설명하는 surface다. command 실행권한을 자체 보유하지 않고 owner가 승인 token·identity를 다시 검증한다. 여러 위험 작업을 한 번에 무조건 승인하는 기능이나 별도 business logic 복사본을 만들지 않는다. 기존 앱별 더 엄격한 확인 조건은 보존한다.

### 6. preference migration와 전체 UX sweep

legacy Launcher favorites/recent opaque IDs, shortcut preference를 새 command/result ID로 mapping한다. deprecated/missing 항목은 이름만 유사한 다른 명령으로 매핑하지 않고 unresolved로 표시한다. 기존 capture/terminal 단축키가 겹치면 충돌 preview와 합리적인 기본값을 제안한다.

context navigation/dirty confirmation/empty-loading-error/offline, focus loss/hide/reopen, keyboard-only/한국어 IME/high contrast/DPI를 네 제품에서 검사한다. 다양한 state store를 무조건 중앙 전역 store로 합치지 않는다. router와 heavy feature chunk 분리를 확인한다.

## 목표와 검토 경계

Devbox Manager를 Control Center로 전환하고, 이미 각 제품에서 검증한 importer를 suite inventory→backup→migration→activation→recovery 흐름으로 조립한다. 네 제품과 필요한 내부 component를 일관된 버전으로 설치·업데이트한다. **설치·데이터 전환·복구가 한 상태기계를 이루므로 B08 한 묶음**으로 검토한다. 제품별 schema importer를 여기서 처음 만들지 않는다.

B01에서 identifier/namespace/DPAPI/기본 설치 proof를 마치고 B02부터 hidden product package를 검증한다. 이 PR을 마지막 순간의 설치 실험으로 사용하지 않는다.

## 현행 Manager에서 계승·변경할 부분

- release manifest 기반 다운로드, host allowlist·size/SHA-256·partial 안전성, 검증된 portable layout/root/registry, root preview, app user data 보존, doctor/diagnostics/Related Tools를 보존한다.
- 현재 batch는 앱별 독립 성공/실패다. 새 suite update는 그대로 batch 함수를 호출하는 것이 아니라 generation 단위 activation/recovery가 필요하다.
- 현재 **installer 실제 위치·uninstaller를 추측하지 않는다**. v0.7 설치 15개 정리를 위해 명시적인 verified installer inventory/migration 경로를 추가해야 한다. 임의 uninstall string 실행이나 전체 디스크 탐색 삭제는 금지한다.
- **현재 Data Inspector의 immutable checkpoint-only 읽기는 live WAL을 병합하지 않는다.** 그 코드를 migration source reader로 재사용하면 최신 데이터가 누락될 수 있다. 진단용 read-only 정책과 consistent backup 획득을 분리한다.

## 구현 순서

### 1. 설치와 데이터 inventory

B01의 결정표를 실제 Windows installer/portable discovery에 연결한다. product ID, bundle identifier, installer identity/ARP, executable identity, protocol/file association, single-instance key, app-local/WebView data root, component registration을 별도 필드로 관리한다.

기존 anchor identifier 재사용은 검증된 경우에만 적용한다. 동일 root를 쓰더라도 v0.8 새 namespace/store가 legacy DB를 in-place upgrade하지 않게 한다. 기존 portable는 Manager-owned exact registration만 migration/제거 대상으로 본다. 미등록 수동 사본은 보고서에서 안내하고 건드리지 않는다.

v0.7.0 full/partial/installer+portable 혼합, 여러 사용자/custom install root, missing/offline source를 검사한다. user source inventory는 민감한 원문을 public log/support bundle로 보내지 않는다.

### 2. consistent backup과 dry-run plan

running services/jobs/PTY/multiplexer/WebView writer 상태를 확인하고 quiesce가 필요한 항목을 preview한다. critical cutover에서 새 구버전 writer가 다시 생기면 중단하거나 일관된 snapshot을 다시 획득한다. 가능한 owner cooperative shutdown을 먼저 사용하고 arbitrary kill은 하지 않는다.

SQLite backup API 또는 검증된 동등 snapshot 방식으로 WAL 포함 consistent copy를 얻는다. 여러 store는 필요한 writer 정지/일관성 경계를 선언하고 서로 다른 시점 snapshot을 하나의 global transaction인 척하지 않는다. backup artifact별 identity/schema/size/digest/count/reference/acquisition metadata를 기록한다.

`source schema → importer → destination namespace → conflict plan`을 보여 준다. 같은 이름/다른 ID, existing v0.8 store, partial old install, unsupported/future schema, locked WebView settings, secret reconnection 상태를 구분한다. skip/keep-both/승인 merge 외 silent overwrite는 금지한다.

### 3. owner importer 실행과 재시작 가능 journal

WP02~06 importer를 versioned contract로 실행한다. sourceSnapshotId/recordId→destinationId mapping과 phase/결과를 journal에 보존해 재시도 시 duplicate를 만들지 않는다. process handle/live PTY/ephemeral ring은 이전하지 않는다.

Knowledge templates와 Everything+ saved queries처럼 index DB 안의 사용자 데이터를 반드시 이전한다. 순수 FTS/link/cache는 재생성한다. Markdown/assets와 Git repo/worktree 원본은 이동하거나 rewrite하지 않는다. localStorage/profile 설정은 실제 지원 경로로 이전하고 제한 항목을 명시한다.

DPAPI는 actual app platform adapter의 user/entropy binding을 검사한다. 필요한 경우 owner 안에서 재봉인하되 평문 file/renderer/공유 journal 경유는 없다. migrated/reconnect required/unavailable를 구분한다. 활성화된 cron/service 정의를 가져오더라도 migration 중 자동 firing을 금지하고 old scheduler와 new scheduler의 소유권 전환을 검증한다.

### 4. suite package와 component resolution

기본 제안: Suite setup 1개 + 네 제품 portable ZIP + release-manifest.json + THIRD_PARTY_NOTICES.md, 총 7개 public asset. 이것은 구현 목표이며 기존 Tauri NSIS 15개를 단순 합치면 자동 달성된다고 가정하지 않는다. 실제 installer/bootstrapper 전략과 필요 signature/metadata를 확인한 뒤 authoritative asset manifest를 확정한다. 제품 수 4와 legacy 공개 0은 바꾸지 않는다.

일반 설치는 Suite 소유 entry/shortcuts/components로 관리하고 user-facing 시작 메뉴는 네 제품만 둔다. portable는 필요한 component를 포함하고 다른 제품 미설치를 허용한다. installed+portable/multiple portable에서 installation/session namespace, versioned API, shared owner lease, verified binary resolution을 적용한다. 다른 폴더의 같은 이름 exe를 우연히 호출하지 않는다.

suite version은 lockstep이지만 component protocol/data schema version은 별도로 검증한다. 지원하지 않는 mixed version은 실행을 차단하고 복구 경로를 제공한다. Control Center 자신의 교체는 minimal verified bootstrap/update helper가 맡도록 하며 업데이트 권한을 모든 product shell에 나눠주지 않는다.

### 5. recoverable activation 상태기계

권장 단계: inventory → stage packages → verify → snapshot/import → validate → quiesce/revalidate → activate generation → health-check → commit. 각 단계에 journal과 idempotent resume/recover를 둔다. 이전 package/data generation을 보존하고 사용자 write는 activation commit 전까지 차단한다.

전체 exe·registry·DB·외부 vault가 하나의 OS transaction으로 바뀐다고 주장하지 않는다. package 교체와 data schema를 함께 되돌릴 수 있는 recovery plan을 기록한다. 실패했는데 old executable이 new schema를 여는 조합을 만들지 않는다.

health-check는 네 product 및 필요한 components의 version/route/IPC/store smoke를 확인하되 실제 사용자 task/request를 실행하지 않는다. 성공 전 legacy uninstall을 시작하지 않는다. 활성화 성공 후 알려진 legacy shortcut/registration/installer만 identity 재확인 뒤 정리한다. cleanup 실패는 '새 suite 활성화 성공 + 구 설치 정리 미완료'처럼 별도 상태로 남겨 재시도하며 전체 성공으로 숨기지 않는다.

### 6. rollback/downgrade/uninstall 계약

commit 전 실패 recovery와 commit 후 downgrade를 분리한다. v0.8에서 새로 작성한 데이터를 v0.7로 무손실 역변환한다고 약속하지 않는다. downgrade 전 backup/export/영향을 보여 주고 신규 데이터를 보존한다. 외부 vault의 사용자 편집은 package rollback으로 지우지 않는다.

uninstall 기본은 user data 보존이다. 별도 data-delete action은 exact owner inventory/preview/명시 승인으로만 제공한다. backup 자동 정리는 보존 정책·여유공간·진행 중 recovery 상태를 검사하고 마지막 복구 수단을 조용히 제거하지 않는다. 업데이트 중 재부팅/종료/잠금/낮은 디스크에 대한 recovery UX를 제공한다.

### 7. diagnostics와 지원 보고서

설치/schema/component/operation/migration 결과는 redacted metadata로 보여 준다. raw DB/log/query/command/env/credential/path를 지원 bundle에 추가하지 않는다. Data Inspector가 읽는 checkpoint freshness/known WAL limitation은 정확히 표시한다. migration 상태를 진단 모드가 임의로 repair/delete하지 않는다. explicit review한 recovery command만 실행한다.

## 목표 / 마지막 PR의 제한

기능·owner importer·suite delivery가 완성된 상태에서 legacy shell과 공개 자산을 제거하고, 네 제품 topology에 대한 전체 parity/실기/설치/복구/릴리스 gate를 확정한다. **새 대형 기능 개발이나 뒤늦은 migration 설계를 이 PR에 몰아넣지 않는다.** 소스 정리·CI/배포 전환·문서·최종 regression fix를 한 B09로 검토한다.

기본 총 PR budget은 B01~B09의 9개다. source merge 후 candidate에서 결함이 발견되면 필요한 corrective PR은 허용하지만, 단순 결과 기록·작은 문서 동기화를 위한 post-release PR을 관례적으로 만들지 않는다. 실제 추가 분리가 필요하면 #541에 이유와 변경된 mapping을 남긴다.

## 확인한 현행 배포 기반

현재 `.github/workflows`에는 `ci.yml`, `windows-package-candidate.yml`, `windows-installer-acceptance.yml`, `release.yml`이 있다. candidate는 tag/release가 아직 없는 **정확한 current main SHA**를 받아 검증하고, catalog 기반 3개 app shard를 계획한다. build scripts와 assembled artifact 검증을 그대로 활용하되 app-count 전제를 product/component 모델로 이전해야 한다.

이전 v0.7의 15-app/32-public-asset 수치는 역사적 계약이다. v0.8은 WP08에서 확정한 네 제품과 실제 asset manifest를 검증하며, 단순히 숫자만 바꾸고 검증 범위를 줄이지 않는다. public 7개는 기본 설계이고 실제 필요한 signature/metadata가 있으면 명시적 manifest 변경을 따른다.

## 실행 계획

### 1. release 전 기능 수용 감사

WP01 parity inventory를 source command/route/tests와 대조한다. 각 legacy feature의 `migrated / merged / intentionally retired`에 근거를 붙인다. unknown/unmapped/missing required test는 release blocker다. 구현된 기능을 계획 범위에서 빼려면 사용자 승인·대체 경로가 있어야 하며 '어려워서 retired'는 허용하지 않는다.

세부 검토에서 드러난 누락 위험을 별도 체크한다:

- standalone file/editor/search/system ports/logs/global jobs.
- Knowledge templates, search saved queries/roots/exclusions 등 index DB 안의 원본 사용자 데이터.
- Windows LSP 설치/cache/local archive와 새 WSL LSP의 구분.
- WSL resource/container start/stop/restart/로그 연결, terminal broadcast/IME/exact restore.
- API Header 순서/중복, protocol transient policy, Toolbox 비영속·공유금지 도구.
- 기존 Manager doctor/Data Inspector/지원 bundle/Related Tools/package-only setup.

### 2. source와 runtime dependency cutover

기능이 추출된 기존 앱 crate/frontend shell, Cargo/pnpm workspace member, old release/catalog entry, duplicated bootstrap/README 경로를 제거한다. 보존할 순수 engine/shared package/migration reader/fixture/유효한 alias를 먼저 목록화한다. 기존 폴더 전체를 무작정 삭제하거나 `legacy/apps`로 옮겨 영구 유지하지 않는다.

새 코드의 old executable name/path/old app-data fixed root 의존을 검사한다. migration reader와 historical docs의 의도된 old ID는 allowlist로 구분한다. 실행 중 제품 route가 legacy binary를 fallback으로 호출하는 경로는 0이어야 한다.

구 AppLink 의미를 새 handler가 실제로 받을 수 있으면 mapping한다. **삭제된 exe의 절대 경로를 가리키는 외부 shortcut/script가 마법처럼 redirect된다고 보장하지 않는다.** suite-owned shortcut/protocol/file association은 검증된 전환으로 갱신하고, 외부 사용자 항목은 unsupported/unresolved 안내한다. 만료된 one-time handoff는 복구 가능한 승인으로 재해석하지 않는다.

### 3. CI와 release topology 확정

catalog/schema 검증, affected graph, bundle budgets, license notices, native command capability, product/component binary 목록을 동기화한다. root/lockfile/알 수 없는 변경은 full CI로 닫는다. required checks의 이름·의미를 보존하고 branch protection을 통과하기 위해 checks를 지우거나 always-success로 바꾸지 않는다.

candidate shard planner는 제품별 크기·공유 component·중복 build 비용을 고려해 계획한다. 사용자 제품 수와 build job 수를 같게 할 필요는 없다. binaries를 각 shard마다 불필요하게 다시 빌드하거나 required component가 package에서 빠지지 않게 한다. 무관한 dependency/toolchain upgrade는 섞지 않는다.

`windows-installer-acceptance`는 네 제품과 shared components, suite generation, migration/recovery를 검사한다. fixture가 runtime 검증용인지 실제 packaged native 실행인지 분리한다. old app-count 하드코딩과 예산 파일·asset allowlist·manifest schema·support notices를 함께 이전한다.

### 4. 전체 실제 수용 테스트

#542 S01~S08을 최종 소스/패키지에서 실행한다.

| 영역 | 필수 시나리오 |
|---|---|
| 개발 흐름 | Windows/WSL project→worktree→edit/LSP→Git, session→task→port→log→Problem→file→stop |
| API/기록 | webhook→request→response diff/transform→mock→Knowledge; Activity→Daily preview |
| 전역 진입 | shortcut 충돌/owner 종료·재기동, cold/hot route, missing product, installed+multiple portable |
| WSL/terminal | distro online/offline/missing, tmux/zellij attach/reconnect, exact layout/failed pane, IME/DPI/monitor |
| 이전 | clean, v0.7 full/partial/mixed, WAL-only row, WebView settings, source conflict/future/corrupt/missing |
| 복구 | low disk/locked exe/permission/cancel/crash/reboot, 단계별 resume, failed activation, postcommit downgrade |
| 데이터 보존 | templates/saved queries/vault/assets/Git 원본, secret reconnection, user data after uninstall |
| 보안·성능 | unauthorized IPC/caller/route/replay, bounds, raw secret leak, startup/idle/resource/bundle baseline |

성능은 B01에서 고정한 조건과 예산으로 비교한다. 제품 통합 후 전체 프로세스/RSS가 늘어도 사용하지 않는 기능이 항상 기동한 결과인지 확인한다. 측정하지 않은 환경은 미실행으로 남기고 full PASS로 합산하지 않는다. 사용자 특정 PC 확인이 필요한 경우 blocker 여부와 정확한 수동 시나리오를 명시하며 필요 검증을 조용히 면제하지 않는다.

### 5. exact-main candidate와 공개 절차

B09 source merge와 required CI/full audit 완료 후 실제 current main SHA로 unpublished candidate를 만든다. artifact에는 intended tag, source SHA, catalog/schema version, product/component list, name/size/digest inventory, test evidence를 연결한다.

후보의 native runtime/installer/migration acceptance가 성공해야 stable tag/publication으로 진행한다. code/installer/schema/package-input 변경이 있으면 같은 이름의 예전 PASS를 재사용하지 않고 새 exact-main 후보를 생성한다. 단순 evidence 기록을 위해 source SHA를 바꾸는 PR은 피하고 issue/Actions artifact에 결과를 기록한다.

공개는 검증한 candidate bytes를 승격하는 방식으로 수행하고 재빌드한 다른 파일을 같은 후보라고 취급하지 않는다. public RC/prerelease는 사용자 명시 요청이 없으면 만들지 않는다. 공개 직후 fresh-download로 manifest/artifact name/size/SHA-256와 네 product topology, missing/undeclared asset, 기본 실행을 확인한다.

배포 승인과 credential 사용은 저장소의 기존 정책을 따른다. 이 계획 이슈가 테스트 gate 우회나 미검증 release를 승인하는 것은 아니다.

### 6. 문서와 이슈 완료 처리

README, AGENTS, CONVENTIONS, architecture/development/projects/roadmap, Windows 설치·migration·recovery 안내, CHANGELOG, feature parity/requirements trace를 새 topology로 맞춘다. 역사적 문서의 v0.7 사실을 v0.8 현재 사실로 덮어쓰지 않는다.

#541의 B01~B09 table에 actual PR, source SHA, CI, native/packaged 결과와 제한을 연결한다. #542 R01~R26은 implementation→test/evidence→result로 수용한다. 메인·명세는 단일 구현 PR의 `Closes`로 닫지 않고 최종 수용이 충족된 뒤 종료한다. 마일스톤 종료는 모든 필수 작업/차단 결함 완료 뒤 수행한다.
