# v0.7.0 Stable Release Plan

> **State (2026-09-03): release preparation.** 공개 Latest는 v0.6.0이다. v0.7.0 tag와 GitHub
> Release는 아직 만들지 않으며, 아래 source·candidate gate가 모두 같은 exact main commit에서
> 통과한 뒤에만 stable로 게시한다. RC/prerelease는 만들지 않는다.

## 1. Outcome and release boundary

v0.7.0은 앱을 추가하는 release가 아니라 WSL Desktop을 주 터미널로 쓰는 흐름과 모노레포
delivery 효율을 함께 완성하는 하위 호환 minor release다.

- #521~#524: in-app dialog, persistent terminal settings, 화면 topology navigation, pane resize,
  WebGL fallback과 buffer/search 명령;
- #525/#526/#528~#531: API/Run editor draft, terminal interaction, frontend native listener와
  multiplexer refresh/preference 수명 보강;
- #532~#534: marker-owned Bash/Zsh OSC 7 integration, progressive exact workspace restore/schema
  v2, system-wide shortcut와 선택적 tray Quick Summon;
- #527/#535/#536: dependency-graph affected CI, verified candidate 승격, 3×5 bounded Windows
  package sharding.

공개 asset 계약은 15개 앱, 15 portable, 15 NSIS installer, notices, manifest의 32개 파일과
31개 manifest-declared asset, missing/undeclared/digest mismatch 0을 유지한다. release tag는 묶음
identity이고 app version은 installer/update identity다.

## 3. Compatibility and physical evidence

#518은 설치된 v0.6.0 WSL Desktop에서 다음 항목을 사용자 실기로 PASS한 뒤 completed로 닫았다.

- distro 사용자-local zellij 탐색;
- 새 zellij session 생성과 기존 session attach;
- disconnect 후 reconnect;
- 기존 zellij/Codex session 보존;
- terminal workspace 사용 흐름.

10개 앱의 legacy identifier migration과 Life Log activity-timeline absorption migration은
v0.7.0에서 제거하지 않는다. v0.7.x 설치·data read-back 근거가 쌓인 다음 minor 준비에서 제거
또는 연장을 다시 판단한다. 이 호환 코드는 이번 release blocker가 아니다.

`glib 0.18.5` GHSA-wrw7-89jp-8q8g는 Windows package에 link되지 않는 현재 Tauri GTK3 graph의
time-bounded exception을 유지한다. alert를 dismiss하지 않고 expiry 2026-11-30도 연장하지 않으며,
Tauri가 compatible patched line을 제공하거나 만료 전 별도 PR에서 재평가한다.

## 4. Source and documentation gate

Release-preparation PR은 다음을 하나의 immutable source boundary로 확정한다.

1. CHANGELOG의 exact `v0.7.0` section과 15-app version matrix;
2. v0.6.0 annotated baseline
   `d2fa25a0a1f087459838449daded00c0b09764b4`를 사용하는 installer acceptance config;
3. generated `THIRD_PARTY_NOTICES.md`, dependency/license/advisory policy와 lock hash;
4. README, AGENTS, CONVENTIONS, architecture/development/dependency/projects/roadmap/windows guide,
   15개 app README와 shared package README의 current/historical status 감사;
5. `pnpm verify:all`, release/candidate/installer static contract, release-note extraction,
   actionlint/YAML, document link와 `git diff --check`.

PR의 required GitHub Actions jobs가 모두 success인 뒤에만 main으로 merge한다. release 준비는
명시적 전체 감사이므로 affected 선택만으로 완료하지 않는다. candidate 이후 source 또는 문서가
한 줄이라도 바뀌면 기존 candidate를 무효화하고 새 exact main에서 다시 시작한다.

## 5. Exact-main unpublished candidate

merge 뒤 remote tag/Release `v0.7.0`이 없는 exact current `origin/main` 40-character SHA로
`Windows package candidate`를 수동 실행한다.

1. Ubuntu plan job이 catalog 15개 앱을 결정론적으로 3개 group으로 나눈다.
2. 세 `windows-2025` shard가 각각 5개 앱의 portable/NSIS만 build·stage한다. fan-out은 3으로
   고정하고 shard 01만 공용 cache를 저장한다. 생성된 notices는 checkout에서도 LF byte identity를
   유지하며, 각 앱 build 직전 exact bundle staging만 안전하게 초기화해 dependency cache는
   보존하면서 이전 NSIS resource payload 재사용은 막는다.
3. Linux assembly가 세 artifact를 regular-file-only topology로 합치고 notices와 manifest를
   추가해 exact 32-file candidate와 provenance metadata를 만든다.
4. Windows packaged runtime job이 assembly가 검증하고 후보 evidence에 보존한 동일 config 원본으로
   15개 앱의 cold launch, renderer/CSP/IPC, second-instance/window, stdout/stderr, owned process와
   data/transaction cleanup을 검사한다.
5. 별도 disposable Windows job은 공개 v0.6.0과 v0.7.0 app version이 다른 앱에서 baseline install
   → candidate update → uninstall → candidate fresh install → baseline rollback → final uninstall을
   수행한다. app version이 같은 앱은 NSIS same-version update를 배포 계약으로 간주하지 않고,
   baseline install/uninstall과 candidate fresh install/uninstall을 각각 검증한다. 두 경로 모두
   registry, install, marker, app-data, integration residue 0을 요구한다.

중간 shard artifact는 1일, 최종 candidate는 14일 보존한다. candidate는 private Actions artifact일
뿐 release, RC, draft, Latest나 runtime catalog source가 아니다. 어느 job이든 실패하면 tag를 만들지
않고 원인을 수정한 새 main commit에서 전체 candidate를 다시 만든다.

## 6. Stable publication by promotion

candidate가 성공한 exact main commit에 annotated `v0.7.0` tag를 한 번 만들고 tag ref를 push한다.
stable release workflow는 다음 순서를 따른다.

1. tag object, peeled commit, stable SemVer, repository와 existing release 상태를 검증한다;
2. 같은 tag·commit의 성공한 비만료 candidate workflow/artifact를 해석한다;
3. candidate metadata와 32개 asset의 name/size/SHA-256을 독립 검증한다;
4. 그 exact 파일을 새 draft에 upload한다. stable 경로에서는 15개 앱을 다시 build하지 않는다;
5. draft를 fresh download해 15 apps/31 declared/32 public/mismatch 0을 다시 확인한다;
6. 검증된 draft만 `draft=false`, `prerelease=false`, Latest로 공개한다.

release note는 tagged source의 CHANGELOG `v0.7.0` section을 사용한다. manual Release dispatch는 이미
존재하는 동일 annotated tag의 실패 workflow를 재시도하는 경로일 뿐 candidate gate나 tag 생성의
대체 경로가 아니다.

## 7. Post-publication read-back and cleanup

- GitHub API와 fresh download verifier로 annotated tag object/peeled commit, workflow, Latest,
  32 asset, 15/31/32/mismatch-0을 다시 읽는다.
- candidate와 public release 파일의 name/size/SHA-256이 byte-identical인지 확인한다.
- release plan, AGENTS, README와 current-status 문서를 실제 candidate/release run ID로 갱신하는
  post-release documentation PR을 CI 뒤 merge한다. 실행 전 evidence를 소급해서 쓰지 않는다.
- 전용 worktree가 clean이고 PR이 merged인지 확인한 뒤 worktree remove → prune → local branch
  delete → remote branch delete 순서로 정리한다.
- 마지막으로 `git worktree list`, local/remote branch, open PR/issue, tag/release와 임시 파일을
  감사한다. active·locked·dirty·unmerged 또는 host-owned worktree는 삭제하지 않는다.
