# v0.4.2 Security Hotfix Release Plan

> **Execution rule:** 각 코드·문서 변경은 기능 단위 PR로 분리하고 required GitHub
> Actions가 통과한 뒤에만 merge한다. Windows packaged-runtime 관찰은 코드·CI 증거와
> 구분하며, 기존 사용자 프로세스와 데이터를 보호할 수 없으면 성공으로 간주하지 않는다.

**Goal:** API Playground 0.3.2의 backend-only secret resolve와 persistence/redaction
경계를 공식 Windows package에서 검증하고, RC1에서 발견한 Collection persistence schema
결함을 수정한 동일 source tree를 새 RC2 package에서 다시 검증한 뒤, 증거가 통과한 source
tree만 v0.4.2 안정판으로 게시한다. RC1은 immutable historical candidate로 보존하며
수정·삭제·재사용하지 않는다.

**Source:** PR #225, PR #226, PR #228, PR #229, PR #231,
`docs/superpowers/specs/2026-08-22-v0.5.0-native-first-plan.md` P1-02·H1,
GitHub issue #176.

**Release sequence:** RC1 release preparation → immutable `v0.4.2-rc1` tag → official
27-asset publication/manifest verification → isolated Windows H1 (RC1 blocker observed) →
separate persistence schema fix PR #231 → RC2 release preparation PR #232 → immutable
`v0.4.2-rc2` tag → official 27-asset publication/manifest verification → isolated Windows
accepted H1-A~D and cleanup (completed) → stable preparation (current) → annotated `v0.4.2`
tag → stable publication/manifest verification → issue evidence and release-close documentation.

## Global Safety Constraints

- RC1, RC2와 stable tag는 각각 대응하는 release-preparation PR이 merge된 `origin/main`의
  정확한 commit에 immutable annotated tag로 만든다. 기존 `v0.4.2-rc1` tag/release나
  이전 source commit을 수정·삭제·재사용하지 않는다. RC2는 PR #231이 포함된 source tree의
  새 tag여야 한다. stable은 RC2 H1을 통과한 code tree에 문서만 갱신한 stable preparation
  PR의 merge commit에서 만들며, H1 이후 제품 코드를 바꾸면 새 RC부터 다시 검증한다.
- API Playground의 기존 `%LOCALAPPDATA%\\com.devbox.apiplayground` 경로는 테스트 전 같은
  volume의 고유 backup 이름으로 atomic rename하고, test process와 WebView child가 모두
  종료된 뒤 생성 데이터만 제거하고 원본을 복원한다. API Playground는 현재 integration
  snapshot producer가 아니므로 존재하지 않는 integration 경로를 임의로 만들지 않는다.
- 기존 API Playground process가 실행 중이거나 파일 lock 때문에 안전한 격리가 불가능하면
  종료·이동을 강행하지 않고 H1을 미검증으로 중단한다.
- secret fixture 원문은 임의의 일회성 값으로 만들고 issue, log, screenshot, shell output에
  출력하지 않는다. evidence에는 fixture ID와 SHA-256 fingerprint의 앞 12자리만 기록한다.
- LevelDB 삭제는 물리적 byte overwrite를 보장하지 않으므로 H1의 localStorage 판정은 CDP가
  반환한 **logical key/value**를 기준으로 한다. 테스트가 의도적으로 seed한 raw v1 byte가
  LevelDB log segment에 남지 않는다고 과장하지 않는다.
- clipboard reveal을 검증할 경우 원래 clipboard를 메모리에 보존하고 `finally` 정리에서
  그대로 복구한다. clipboard 읽기·복구가 불가능하면 reveal-copy 관찰은 중단하고 masked
  cURL과 persistence 부재만 검증한다.
- H1 실패 시 stable release로 진행하지 않는다. 원인 수정은 별도 기능 PR과 새 RC tag로
  처리하며 기존 RC release를 덮어쓰지 않는다.
- RC1의 packaged H1에서 Collection v1→v2가 실패한 경우처럼 일부 matrix만 통과해도
  전체 H1 성공으로 간주하지 않는다. `requiresSecretReview`의 schema metadata와 raw v1
  삭제·marker write/read-back을 RC2에서 다시 직접 확인해야 한다.
- 문서·issue·workflow 출력에는 secret fixture 원문, DPAPI sealed envelope/blob, clipboard
  원문을 기록하지 않는다. evidence는 key 존재 여부, schema version, boolean 상태, 원문 부재,
  SHA-256 fingerprint prefix와 asset size/hash 같은 비밀값이 아닌 검증 결과만 남긴다.

## Task 4 — Execute the packaged H1 matrix (RC2 accepted run completed)

**RC1 H1 result record:** RC1 packaged execution directly confirmed the DPAPI/backend-only
resolution boundary, History v1 fail-closed behavior, cURL·response·error redaction and
cross-origin redirect protections. The Collection v1→v2 path failed before a valid v2
read-back/marker result because `requiresSecretReview` boolean metadata was sanitized into a
string and the frontend parser rejected the store; the logical raw v1 key remained, so stable
was blocked. Clipboard reveal-copy was deliberately not exercised because the harness could not
guarantee exact multi-format clipboard preservation. RC2 must execute every item below again from
the beginning; no RC1 pass is copied to an RC2 checkbox. Storage-fault branches는 packaged
LevelDB를 고의로 손상시키지 않고 PR #225의 fault-fixture 회귀 테스트로 연결하며, clipboard
write는 global safety constraint에 따라 정확한 multi-format 복구가 불가능해 실행하지 않는다.

### H1-A. DPAPI and backend-only resolution

- [x] UI를 통해 secret environment variable을 추가한다. logical `apip-environments` 값은
  `secret=true`, 원문과 `plain:` prefix 부재, 비어 있지 않은 sealed envelope여야 한다.
- [x] `${NAME}` 또는 `{{NAME}}` reference를 URL/header/body/auth에 넣어 loopback echo로
  전송하고 server가 expected secret fingerprint를 수신했음을 확인한다. DOM에 표시된 request,
  response, error, History와 logical localStorage에는 원문이 없어야 한다.
- [x] browser-only command fallback은 packaged WebView의 runtime 경로가 아니므로 H1 성공으로
  가장하지 않는다. PR #225의 frontend 회귀 테스트에서 secret seal/send/reveal 거부와
  pseudo-sealed value 부재가 통과했음을 별도 코드 증거로 연결한다.

### H1-B. History v1 fail-closed deletion

- [x] CDP로 raw `apip-history` v1에 direct secret fixture를 seed하고 v2·marker는 제거한 뒤
  reload한다. reload 전 fixture raw key가 존재했음을 key name과 fingerprint로만 기록한다.
- [x] reload 후 UI가 raw history를 렌더링·검색·재전송하지 않으며 `apip-history`가 logical
  storage에서 사라졌는지 확인한다.
- [x] `apip-history-v2`가 schema version 2의 안전한 store이고 원문이 없으며,
  `apip-history-v1-migrated=2`는 raw key 부재 확인 뒤에만 존재하는지 확인한다.
- [x] automated storage fault fixture로 v2 write, raw delete, marker write 실패 각각에서
  raw UI 격리와 marker 부재·재시도 동작을 확인한다. packaged app storage를 고의로
  손상시키거나 raw backup key를 만들지 않는다.

### H1-C. Collection safe conversion

- [x] `apip-collections` v1에 reference field와 direct Authorization/Cookie/API-key/auth/body
  secret을 함께 seed하고 v2·marker를 제거한 뒤 reload한다.
- [x] reference는 보존되고 direct credential은 `[REDACTED]`, auth-safe replacement 또는
  `requiresSecretReview=true`로 변환됐는지 확인한다.
- [x] `apip-collections-v2` write/read-back 뒤 raw v1이 제거되고 marker가 기록됐으며,
  logical localStorage의 어떤 key/value에도 fixture 원문이나 raw backup/quarantine이 없는지
  전체 key scan으로 확인한다.

### H1-D. cURL, response, error, and redirect

- [x] default cURL view/copy가 Authorization, Cookie, API key, query/body/auth direct value를
  마스킹하고 environment reference는 template 형태로 보존하는지 확인한다.
