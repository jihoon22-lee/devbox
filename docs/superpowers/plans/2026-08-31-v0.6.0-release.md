## 1. Outcome and release boundary

v0.6.0은 milestone #2의 W01~W11을 한 번에 배포한 stable release다. 계획 당시 공개 Latest는
모든 gate가 끝날 때까지 v0.5.1로 유지했다. RC/prerelease는 만들지 않았으며, 비공개 GitHub
Actions artifact는 release가 아니라 exact package checkpoint로만 사용했다.

이 release의 완료 조건은 기능 PR merge가 아니라 다음 네 증거가 모두 같은 source identity를
가리키는 것이다.

1. main source와 전체 frontend/Rust/dependency/catalog CI;
2. exact current main에서 만든 unpublished Windows package candidate와 disposable installer
   lifecycle;
3. 실제 Windows+WSL 호스트에서 candidate portable을 실행한 integration/UX 결과;
4. annotated `v0.6.0` tag에서 새로 만든 public asset의 independent digest/Latest 검증.

candidate 또는 draft는 v0.6.0 외의 공개 version을 만들지 않는다. 실패한 candidate는 run과
redacted evidence만 보존하고 source를 수정한 뒤 새 main commit으로 다시 만든다.

## 4. Dependency and build-runtime decisions

### Cargo and notices

- yanked `chacha20 0.10.1`은 `rand 0.10.2`가 허용하는 non-yanked `0.10.2`로만 올린다.
  상위 `lopdf 0.44.0`/`tungstenite 0.30.0` 또는 feature surface는 바꾸지 않는다.
- Dependabot GHSA-wrw7-89jp-8q8g의 `glib 0.18.5`는 Tauri 2.11.5 Linux GTK3 graph와 patched
  glib 0.20 compatibility를 재평가했다. 2026-09-01 post-release 재검토에서도 공식 최신
  Tauri와 upstream `dev`가 GTK3 0.18을 유지하고 resolver가 glib 0.20 강제 갱신을 거부했다.
  Windows package가 link하지 않는 범위와 2026-11-30 expiry를 유지하고 alert를 dismiss하지 않는다.
- `Cargo.lock` 변경 뒤 `THIRD_PARTY_NOTICES.md`를 generator로 다시 만들고 byte-for-byte check,
  `cargo deny --locked check`, Dependabot 상태와 graph path를 기록한다.

### GitHub Actions

- checkout/setup-node/cache/upload/download는 Node 24-capable official major만 사용한다.
- repository는 pnpm 9를 유지한다. pnpm 11 이상을 요구하는 새 setup action으로 package manager를
  몰래 올리지 않고, setup-node 뒤 Corepack이 root `packageManager`의 exact `pnpm@9.0.0`을
  활성화한다.
- runtime policy test가 retired major와 `pnpm/action-setup` 재도입을 거부한다. release와
  installer workflow처럼 PR에서 직접 실행되지 않는 YAML도 static contract와 actionlint로
  검사한다. Rust action은 각각 composite(`dtolnay/rust-toolchain`), Node 24
  (`Swatinem/rust-cache`), Docker(`cargo-deny-action`) metadata를 확인한 audited ref만 허용한다.

## 5. Source gate before merge

아래 검사는 resource 사용을 감시하며 순차 실행한다. WSL의 shared target artifact 오염을
피하기 위해 전용 Linux-native `CARGO_TARGET_DIR`을 사용하고 `CARGO_BUILD_JOBS=1`로 제한한다.

1. `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm build`;
2. 15-app accessibility, Vite manifest와 initial bundle budget;
3. `cargo test --workspace`, `cargo check --workspace --all-targets`, all-target Clippy
   `-D warnings`, workspace fmt;
4. catalog/version/single-instance/package smoke config;
5. dependency policy, pnpm audit, cargo-deny, generated notices read-back;
6. release input, manifest, public/candidate verifier, installer config, candidate workflow and
   action runtime tests;
7. `git diff --check`, actionlint, document link and stale-state review.

PR의 six required jobs가 모두 success인 뒤에만 main으로 squash merge한다. CI annotation에
Node 20 action runtime 경고가 남으면 W11은 완료하지 않는다.
CHANGELOG 날짜와 version metadata도 이 PR에서 확정한다. candidate 생성 뒤 source나 문서를
한 줄이라도 바꾸면 package evidence를 무효화하고 새 main commit에서 candidate부터 다시 수행한다.

## 6. Unpublished package checkpoint

`Windows package candidate` workflow는 manual dispatch만 허용한다. 입력은 intended stable tag
`v0.6.0`과 40-character current main commit이다.

Preflight는 다음을 build 전에 확인한다.

- checkout HEAD, input commit, exact current `origin/main`이 모두 동일함;
- stable SemVer이고 remote tag와 GitHub Release가 아직 없음;
- workflow contents permission은 read-only이고 release create/edit/upload 명령이 없음.

Windows build job은 catalog의 15개 앱을 순차 build해 app별 portable/NSIS를 즉시 staging한다.
notices와 manifest를 더해 flat 32-file set을 만들고, manifest의 15 apps/31 declared asset과
모든 size/SHA-256 mismatch 0을 검증한다. candidate metadata에는 tag intent, exact commit,
repository, workflow run과 32개 digest만 기록한다.

두 번째 fresh `windows-2025` job은 v0.5.1 annotated tag
`300cb158d1f0c23973857549a1aeddd9997c3f16`의 public 32 assets를 baseline으로 받는다. 15개
모두에 대해 다음 lifecycle을 실행한다.

1. v0.5.1 install;
2. candidate update와 marker 보존;
3. uninstall과 data marker 보존;
4. candidate fresh install;
5. v0.5.1 rollback install과 marker 보존;
6. final uninstall, registry/install/shortcut/app-data/integration residue 0.

이 job은 disposable GitHub-hosted runner에서만 실행되며 pre-existing Devbox process/data/install이
있으면 mutation 전에 중단한다. package artifact와 redacted JSON evidence는 서로 다른 retention
기간으로 보관하고 artifact digest/run URL을 #493에 기록한다.

## 7. Physical Windows + WSL acceptance

candidate artifact를 새 non-system scratch directory에 내려받고 metadata/config를 같은 volume에
복사한 뒤 verifier를 다시 실행한다. 기존 Devbox process가 하나라도 있거나 app-data recovery
residue가 있으면 자동 harness는 사용자의 process를 종료하지 않고 즉시 중단한다.

### Automated portable matrix

- 15 apps cold launch, exact title/marker, bounded read-only IPC probe;
- second launch가 새 process/window를 남기지 않고 기존 main window를 restore/focus;
- renderer/runtime/console error 0, CSP와 packaged asset load;
- owned child process와 temporary app-data backup/quarantine/staging/journal residue 0;
- test-created state만 정리하고 pre-existing data는 byte-identical restore.

GitHub-hosted `windows-2025`의 elevated runner와 WebView2 Runtime 150+ 조합에서는 process 환경의
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`가 무시된다. 이 경우 harness는 각 executable image에만
적용되는 HKLM WebView2 policy를 충돌 없는 임의 port로 단 한 번 설정하고 exact read-back한 뒤,
성공·실패와 무관하게 동일 값의 소유권을 확인해 제거한다. 기존 policy value는 덮어쓰지 않고,
설치 결과가 불명확한 timeout도 재시도하지 않으며, policy 원상복구 실패는 release를 차단한다.

호스티드 elevated desktop이 외부 `ShowWindow` 계열 상태 전환을 수용하지 않는 경우에도
single-instance 검증을 생략하지 않는다. `GITHUB_ACTIONS=true`, `RUNNER_ENVIRONMENT=github-hosted`,
`RUNNER_OS=Windows`가 모두 일치할 때만 15개 앱의 second process 정상 종료, 기존 process 생존,
단일 image, visible/non-minimized primary, renderer focus 진단과 무출력을 차단 계약으로 사용한다.
처음부터 숨겨지는 앱은 second launch 후 실제 show를 계속 직접 검증한다. 일반 Windows와
self-hosted runner는 최소화→visible/non-minimized 복원을 그대로 요구하며, exact candidate의
물리 Windows Port Manager 최소화→복원 결과와 15개 앱의 공통 show/unminimize/focus source gate를
함께 보존한다.

### Human-observed UX

## 8. Stable publication

candidate와 physical blocking matrix가 PASS한 exact main commit에서만 annotated `v0.6.0` tag를
만들고 tag ref를 한 번 push한다. tag push가 release workflow의 유일한 실행이다.

1. preflight가 remote annotated tag, peeled commit/workflow SHA, stable input, existing release
   부재를 확인한다;
2. Windows job이 tagged source에서 15 portable + 15 NSIS + notices + manifest를 새로 build한다;
3. publish job은 정확히 32 assets를 draft로 staging한다;
4. verify job은 draft를 fresh download해 15 apps, 31 manifest-declared, 32 public,
   missing/undeclared/size/SHA mismatch 0을 확인한다;
5. 검증된 draft만 `draft=false`, `prerelease=false`, Latest로 전환한다.

실패한 workflow는 같은 tag를 임의 재작성하지 않는다. draft/partial 상태와 원인을 먼저 감사해
복구 가능하면 같은 immutable artifact boundary 안에서만 처리하고, source 변경이 필요하면
v0.6.0을 공개하지 않은 상태에서 tag/release mutation 계획을 사용자에게 보고한다.

- candidate와 public package가 byte-identical하다고 가정하지 않고 public portable의 핵심
  cold/second-instance/WSL regression을 다시 확인;
- #482/#492/#493 checklist와 milestone을 실제 evidence만으로 닫음;
- 전용 worktree clean/merged 확인, worktree remove → prune → local branch delete → remote branch
  delete 순서로 정리;
- 마지막 `git worktree list`, local/remote branch, open PR, running build process와 자원 사용률을
  재감사한다. active/locked/dirty/unmerged 또는 host-owned worktree는 삭제하지 않는다.
