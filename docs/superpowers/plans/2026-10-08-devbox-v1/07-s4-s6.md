- 상세화 수준: 하위 프로젝트 셋을 과제·파일·인터페이스·핵심 테스트까지 적었다. **각 하위 프로젝트의 첫 과제(S4-1·S5-1·S6-1)에서 실제 코드에 맞춰 단계별 코드까지 상세화한 뒤 실행한다.** 상세화 결과는 이 문서를 `07a-s4-editor-git.md`·`07b-s5-tools.md`·`07c-s6-release.md`로 나눠 담는다.

**Goal:**
- **S4:** 파일 편집(하이라이트·LSP 진단·이동·서식), 미리보기, Git 전체(hunk·커밋·브랜치·stash·blame·원격·충돌 해결·정리), Dependency Lens를 제공한다. 에이전트 검토와 같은 diff·병합·충돌 컴포넌트를 쓴다.
- **S5:** API 요청(HTTP·GraphQL·WS·SSE·gRPC·MCP), 웹훅·모의 서버, 변환 도구 21종, 개발 환경 점검·도구 설치를 제공한다.
- **S6:** 설치기·업데이트·릴리스 워크플로, 성공 기준 SC1–SC9 측정, 문서 정리, 버전을 한 번만 올려 v1.0.0을 공개한다.

**Architecture:**
- 편집은 S3의 `documents` + `DocumentStore`(코드 정책)를 그대로 쓴다.
- LSP는 데몬이 WSL에서 서버를 띄우고, Content-Length 프레이밍을 벗긴 JSON 메시지를 스트림으로 중계한다. 화면은 `@codemirror/lsp-client`의 `Transport`에 그 스트림을 붙인다. 데몬은 `publishDiagnostics`를 엿봐 문제 목록(S2)에 넣는다.
- Git은 S1의 `crates/git`을 넓힌다. `.git`을 inotify로 감시해 `git.changed`를 발행한다.
- API·웹훅은 데몬 crate(`api`·`webhooks`)다. 변환 도구는 화면(TS)에 둔다.
- 출시는 `windows.yml`의 태그 실행에 release job을 더한다(워크플로 3개 이하, SC7).

**Tech Stack:** S3 스택 + `@codemirror/language-data`·`@codemirror/lsp-client`·`@codemirror/merge`, `reqwest`(rustls)·`tokio-tungstenite`·`eventsource-stream`·`tonic`+`prost-reflect`(gRPC reflection), `rmcp`(MCP 클라이언트), `hyper` 1(웹훅), OSV API.

**Spec:** [01-design.md](01-design.md) §2.3·§2.4·§2.5·§8.2 소스·도구·§9 `lsp`·`git`·`api`·`webhooks`·`tools`·§9.1-1·4·§9.3·§10·§1 성공 기준

## Global Constraints

- S0b–S3의 Global Constraints를 따른다.
- 버전은 S6에서 한 번만 올린다(`1.0.0-dev` → `1.0.0`). 중간 공개 릴리스는 없다.
- 개인용 보안 범위(ADR 0016)를 따른다. 코드 서명·업데이트 서명·네이티브 확인 대화상자·추가 접근 제어는 하지 않는다. 업데이트 무결성은 GitHub 자산 digest(SHA-256) 비교로 한다.
- LSP 서버 설치는 관리형 설치기를 만들지 않는다. 감지한 설치 명령을 터미널 세션에서 실행한다(sudo 입력 가능).
- API 요청 본문·응답·헤더 값은 로그에 남기지 않는다. 기록 본문은 `api-history/` 파일, 색인은 `index.db`다.
- 웹훅 리스너의 LAN 허용은 사용자가 켤 때만이다. 기본은 127.0.0.1이다.
- 변환 도구 21종은 v0.9.0 `packages/api-studio-features/src/transforms/tools/*`와 테스트를 이식한다. 해시·HMAC는 WebCrypto다.

### S4-5: Git 조회·변경 넓히기

**Files:**
- Modify: `crates/git/src/{status,diff,mutate}.rs`
- Create: `crates/git/src/{hunks,branches,stash,blame,remote,watch,safety}.rs`

**Interfaces:**
- hunk 단위 stage·unstage·discard(`git apply --cached [--reverse]`에 hunk 패치를 넣음)
  - discard는 `always` 확인이다.
  - stage는 reversible(되돌리기 = unstage)이다.
- `git.commit{ message, amend }`, `git.branches`, `git.checkout{ branch, create? }`, `git.branch_delete{ force }`(always)
- `git.stash{ push|pop|apply|drop|list }`, `git.log{ path?, limit, skip }`, `git.blame{ path }`
- `git.fetch`·`git.pull{ rebase, expect }`·`git.push{ force_with_lease?, expect }`(push·pull 모두 always)
  - 진행 작업 ID와 진행 이벤트를 쓴다.
  - 자격 증명은 git이 가진 것(credential helper)만 쓴다.
  - `expect = { branch, headOid, upstream, upstreamOid }`는 확인 대화상자가 보여 준 상태다. 실행 직전 현재 브랜치·HEAD·upstream 설정·upstream OID와 비교해 다르면 `git.state_changed{ branch, head, upstream }`(지금 상태)로 거절하고 원격을 건드리지 않는다(01-design §5.2·§9.1-12, AR-F01). push의 refspec은 확인한 `headOid:refs/heads/<branch>`로 고정한다. 확인 뒤 생긴 커밋이 섞이지 않는다. S1 `ReviewExpect`·`check_expect`와 같은 모양을 쓴다.
- `git.worktrees{ projectId }`
- 정리 목록: 병합된 브랜치·연결 없는 worktree. S1 `agents.cleanup_candidates`를 일반화한다.
- `watch.rs`: `.git`의 `HEAD`·`index`·`refs` 변경을 inotify로 감시 → `git.changed { projectId }`(300ms 디바운스)
- `safety.rs`: 프로젝트를 처음 등록할 때 Git 실행 설정(`core.fsmonitor`·`core.hooksPath`·`filter.*`·`diff.external`)을 검사해 경고한다(01-design §12). S0b의 `projects.add`에 붙인다.

**핵심 테스트:**
- `stage_and_unstage_a_single_hunk`
- `discard_hunk_restores_only_that_hunk`
- `amend_keeps_author`
- `push_force_with_lease_refuses_when_remote_moved`(로컬 bare 원격)
- `push_after_an_external_checkout_is_refused`(AR-F01 입력): 로컬·bare 원격에서 브랜치 A 상태로 `expect`를 만든 뒤 터미널에서 B로 checkout → `git.push{ expect: A }` → `git.state_changed`, bare 원격의 모든 ref 그대로. 상태가 그대로인 A는 정상 push
- `pull_after_upstream_config_changed_is_refused`: `expect` 이후 `branch.<A>.merge`를 바꿈 → `git.state_changed`
- `watch_emits_changed_after_commit_from_terminal`
- `risky_git_config_is_reported_on_project_add`

### S4-6: 3-way 충돌 해결 (CV-F01)

**Files:**
- Create: `crates/git/src/conflicts.rs`(v0.9.0 `crates/repositories-engine/src/commands/conflicts.rs` 참고), `app/src/ui/MergeView.tsx`(`@codemirror/merge`)

**Interfaces:**
- `git.conflicts{ projectId|worktree }` → 파일 목록(종류: 양쪽 수정·삭제/수정·추가/추가)
- `git.conflict_preview{ path }` → `{ base, ours, theirs, merged, token: { worktreeHash, stageOids: [1,2,3] } }`
- `git.conflict_apply{ path, resolution, token }`(mutation)
  - 적용 직전에 작업 파일 해시와 index stage OID를 다시 읽는다. `token`과 다르면 적용하지 않고 `git.conflict_stale`(새 미리보기 포함)을 돌려준다.
  - 같으면 원자적으로 쓰고 `git add`한다.
- 화면 `MergeView`:
  - base·ours·theirs·결과 4칸이다. hunk마다 [내 것][그쪽][둘 다]를 고르거나 직접 편집한다.
  - 칸 머리에는 ours·theirs 대신 실제 브랜치·커밋 이름을 쓴다. rebase 중에는 Git의 ours가 기준(onto) 쪽, theirs가 다시 적용 중인 커밋이라 merge와 뜻이 뒤바뀌므로, "기준 `main`"·"적용 중 `abc123 커밋 제목`"처럼 적는다(CV 제안).
  - `stale`이면 작성 중 결과를 보존한 채 비교를 다시 보인다.
- 에이전트 작업의 기준 반영 충돌(S1)에서도 같은 화면을 연다. 이때 대상은 그 작업 폴더다.

**핵심 테스트:**
- `apply_refuses_when_file_changed_after_preview`
- `apply_refuses_when_index_stage_changed_after_preview`

### S5-3: 컬렉션·환경·가져오기·실행기·코드 생성 (화면 + 파일)

- 실행기:
  - 순서대로 실행하고, assertion을 평가하고, 캡처를 세션 변수에 넣는다.
  - 캡처 값은 `{ value, fromRunId, fromRequestId }` 출처를 가진다. 생산 요청이 건너뛰기·취소·실패면 그 값을 쓰지 않고 "출처 요청 실패"로 표시한다(CV-F04).

  - 본문 종류(GraphQL·JSON·raw·form·multipart·binary)마다 초안을 메모리에 따로 둔다. 종류를 바꿔도 다른 종류의 초안은 남는다. 보내기 snapshot과 파일 저장에는 활성 종류만 넣고, 비활성 비밀은 풀지 않는다.
  - "저장"(같은 파일 갱신)과 "새 요청으로 저장"을 나누고, 탭과 컬렉션 트리에 dirty 점을 보인다(AR U04).
- 결과 출처(AR-F08): 응답 보기 머리에 그 응답을 만든 요청(이름·메서드·URL·보낸 시각)을 보인다. 지금 편집기 내용과 다르면 "편집 중인 요청과 다름"을 표시한다.
- 실행기 화면(AR U04·CV 제안): 실행 전에 순서와 생산·소비 관계(어느 요청의 캡처를 어느 요청이 쓰는지)를 미리 보여 주고, 끌어서 순서를 바꾼다. 요청별로 변수의 출처(환경·세션·캡처한 생산 요청)와 건너뛴 이유를 보인다.
- 가져오기: cURL·Postman·Insomnia·Bruno·HAR·OpenAPI → 미리보기 → 프로젝트 또는 개인 컬렉션
- 코드 생성: curl·fetch·axios·python requests·Go·Rust reqwest
- 응답 비교(이전 기록과). 요청·응답 본문 편집·보기는 S2 Task 15b의 `CodeView`를 쓴다. "응답을 노트에 붙이기"는 S3가 필요해 S6-1b에서 한다

**핵심 테스트:**
- 이식한 TS 테스트 전부
- `captured_value_from_failed_request_is_not_used`(실행기 단위)
- `skipped_or_cancelled_producer_blocks_the_consumer`(CV-F04·AR-F03 입력): 이전 실행의 토큰이 세션에 있는 상태에서 생산 요청을 ① 비밀 재검토로 skip ② 파일 누락으로 skip ③ 취소 → 소비 요청 송신 0회, "출처 요청 실패" 표시. `stopOnFailure` 참·거짓 모두

### S5-5: gRPC·MCP 클라이언트·OAuth 2.1 (묶음 3)

**Interfaces:**
- `api.grpc_describe{ target, protoFiles? }`: reflection 또는 proto 파일로 서비스·메서드 목록

- 화면: 메서드 고르기 → JSON 입력(스키마 기반 기본값) → 응답
- gRPC 초안과 결과(01-design §9.1-14, AR-F07·F08):
  - 입력 초안은 (대상, 메서드)마다 메모리에 둔다. 필터가 선택을 바꿔도 이전 메서드의 dirty 초안을 지우지 않는다. 필터의 자동 선택 동작 자체는 유지한다.

**핵심 테스트:**
- 로컬 tonic 테스트 서버(reflection 켬)로 describe·unary
- `grpc_filter_switch_keeps_the_dirty_draft`(AR-F07 입력): 메서드 A 입력 수정 → 필터로 B 자동 선택 → 필터 지움 → A의 수정 내용 그대로. 일치 없음 → 지움에서도 그대로
- `late_grpc_response_shows_its_origin`(AR-F08 입력): A 호출 대기 → B 선택 → A 응답 도착 → 결과 머리에 A, 기록 항목은 A, [취소]는 A의 요청 ID
- S1의 `devbox mcp`를 stdio 대상으로 써서 `tools/list` 왕복(자기 자신을 시험 대상으로)

- 도구 21종: JSON 4, 인코딩 7, 시간 1, 텍스트 3, 보안 3, 정규식 1, 차이 1, JWT 1. `api-studio-tools.json`에서 한 행씩 대조한다.
- v0.9.0의 제품 간 전달 동작(`ApiHandoffAction`·`KnowledgeDraftAction`)은 옮기지 않는다(01-design §2.7). 대신 "응답을 노트에"·"요청으로 열기"를 같은 앱 안 이동으로 둔다.
- 자동 감지: 입력을 보고 맞는 도구를 제안한다(JSON·JWT·Base64·URL 인코딩·Unix 시각·UUID). 최근 사용 도구는 `localStorage`에 둔다.
- 명령 팔레트 "클립보드로 변환…": 클립보드 값으로 제안 도구를 연다.
- 로그·터미널 선택의 우클릭 "변환 도구로 보내기"(코드 편집기 선택은 S4가 필요해 S6-1b에서 한다)
- 파이프라인 저장(X-2)은 하지 않는다.
- 정규식 도구는 화면(TS)의 `RegExp`로 실행하고, 일치 위치는 UTF-16 code unit이다. v0.9.0처럼 Rust의 byte 위치를 받아 JS 문자열을 자르지 않는다(01-design §9.1-15, AR-F09).

**핵심 테스트:** 이식한 테스트 전부 + `detect` 단위(입력별 제안 순서) + `regex_ranges_are_utf16_and_cover_the_text`(AR-F09 입력: `가a나`에서 `a` → 1..2, `😀a`에서 `a` → 2..3, 일치·불일치 조각을 이으면 원문과 같음, 너비 0 일치·여러 일치 포함).

# S6 마무리·출시

## 작업 묶음

S6 전체가 브랜치 `v1/s6-release` 하나, PR 하나다(00-roadmap §3). 작업 위치는 worktree `../devbox-wt/v1-s6-release`다.
묶음은 그 안의 중간 지점이다. 묶음이 끝나면 로컬 검사(`pnpm check`, 그 시점에 없으면 있는 검사만) → `PROGRESS.md` 묶음 행 갱신 커밋 → push 한다. PR·CI는 없다. 세션 인계 지점이 된다.
PR은 마지막 묶음이 끝난 뒤 한 번 열고, 그 CI가 S6 전체를 한 번 검사한다.

| 묶음 | 과제 | 끝나면 |
|---|---|---|
| 상세화 | S6-1 | 커밋(이 브랜치의 첫 커밋) |
| AF | S6-1b–S6-2 | push |
| AG | S6-3 | push |
| AH | S6-4–S6-6 | **S6 PR 열기** → CI → 머지 → main CI 통과 → 태그 `v1.0.0` |

### S6-3: 업데이트 (CV-F09)

**Files:**
- Create: `app/src-tauri/src/update.rs`, `app/src/features/settings/Update.tsx`

**Interfaces:**
- 릴리스 빌드만 하루 한 번과 요청 시 GitHub Releases `latest`를 조회한다. 개발 빌드(`-dev`)는 끈다.
- 새 버전이면 상태 표시줄·설정에 알린다.
- [업데이트]
  1. `devbox-<v>-setup.exe`를 `%LOCALAPPDATA%\…\updates\`로 받는다.
  2. GitHub 자산 `digest`(SHA-256)와 비교한다.
  3. 실행 중 작업 요약(에이전트 n·서비스 n — 데몬 쪽은 유지됨을 함께 안내)을 보여 주고 확인받는다.
  4. 앱을 종료하고 `/S`로 실행한다. setup이 끝나면 앱을 다시 연다.
- 진행 상태는 Windows 앱(Rust)이 소유한다. `devbox://update` 이벤트로 모든 창에 알리고, 새로 열린 창은 `update_status()`로 현재 상태를 받는다(CV-F09).
- 서명 기반 Tauri updater는 쓰지 않는다(ADR 0016).
- 새 앱은 시작할 때 내장 바이너리 버전이 다르면 데몬을 다시 배치한다(S0b 배치 + 01-design §4.6). 실행 unit·tmux는 유지된다.

**핵심 테스트:**
- digest 비교·자산 고르기 단위(GitHub API 응답 fixture)
- `update_state_survives_window_close_and_reopen`(상태 소유가 Rust 쪽인지 단위)
