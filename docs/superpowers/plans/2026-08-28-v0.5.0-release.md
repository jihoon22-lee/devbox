# devbox v0.5.0 Release Plan

> **Execution rule:** v0.5.0 기능 범위는 이미 main에 병합된 P1·P2·선택 P3와 신규
> Devbox Launcher·Log Lens를 그대로 유지한다. release preparation, 실패 수정, stable
> preparation은 서로 다른 PR로 처리하고 required GitHub Actions가 모두 성공한 뒤에만
> merge한다. Windows packaged-runtime 관찰은 코드·CI 증거와 구분하며 직접 실행하지 않은
> 항목을 성공으로 표시하지 않는다.

**Goal:** v0.4.2 stable을 기준으로 구현 완료된 15개 앱의 target version과 배포 행렬을
정렬하고, immutable v0.5.0 RC package에서 W1~W4를 검증한 뒤, 같은 product source를
stable preparation과 exact stable package 재검증을 거쳐 `v0.5.0`으로 게시한다.

**Source:** `docs/superpowers/specs/2026-08-22-v0.5.0-native-first-plan.md`,
`docs/roadmap.md`, v0.5.0 milestone, GitHub issue #176, v0.4.2 release plan과 그 H1 증거.

**Release sequence:** target-version/release-preparation PR → immutable `v0.5.0-rc1` tag →
official 32-asset publication and independent verification → isolated Windows W1 → W2 → W3 →
W4 → failure이면 별도 fix PR과 새 RC, 모두 통과하면 stable-preparation PR → immutable
annotated `v0.5.0` tag → exact stable 32-asset verification and packaged replay → evidence
documentation, milestone close, worktree/branch cleanup.

## 1. Fixed scope and release inventory

### 1.1 Included scope

- P1 전부: native-first/dependency policy, v0.4.2 API security boundary, catalog/runtime,
  single-instance inbound, integration snapshot, context menu, WSL terminal/workspace/profile,
  각 기존 앱의 필수 usability 보강.
- P2 전부: `applink` v2 one-time handoff, Webhook→API와 Life Log→Knowledge, identity-safe
  process/Git mutation, Toolbox/API/document/content-index/capture/export/install-root/LSP/log/
  environment 기능.
- 선택 P3 전부: Devbox Launcher, Log Lens, 15개 앱 window state, 선택된 각 앱의 detection,
  pipeline, history, import/export, template, inspector, support, retry, replay, cleanup 기능과
  Toolbox→API·Run/WSL→Log Lens handoff.
- v0.4.2에서 먼저 출시한 API backend-only secret resolve, fail-closed History/Collection
  migration과 redaction은 v0.5.0에서도 release-blocking 회귀 기준이다.

명시적으로 제외된 범위는 계획서 §6을 그대로 유지한다. 전체 IDE/DB GUI/container desktop,
cloud sync/telemetry, runtime download에 의존하는 core flow, unrestricted shell/plugin execution,
GraphQL subscription/introspection/codegen, OCR/semantic search 등은 이번 release에 조용히
추가하지 않는다. 외부 도구가 없거나 network가 끊긴 환경에서도 devbox-owned core flow는
동작해야 한다.

## 2. Global safety and evidence constraints

- RC와 stable tag는 대응 preparation PR이 merge된 `origin/main`의 exact commit에 annotated
  tag로 만든다. 이미 존재하는 tag/release를 force-update, delete, asset replacement 또는
  dispatch 재사용하지 않는다.
- RC에서 product code, manifest, dependency graph, Tauri config가 바뀌면 stable로 바로
  진행하지 않는다. 별도 PR 뒤 `v0.5.0-rc2`처럼 새 immutable RC에서 W1~W4를 다시 시작한다.
- release asset과 harness 임시 파일은 여유가 큰 E:에만 둔다. C: free space가 100GB 아래로
  내려가면 새 build/download를 시작하지 않고 원인을 확인한다. WSL sparse disk compact나
  빈 블록 반환은 이번 작업 중 수행하지 않는다.
- Windows acceptance 전 기존 devbox process, app-data, integration snapshot, install registry,
  shortcut과 clipboard를 read-only로 조사한다. 기존 process가 있거나 path lock 때문에
  exact isolation이 불가능하면 강제 종료·이동하지 않고 해당 항목을 미검증으로 중단한다.
- app-data와 integration path 격리는 같은 volume의 고유 backup 이름으로 atomic rename한다.
  test parent와 새 WebView child가 모두 종료된 뒤 생성 데이터만 지우고 원본을 복원한다.
  원래 없던 path는 cleanup 뒤에도 없어야 한다. backup residue가 있으면 다음 앱으로 진행하지
  않는다.
- process cleanup은 harness가 시작하고 exact PID/creation time으로 추적한 process tree만
  대상으로 한다. `taskkill /IM`, broad process-name kill, 기존 WSL/container/service 중지는
  금지한다.
- clipboard는 text/image/HTML/file-drop 등 기존 format을 정확히 메모리에 보존하고 finally에서
  복원할 수 있을 때만 쓰기 검증한다. 그렇지 않으면 clipboard write를 미실행으로 기록한다.
- secret fixture는 매 run마다 생성한 일회성 값으로 하고 issue, log, screenshot, result JSON에
  원문이나 DPAPI envelope를 남기지 않는다. evidence에는 fixture ID, boolean 결과와 SHA-256
  prefix만 허용한다.
- installer/upgrade/rollback은 기존 사용자 설치가 없는 disposable Windows account/VM 또는
  충돌하지 않는 검증 환경에서만 수행한다. 실제 사용자 uninstall registry나 install root와
  겹치면 overwrite하지 않는다.
- issue #176에는 exact tag/commit/workflow, Windows build/WebView2, asset count/hash, 실행/미실행
  항목, cleanup을 comment로 기록한다. 기존 historical checkbox를 직접 관찰 없이 바꾸지 않는다.

pnpm install --frozen-lockfile
pnpm test

## 10. Task H — RC failure control or acceptance

RC에서 failure가 하나라도 관찰되면:

1. 기존 RC tag/release와 asset을 그대로 보존한다.
2. issue #176에 failed scope, 환경, exact asset, cleanup과 stable block을 기록한다.
3. 원인을 순수 logic, package/config, environment/reproducibility로 분류한다.
4. 제품/배포 결함은 별도 fix PR에서 최소 회귀 테스트와 전체 CI를 통과시킨다.
5. 새 preparation section과 `v0.5.0-rcN` tag를 만들고 영향을 받은 checkpoint만이 아니라
   W1~W4 전체 release gate를 새 exact package에서 재수행한다.

## 13. Stop conditions

다음 조건에서는 사용자의 기존 상태를 추측해 변경하지 않고 release 진행을 멈춘다.

- C: free space 100GB 미만이며 안전한 E: 대체 경로를 쓸 수 없음
- 기존 devbox/WSL/container process 때문에 exact data isolation이 불가능함
- disposable Windows installer/upgrade 환경을 확보할 수 없음
- required CI 또는 Release workflow 실패
- asset count/hash/version/tag/head SHA 불일치
- W1~W4 release-blocking 항목 실패 또는 직접 관찰 불가
- backup/clipboard/registry/process cleanup을 보장할 수 없음
- secret이나 사용자 path가 evidence에 노출될 위험

중단은 release gate를 완화하는 근거가 아니다. 안전한 대안, 새 RC 또는 사용자의 명시적
환경 지원으로 같은 gate를 다시 수행한다.
