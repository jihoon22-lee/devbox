## 2. Global safety and evidence constraints

- RC와 stable tag는 대응 preparation PR이 merge된 `origin/main`의 exact commit에 annotated
  tag로 만든다. 이미 존재하는 tag/release를 force-update, delete, asset replacement 또는
  dispatch 재사용하지 않는다.
- RC에서 product code, manifest, dependency graph, Tauri config가 바뀌면 stable로 바로
  진행하지 않는다. 별도 PR 뒤 다음 `v0.5.0-rcN` immutable RC에서 W1~W4를 다시 시작한다.
- release asset과 harness 임시 파일은 여유가 큰 E:에만 둔다. C: free space가 100GB 아래로
  내려가면 새 build/download를 시작하지 않고 원인을 확인한다. WSL sparse disk compact나
  빈 블록 반환은 이번 작업 중 수행하지 않는다.
- Windows acceptance 전 기존 devbox process, app-data, integration snapshot, install registry,
  shortcut과 clipboard를 read-only로 조사한다. 기존 process가 있거나 path lock 때문에
  exact isolation이 불가능하면 강제 종료·이동하지 않고 해당 항목을 미검증으로 중단한다.
- app-data와 integration path 격리는 같은 volume의 고유 backup 이름으로 atomic rename한다.
  test parent와 새 WebView child가 모두 종료된 뒤 생성 데이터만 지우고 원본을 복원한다.
  원래 없던 path는 cleanup 뒤에도 없어야 한다. backup residue가 있으면 다음 앱으로 진행하지
  않는다.
- process cleanup은 harness가 시작하고 exact PID/creation time으로 추적한 process tree만
  대상으로 한다. `taskkill /IM`, broad process-name kill, 기존 WSL/container/service 중지는
  금지한다.
- clipboard는 text/image/HTML/file-drop 등 기존 format을 정확히 메모리에 보존하고 finally에서
  복원할 수 있을 때만 쓰기 검증한다. 그렇지 않으면 clipboard write를 미실행으로 기록한다.
- secret fixture는 매 run마다 생성한 일회성 값으로 하고 issue, log, screenshot, result JSON에
  원문이나 DPAPI envelope를 남기지 않는다. evidence에는 fixture ID, boolean 결과와 SHA-256
  prefix만 허용한다.
- installer/upgrade/rollback은 기존 사용자 설치가 없는 disposable Windows account/VM 또는
  충돌하지 않는 검증 환경에서만 수행한다. 실제 사용자 uninstall registry나 install root와
  겹치면 overwrite하지 않는다.
- issue #176에는 exact tag/commit/workflow, Windows build/WebView2, asset count/hash, 실행/미실행
  항목, cleanup을 comment로 기록한다. 기존 historical checkbox를 직접 관찰 없이 바꾸지 않는다.

### 2.1 Relocation-ready cleanup intent (v0.5.0 historical execution rule)

Release evidence and disposable build state are intentionally separated from the repository. During
acceptance, Windows packages, downloaded assets, manifests, metadata, harnesses, and redacted
results stay on the E: volume. After all devbox release work and cleanup finish, the user will move
the WSL distribution storage from C: to E:, then move projects from `/mnt/e/projects` to
`/home/jihoon/projects` inside that relocated WSL environment. Both are user-scheduled
copy/verification/migration boundaries, not release-automation work or permission to delete the
source tree early; no move may cross a live process, lock, or user-data boundary.

The following preservation rule governed the v0.5.0 execution. RC1~RC3 tags/releases were later
deleted by explicit user instruction; their workflow/evidence remains historical.

The v0.5.0 execution required preserving until independently incorporated into the release evidence:
immutable RC tags/releases,
their exact asset manifests and SHA-256 results, source and documentation history, dirty or
unmerged worktrees/branches, unregistered user files, active process/app-data/integration paths,
and any host-owned or locked `.claude` worktree. Historical absolute paths in tests or workthroughs
are evidence, not a reason to rewrite or remove those files.

Only after the final audit may cleanup remove a worktree or branch that is clean, demonstrably
merged or superseded by a reviewed squash, has no unique user changes, and is not active, locked,
unmerged, or host-owned. Regenerable `node_modules`, `dist`, release downloads, runtime scratch,
and external build caches are removable only after their source/evidence review; they are never a
substitute for classifying a dirty worktree. The prescribed mutation order remains worktree remove
→ `git worktree prune` → local branch delete → confirmed remote branch delete. No force delete,
reset, broad clean, or blind recursive removal is allowed.

## 14. Stop conditions

다음 조건에서는 사용자의 기존 상태를 추측해 변경하지 않고 release 진행을 멈춘다.

- C: free space 100GB 미만이며 안전한 E: 대체 경로를 쓸 수 없음
- 기존 devbox/WSL/container process 때문에 exact data isolation이 불가능함
- disposable Windows installer/upgrade 환경을 확보할 수 없음
- required CI 또는 Release workflow 실패
- asset count/hash/version/tag/head SHA 불일치
- W1~W4 release-blocking 항목 실패 또는 직접 관찰 불가
- backup/clipboard/registry/process cleanup을 보장할 수 없음
- secret이나 사용자 path가 evidence에 노출될 위험

중단은 release gate를 완화하는 근거가 아니다. 안전한 대안 또는 사용자의 명시적 환경 지원으로
같은 gate를 다시 수행하며, 새 RC는 사용자가 명시적으로 요청한 경우에만 만든다.
