## Implemented development topology

`apps/catalog.json` remains schema v2. Its original 15 public applications keep
their release, capability and Manager visibility contracts. Four development
entries have `release=false`, `managerVisible=false`, and no legacy handoff
capabilities. Packaging selectors still select 15 apps and 32 public assets.
Do not promote the development entries by changing those flags alone.

`apps/products.json` is a separate schema v3 development contract, parsed by
`catalog::products` and consumed by all four native shells. Product, Component,
Feature, Route and Command are distinct records/fields in that one static
catalog. Duplicate routes and command IDs, foreign owners, unregistered
components, future schemas and unsupported authority fail validation.

The four shells consume `packages/product-shell` and `crates/product-shell-tauri`.
These are extracted for four actual consumers; domain engines remain in the
existing apps. Navigation is keyboard accessible, bounded to 64 history entries,
and keeps visited route components mounted so navigation is not a lifecycle
termination signal. Heavy routes load lazily. Browser preview is labelled as
synthetic; failed native initialization is never replaced with a mock success.
Optional `?route=` development selection accepts only a registered local route.

The current route surface explicitly reports that feature migration is pending.
No legacy executable is invoked from these surfaces. The later bundles must
replace the foundation routes with real domain implementations and tests.

## Identity decisions and current limits

| Concern | Decision | Evidence / remaining gate |
|---|---|---|
| Product identity | New `com.devbox.v08.{workspace,apistudio,knowledge,controlcenter}` base identifiers | Catalog/config validator; no anchor identifier reuse |
| Development data and mutex | Runtime suffix derived from canonical executable location, with a fresh native session UUID | Native adapter; dedicated Windows fixture runs two locations concurrently |
| Production install identity | Verified suite/portable registration must replace development location identity in B08 | Not implemented; location hashing is not a trusted installation registration |
| Legacy data root | No legacy DB/config opened by shell commands | Read-only describe/route-status surface |
| Destination data | B02–B06 import into new product stores; B08 controls cutover/write barrier | Domain importers and activation are pending |
| NSIS/ARP/shortcuts/protocol | New product names and identifiers; no legacy uninstall/association mutation in B01 | Windows workflow builds hidden NSIS packages; installer lifecycle proof remains pending |
| Single instance | Existing Tauri plugin uses the runtime namespace | Same-location second process and different-location concurrency tested by Windows fixture |
| Vault | Keep user-selected existing vault path; do not copy or relocate notes automatically | Knowledge importer pending B03 |
| Downgrade | Preserve old generation and new data separately; no reverse-schema promise | B08 recovery state machine pending |

Canonical executable location plus a hash distinguishes development copies; it
does not authenticate a same-user malicious process, prove Windows file identity
against aliases, or implement production portable discovery. The shared shell
does not expose a cross-process server. Its handshake is provenance and replay
validation on Tauri's existing local webview transport, not a new OS sandbox.

## Authority and lifecycle decisions

| Responsibility | Owner / authority | Lifecycle and writer rule |
|---|---|---|
| Shell | Owning product, `shell-read` | Product lifetime; no arbitrary command dispatch |
| API secrets / requests | API Studio API adapter | Source-owned secret store; decrypt only for explicit execution |
| Webhook listener | API Studio listener adapter | Independently stoppable worker; raw headers bounded and memory-only |
| Transforms | API Studio transform adapter | Bounded operation; HMAC/JWT transient policies remain enforced |
| Notes | Knowledge notes adapter | Vault files remain authoritative; templates are user data |
| Activity | Knowledge activity worker | Separate single writer; opt-in sources and retention |
| Search | Read-only search adapters | Existing source indexes; roots/exclusions/saved queries are authoritative |
| Project / editor | Workspace project and editor adapters | Worktree identity/trust; LSP lifetime separate from editor surface |
| Runtime | Workspace runtime worker | Owns tasks, services, run logs and execution-time secrets |
| External process action | Separate Workspace action adapter | Revalidates selected external process; no Runtime secret access |
| Terminal | Workspace PTY worker | Hide/unmount does not terminate owned PTY; restored UI is not automatic execution |
| Launcher | One registered shortcut owner per installation scope | B07/B08 leases and collision handling; no arbitrary shell commands |
| Installation / recovery | Control Center | Explicit review, stage/validate/quiesce/activate/health/commit/recover |

Only the first row is exposed by the current native shell. The remaining rows
constrain subsequent adapters; they are not claims that workers already exist.
Logical responsibility does not require one daemon or executable per row.

The inlined Tauri plugin autogenerates explicit command permissions. The local
`main` capability grants only `describe` and `route_status`; native code also
checks the real window label and origin. Remote origins, foreign installation
and session IDs, future protocol versions, unknown routes, expired deadlines,
oversize request values and replay are rejected. The replay cache holds at most
1,024 unexpired IDs, rejects overload, and never evicts live IDs to admit work.
Response provenance includes owning product/component, request ID and revision.
No path, command line, secret value or artifact body appears in the handshake.

## Migration harness and source preservation

The Control Center core owns the initial harness. It is not a production
migration command and must not be connected to arbitrary renderer-selected
paths. Domain importers and a native source/destination resolver remain required.

`acquire_snapshot` uses a read-only SQLite connection, pins one read transaction,
checks supported `user_version`, and steps the SQLite backup API in bounded
chunks. It includes committed WAL content while excluding an in-flight writer's
uncommitted row. Backup uses a new staging directory, a 256 MiB size budget and
a ten-second deadline with cancellation checks. Integrity, schema and digest
checks apply to the completed backup artifact, not the live source DB. Failed
stages remain unaccepted. Logical source schema/data are unchanged; ordinary
SQLite locks/SHM and unrelated source writers are not byte-immutability promises.

`import_once` records snapshot/source → destination mapping in the same SQLite
transaction as the destination write. Failed writes roll back, repeated mapping
is a no-op, and a conflicting mapping is rejected. The caller must provide an
isolated destination connection; this low-level harness does not authorize a
connection, map real product schemas, merge records or manage scheduler enable
states. B02–B06 add domain dry-run plans and conflict/reference validation. B08
adds cross-store quiesce, durable suite journal and activation/recovery.

The legacy platform implementations already use distinct DPAPI entropy domains:
API environment `devbox.api-playground.secrets.v1`, API gRPC TLS
`devbox.api-playground.grpc-tls-credentials.v1`, and Runtime environment
`devbox.run-manager.environment.v1`. They use user-bound DPAPI and prohibit UI
prompts. Reusing/new identifiers alone does not determine decryptability.
Preserve these owner adapters and the existing `secrets::SecretReference`,
`Sealer` and versioned envelope. No central decrypted store, new SecretRef
protocol or plaintext migration file is introduced. Windows cross-owner
decrypt/reseal acceptance remains required before secret import can be claimed.

Existing AppLink typed targets and one-time claim/ack/restore remain the artifact
transport until product adapters are connected. The shell currently has no
artifact export command and cannot bypass Toolbox's non-exportable results.

## Inventory, verification and performance

`apps/v0.8-feature-parity.json` inventories 15 legacy apps and 572 native command,
frontend surface and storage-source entries. These are code-discovered audit
anchors, not 572 verified semantic features. All are pending owner review.
Each later bundle must refine the route/data/authority mapping and provide real
implementation and test evidence; no feature may become `verified` with empty
evidence. Root metadata and unknown files retain full-scope verification.
Products/contract fixtures have explicit TS and Rust affected-graph edges.

All 19 buildable apps now have bundle/accessibility coverage. Public release
selection is separate. The required CI compiler job names and success semantics
are unchanged. `Product foundation acceptance` builds unpublished Windows
installers and tests native route/replay/installation isolation and WAL fixtures.
This workflow is not the exact-main release candidate and cannot authorize
stable promotion.

Initial shell budget, fixed before first build: raw 280,000 bytes / gzip 90,000
bytes. Initial local measurements: approximately 205,090 bytes / 64,320 bytes
JavaScript per shell, with the route view in a separate lazy chunk. These are
build-size measurements only. Anchor cold/hot start, first input, idle CPU/RSS,
representative search/task/terminal restore and real Windows baseline remain
unmeasured. Native fixture startup timings are observations on the named hosted
runner, not a before/after performance verdict or completion of R24.
