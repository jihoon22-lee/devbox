# Workspace project, Source and Files ownership

B04 / #546 owns this product slice. The implemented UI extraction and private
native adapters now feed the Registry and basic Files product host. Source,
execution trust, importer and Windows/WSL LSP acceptance remain incomplete. Runtime and Terminal/session providers remain B05/B06.

## Registry model and storage

`apps/devbox-workspace/src-tauri/src/core/registry.rs` assigns opaque UUIDs to
projects, worktrees and common Git repositories. A worktree binding separates
Windows/WSL target, opaque distro ID, canonical root, native root object evidence
and common Git directory evidence. Names and paths do not mint identity.

Discovery returns known, alias/move, replaced root, linked worktree or new project
metadata. It never registers, grants trust or starts work. Native platform code
must obtain and recheck object evidence before admitting a reviewed mutation;
renderer-provided `Binding` JSON is not authority. The native Windows probe and
one-time registration owner implement this boundary through the native host/UI;
native WSL distro admission remains pending.

Known observations retain IDs and do not advance revision. Linked worktrees share
project/repository IDs while keeping distinct worktree IDs. Rebind preserves old
references, increments context revision and clears trust; changing target/common
repository requires a separate reassignment decision. Windows spelling aliases
fold for lookup, WSL POSIX case is preserved, and different distro IDs remain
distinct. The registry contains last reviewed metadata, not a promise that the
root is currently online. Availability must be observed separately at operation
admission.

Legacy references are owner-qualified mappings, not an unqualified global ID
namespace. Repeated identical mappings are no-ops; conflicting mappings fail.
Removing a worktree with legacy references requires a reviewed unlink instead of
silently cascading away references. An exact owner/old-ID/worktree mapping must be reviewed to unlink it; the UI flow remains to be connected.

`core/registry_store.rs` owns `project-registry.json` in the activated product
generation, with a held directory identity and nonblocking OS writer lease.
Bounded strict reads reject corruption/future versions. Mutations check expected
revision, validate a complete next document, compare the current bytes and use
the existing filesystem atomic writer. Directory/lease replacement is rejected.
Restart opens the same durable metadata; there is no fallback that overwrites
an unreadable document with an empty one. Other products consume native typed
projections instead of opening this owner store directly.

## Native project observation and reviewed registration

`platform/project_probe.rs` opens real root and common Git objects without
executing Git, reading executable hooks, or starting a distro. It preserves
handles for `.git`, linked-worktree `commondir`/backlink and metadata objects.
Windows volume/file-index (portable test device/inode) produces stored evidence.
Common Git objects associate linked worktrees; root objects remain distinct.
Malformed/missing Git metadata is an explicit failure, never a plain-folder
fallback. No-link ancestor checks and bounded pointer reads reject escaping
symlink/reparse traversal. Transport checks precede IO: repository pointers cannot
start WSL via its redirector or contact a new UNC host/share. A new `.git` in a previously plain folder, changed
pointer bytes or replaced directory invalidates the observation.

`project_owner.rs` binds native observations to the Registry revision and opaque
one-time preview IDs. Cancel/expiry, object replacement, changed Registry and
mismatched register/rebind actions fail before persistence. Successful registration
retains untrusted state and changes only product-owned metadata. No repository
file is created or modified. At most eight previews retain handles for 180 seconds;
the host calls expiry and runs blocking IO in a bounded worker. Windows-local and
ordinary UNC probes are implemented; WSL roots are rejected until a verified
distro binding and running-state gate is supplied.

## Shareable manifest and local overlay

`core/manifest.rs` defines schema 1 of `.devbox/project.json`. The closed schema
accepts named tasks with a relative source and selector, toolchain requirements,
relative OpenAPI/log sources, expected ports and session membership. It does not
accept root/distro bindings, secret values, shell strings or personal layout.
Source paths reject absolute paths, traversal, device/stream syntax, backslashes
and ambiguous segments. Native readers must additionally reject escaping links
and verify the actual objects; lexical validation is not filesystem authority.

The local overlay binds to the exact registered project/worktree/target/revision.
It keeps existing owner-qualified `OwnedSecretReference` values and opaque API
environment/layout IDs locally. Secret resolution uses the existing owner at
execution time. Neither parsing nor merging resolves plaintext values.

Precedence is defaults → project → local. Named project entries replace default
entries; named local entries replace those whole entries. Local null removes an
entry and an omitted entry inherits. Ports replace the whole list; an omitted
list inherits and an explicit empty list clears it. A task still referenced by a
session cannot be removed without resolving the session conflict. Unknown fields,
future versions, duplicate/invalid IDs, excessive entries and stale overlay
context fail explicitly.

Definition diff reports added/changed/removed named fields and port changes.
The native edit/import flow must display the actual proposed definitions and
request explicit save before writing `.devbox/project.json` or the overlay.
There is no automatic Git commit or task/package execution. The native/UI flow now
implements one-target JSON edit/import, before/after preview and explicit save;
export contains the shared manifest only.

Trust checks the registered context and a deterministic digest of effective
execution definitions plus every referenced task/toolchain source digest. The
native owner must compute source digests with bounded identity-checked reads.
Missing/extra source digests fail. A changed task/hook/tool definition or source
content produces a different digest; previous trust does not authorize it.
An alias/rebind also clears trust even if the definition bytes are unchanged.

## Native definition inspection and approval

`platform/project_files.rs` captures bounded project-relative files from a native
ProjectLease. It retains root/ancestor/file identities and exact bytes, including
the first absent component of an optional manifest. Missing sources remain visible
but cannot be approved. A changed source, replaced object, linked parent, unavailable
root or changed local overlay invalidates the pending review. Limits are 130 files,
1,024 retained objects, 2 MiB per source and 8 MiB total; only four expiring previews
can be retained. No executable or source command is run during inspection.

`definitions.rs` reads `.devbox/project.json` and an optional private per-worktree
`local-overlay.json`, applies the existing precedence model and issues a one-time
approval token. The main-window UI explicitly reviews, approves, cancels or revokes.
Source bytes are hashed natively and never accepted as renderer-supplied evidence.
Registry CAS and the final source/overlay recheck precede approval persistence.
Approval changes the Registry revision and trust digest, while preserving worktree
binding revision so existing overlays and file contexts remain valid. Rebind still
invalidates both context and trust. Stored approval history is distinct from the
freshly checked `definitionsTrusted` state.

The definition role cannot dispatch Git, task or LSP commands. The current digest
covers manifest execution definitions and their explicit sources. Before those
engines are enabled, admission must include their native config/hook/tool evidence.
Manifest/local-overlay edits use an exact-byte/context/Registry revision derived
natively at load time. Preview rechecks that revision, parses the strict schema,
and retains the actual before/after definitions and effective diff under a separate
one-time token. Save revalidates the pending sources, root and overlay, then durably
revokes trust before writing one target. A failed write may leave trust revoked;
no cross-file transaction or automatic rollback over external changes is claimed.

Existing definition writes reuse Code Pad's bounded object/mtime/size/hash checks
and preserve line endings. First creation syncs a complete sibling then publishes
it with no-overwrite hard-link semantics; unsupported volumes fail without replacing
the destination. A failure may leave a newly created empty `.devbox` directory.
Native context exclusivity serializes definition saves with Files and binding changes.
Local JSON cannot mint Secret/API owner references; those require their owner flow.

The UI retains a conflicted draft and requires a new preview. Imported JSON goes
through the same native validation/save review, and shared export excludes local
references. The Windows fixture covers first creation, changed-file/cancel/replay
rejection, actual UI save and local precedence alongside trust lifecycle checks;
it also verifies that synthetic command sources were never executed.

## Feature reuse and pending integration

The original UI/test trees are shared through `packages/workspace-features`.
Legacy entries keep their CSS/a11y smoke contract. Overview, Source and Files
are lazy product routes. Files retains its draft when hidden and ignores global
shortcuts until active. Direct Dependencies routing is pending.

Workbench/Repo Manager/Code Pad expose 111 typed native adapters. Component
initialization fixes immutable private data/integration roots, while standalone
builds preserve their original namespaces. Initialization does not absorb old
profiles, migrate legacy identifiers, launch an LSP or perform a network request.
Existing Windows LSP installer/cache/archive behavior is retained in the engine;
actual product routing and new WSL-native transport remain unfinished.

Recovery import must validate source schema and preserve dirty buffers/settings.
Legacy session/recovery convenience readers that return empty on malformed input
are not import validators. Active rename journals must not be copied into a new
manager that would apply them to user files implicitly. Product recovery apply
uses the identity-checked preview/apply owner below. The legacy raw-path action
remains blocked; legacy importer and LSP journal parity remain incomplete.

The [workthrough](../../workthrough/2026-09-08-v08-b04-workspace-source-files.md)
records actual checks and remaining acceptance. Pure model and store tests do

## Store activation and metadata preservation

`core/stores.rs` holds one native product-root/lock owner and selects UUID store
generations through a bounded versioned `active-stores.json`. Registry, Overview,
Files and private common data occupy separate directories. Prepared generations
remain unselected until explicit activation; a new-user activation cannot replace
an existing active pointer. A 32-generation limit refuses new preparation without
deleting data that may be needed for recovery.

Before startup or selection, the owner reuses the engines' strict profile/template,
session and LSP schema parsers and checks recovery version/content bounds. It does
not use the legacy empty-on-corruption session/recovery readers. Missing optional
files are valid; corrupt/future metadata and linked/non-directory components stop
activation and preserve bytes. Validation never opens referenced project files,
executes a command or starts a distro. The importer still needs source inventory,
reviewed conflict/mapping and journal/resume before this becomes an import workflow.

## Native host and Registry requests

`host.rs` retains the selected generation and its ProjectOwner. `component.rs`
uses the existing native installation/session/window/context/replay admission
before dispatch. The activation service cannot register a project; Registry
commands cannot activate storage or execute a task. Renderer registration sends
only the native preview token, name and reviewed action, never object evidence.

Two external-probe permits are separate from two metadata-worker permits. A
15-second preview timeout retains the worker permit until the OS call returns;
a late preview only creates expiring in-memory review metadata. Periodic expiry
closes at most the already-bounded pending set on a metadata worker. Status reads
use nonblocking locks, and startup filesystem work stays off the webview thread.
The frontend rejects mismatched response provenance and stale startup/list replies.

Explicit project selection resolves the exact persisted Project/Worktree/target/
revision, probes the current root and Git objects, and compares the binding again
before native session selection. Replacement requires reviewed rebind; missing or
stale metadata cannot enter a previous context. Selection updates the session only
within its request deadline and only if its previous context still matches. Clear
selection is explicit. Neither operation grants execution trust.

The shell refreshes native description/context without remounting the feature
subtree. The Registry UI supplies opaque context fields, and subsequent requests
with the previous context are rejected by the shared session guard. File/Git/LSP
operations still require fresh per-operation owner admission before integration.

The native screen admits startup, Registry, project selection and the retained
Files route. Dirty/busy/hydrating/recovery states disable project changes in the
Registry UI. Native mutation guards independently check the actual binding and
opened document snapshot. Source/trust/LSP/importer end-to-end remains pending.
An owned context permit spans file request admission, queueing and native IO.
Select/clear/rebind/removal hold the exclusive side; file workers hold the shared
side. A cancelled caller cannot release a still-running worker's permit.

## File and recovery ownership

`file_owner.rs` admits at most 64 documents from a freshly admitted project root
or a native file-dialog selection. It retains file/ancestor identities and native
mtime/size/hash/encoding state. Each document has an opaque revision; object
replacement, changed bytes or context invalidates an earlier save/rename/delete
request. Saves preserve the Code Pad encoding/line-ending/conflict behavior. A
rename stays within the same parent and cannot overwrite an existing file.

Native dialog selections persist only path consent in the private generation.
Restart reads the file and pins fresh objects; serialized metadata never restores
write authority. The native dialog has one outstanding slot and reauthenticates
the unchanged window/session/context after the user answers before reading a
selected path. Files permits two IO workers with at most 16 queued requests.
Current Files state serializes operations under one mutex; ordinary UNC OS calls
can still delay other file calls. Independent remote cancellation remains part of
WSL integration acceptance.

`files_host.rs` stores session/recovery metadata separately for each registered
worktree and the project-free view. Generation/component/view identities remain
pinned, and bounded no-link reads and atomic writes preserve corrupt metadata.
Clean context changes rehydrate the next view and retire previous session timers.
Failed restored documents suppress automatic session rewriting until an explicit
editing action. Existing Windows LSP install/cache code remains present, but
product LSP execution is disabled until its execution-trust owner is connected.

Recovery preview binds native before/after data to the entry, context, document
revision and an expiring one-time token. Apply rechecks all evidence; cancel keeps
the stored entry and releases only temporary preview documents. A raw renderer
path/content pair cannot invoke the legacy writer. Preview assets must stay in
the selected project, with no-link ancestor/object checks and bounded reads.

The Windows fixture uses owned synthetic files to exercise revision conflicts,
object replacement, CRLF save, rename/delete, cancelled/replayed recovery and
actual CodeMirror editing across routes. Native dialog and full Windows/WSL LSP
flows require separate execution evidence before parity is claimed.

## Native Dependencies

Dependencies uses the existing Repo Manager parsers, graph diagnostics and remote
client through a native-created `DependencyAccess`. The product binds the actual
ProjectLease, exact Registry context, private common generation and request
permit before dispatch. A renderer path only checks its displayed selection;
it cannot choose a root. Plain projects need no Git command for local analysis.
Standalone Repo Manager retains its existing Git admission and data namespace.

Analysis is explicit and bounded by the existing filesystem/parser limits. The
shared summary builder preserves unrelated views and publishes into existing
product-owned directories. Product cache/snapshot publication cannot recreate a
removed generation; invalid/future metadata is preserved. Cache failure does not
block the local inventory. These are derived snapshots, not cross-file commits.

Remote previews bind exact context and native input revision. Cancel, replay,
expiry, changed inputs and changed roots reject execution; only reviewed package
coordinates reach the existing fixed HTTPS endpoints. The 30-second product
budget drops pending network futures at expiry. Blocking workers retain both
context and single-flight guards until completion, and check the deadline before
further IO. An active OS filesystem call remains cooperatively bounded.

The lazy UI retains analysis across routes, discards stale replies/tokens, and
locks project selection while analyzing, querying or reviewing a transmission.
Windows fixtures cover native plain-folder parsing and UI review/cancel without
contacting public APIs. Current-run evidence remains in the B04 workthrough.
