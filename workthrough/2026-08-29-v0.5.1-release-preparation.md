# v0.5.1 Stable Release Preparation

## Overview

v0.5.1은 공개 v0.5.0 이후 main에 병합된 #470, #473, #477, #478, #479를 하나의 stable
maintenance bundle로 배포한다. RC나 prerelease를 만들지 않고, source·문서·version·CI 검증을
annotated `v0.5.1` tag push 전에 끝낸다. 태그 뒤에는 제품 검증이나 source 수정을 추가하지
않으며, release workflow가 만든 draft의 exact asset 계약을 확인하고 검증된 draft만 공개한다.

## Context

- v0.5.0 stable은 annotated tag `v0.5.0`의
  `efc98dd3c91b77ee7c9024010ac012a6c68f2b54`에서 release workflow `33216176818`로
  게시됐다.
- v0.5.0은 15 apps, 30 binaries, notices, manifest인 공개 asset 32개를 갖고, manifest가
  선언한 31개 asset의 누락·추가·size·SHA-256 mismatch가 0이었다.
- v0.5.0 이후 Windows acceptance inventory, Log Lens Run reader, prerelease authorization,
  Manager browser fallback, Run Manager → Launcher named sidecar가 main에 병합됐다.
- v0.5.0 RC1~RC3 tag/release는 사용자 지시에 따라 삭제됐고 다시 만들지 않는다. 향후 RC는
  사용자가 정확히 요청할 때만 manual prerelease gate로 만든다.
- issue #176은 자동·코드·기존 packaged 근거 63개와 실제 Windows 환경이 필요한 7개 미완료
  항목을 분리한다. v0.5.1 배포는 이 7개를 관찰했다고 주장하지 않는다.

## Release Changes

### Changed app versions

Release tag는 bundle identity이고 앱 version과 독립이다. 그러나 v0.5.0 이후 실제 설치
binary가 바뀐 앱을 기존 version으로 다시 게시하면 Devbox Manager의 installed/available
version 비교가 update를 찾지 못한다. 따라서 변경된 네 앱만 patch bump한다.

| App | v0.5.0 asset version | v0.5.1 asset version | Reason |
|---|---:|---:|---|
| log-lens | 0.1.0 | 0.1.1 | Run Manager stdout/stderr reader |
| devbox-manager | 0.4.0 | 0.4.1 | browser fallback catalog correction |
| run-manager | 0.4.0 | 0.4.1 | Launcher jobs/services sidecar producer |
| devbox-launcher | 0.1.0 | 0.1.1 | named sidecar consumer and strict fallback |

각 앱의 `package.json`, `src-tauri/Cargo.toml`, `src-tauri/tauri.conf.json`과 root
`Cargo.lock`을 같은 version으로 맞춘다. 실제 기능이 바뀌지 않은 11개 앱 version은 유지한다.

### CI timing stabilization

PR #479의 첫 frontend run에서 Developer Toolbox handoff mock 호출과 React dialog close 사이를
즉시 비교하는 기존 테스트가 한 번 실패했고 동일 source 재실행은 통과했다. release-prep CI를
다시 흔들지 않도록 mock 호출뿐 아니라 최종 dialog 제거까지 `waitFor`로 기다린다. 제품 동작은
바꾸지 않는다.

### Documentation

- `CHANGELOG.md`에 exact `v0.5.1` section을 추가해 release workflow가 같은 section만 notes로
  추출하게 한다.
- README, AGENTS, roadmap, architecture, development, Windows guide, project/app README와
  상세 v0.5.0 계획 문서에 v0.5.0 stable history와 v0.5.1 포함 범위를 시간 순서대로 구분한다.
- #479의 `summary.json` compatibility, `jobs-services.json` named sidecar, missing-only legacy
  fallback, corrupt/permission/link fail-closed, secret/path exclusion을 보존한다.
- `crates/logs`는 현재 누락이 아니라 두 번째 consumer가 생길 때 추출할 계획 상태로 남긴다.
- v0.5.0의 immutable tag/workflow/asset 증거와 삭제된 RC의 역사적 검증 기록은 소급 수정하지
  않는다.

## Pre-tag Verification

태그 생성 전 다음을 모두 끝낸다.

1. 네 앱의 frontend/Cargo/Tauri version 일치와 catalog/release build target 15개를 검사한다.
2. `v0.5.1` changelog exact extraction과 extractor, release-input, manifest, downloaded-release,
   dependency, Windows acceptance configuration 회귀 테스트를 실행한다.
3. 변경 frontend 테스트·build/typecheck와 변경 Rust package test/check/Clippy/fmt를 로컬에서
   실행한다. 병렬 작업 수는 2로 제한한다.
4. 전체 diff, 문서 링크, dependency notices/hash와 release workflow 32-asset 계약을 검토한다.
5. release-prep PR required CI의 frontend, Linux Rust, Windows Rust, dependency, catalog,
   scope gate가 모두 성공한 뒤에만 main으로 병합한다.
6. main이 clean이고 origin/main과 같으며 `v0.5.1` tag/release가 존재하지 않는지 다시 확인한다.

## Publication Contract

- release-prep merge commit 하나에 annotated `v0.5.1` tag를 만들고 그 tag ref를 한 번만
  push한다. manual dispatch를 중복 실행하지 않는다.
- preflight는 stable input, remote annotated tag, tag peel과 workflow SHA 일치, 기존 release
  부재를 build 전에 확인한다.
- Windows job은 catalog의 15개 앱을 순차 build하고 앱별 portable/NSIS를 즉시 분리 staging한
  뒤 notices와 manifest를 추가한다.
- publish job은 정확히 32개 asset만 draft로 만들고, verify job은 release를 새로 download해
  15 apps, 31 manifest-declared assets, public 32 assets, missing/unexpected/size/SHA mismatch 0을
  확인한다.
- 검증된 draft만 `draft=false`, `prerelease=false`, Latest stable로 전환한다. 실패한 draft나
  partial asset을 정상 release로 표시하지 않는다.
- 배포 후에는 workflow와 공개 asset이 위 계약대로 게시됐는지만 확인한다. 새 기능 검증,
  source 변경, RC 생성, 동일 tag 재빌드는 하지 않는다.

## Cleanup

release 결과는 GitHub release와 issue #176에 기록한다. 이후 release 전용 worktree가 clean이고
merge된 상태인지 확인해 제거하고, `git worktree prune`, local/remote task branch 삭제를
수행한다. `/mnt/e/projects/worktrees`와 devbox 전용 worktree root를 다시 감사하고, clean·merged
작업 잔존물과 이번 작업의 `/tmp/devbox-*` 파일, 종료된 cargo/node monitor를 정리한다. 활성,
dirty, unmerged 또는 host-owned worktree/process는 임의로 삭제하지 않고 정확히 보고한다.
