# B02 API Studio consolidation

Tracking: #544, master #541, acceptance #542; draft PR #555. Implementation
in progress; full product parity and migration acceptance remain open.

## Changes

- Extracted API Playground's six pure protocol modules into `crates/api-protocols`.
  Legacy API commands and the new API Studio API component share the same engine.
- Moved the three frontend implementations and their 623 tests into
  `packages/api-studio-features`. Legacy entry points consume the same exports.
  API Studio lazily opens Requests/Protocols, Webhooks and Transforms; mounted
  feature groups retain their drafts and native connections across navigation.
- Added explicitly enumerated native adapters around the existing commands.
  New product startup initializes state without running legacy bootstrap or
  starting requests/listeners/processes. Storage roots use the product namespace
  and component subdirectories. Internal API→Transforms and Webhook→API sends
  use product-owned one-time storage; no legacy executable is launched. Other
  cross-product sends remain unexposed until their receiving owners are integrated.
- Legacy crates default to their `standalone` executable feature; API Studio
  disables it and links only the native component implementation. This keeps
  legacy frontend bundles and bootstraps out of the product build. The original
  standalone apps keep their existing default behavior.
- Product IPC checks the native main window, registered component owner, session,
  installation, context, replay, admission deadline and bounded arguments before
  dispatch. Active IDs stay reserved across long awaits. Responses carry native
  operation provenance; dialogs and explicit clipboard reads use that boundary.
- Catalog revision 3 declares API Studio's three component authorities and its
  separate startup importer authority.
  Public v0.7 selection remains 15 apps. Historical source paths are retained
  alongside relocated inventory paths.

- Internal sends return `ArtifactReference` with native source provenance. Webhook
  sends load source-owned masked history/fixtures by opaque ID; API selections
  reuse the existing redactor. Pending deliveries cannot overwrite unread actions.
  Busy-receiver failures revoke publication. API/Transforms retain claim, preview,
  renewal, explicit apply and restore using the same product-owned store. Scoped
  wake-ups open the recipient view, whose data comes from native pending state.
- Restored standalone entry-point CSS and real shared-feature axe smoke tests for
  the three legacy apps. This preserves their accessibility gate after the move.

## Legacy import implementation

The Webhook/Transforms pure engines and Control Center snapshot/transaction
harness now have real API Studio consumers in `crates/webhook-core`,
`crates/transforms-core` and `crates/data-migration`. Mechanical moves are kept
separate from importer wiring. The affected graph checks all reverse consumers;
the capability checker enforces the main/isolated-export window separation.

The startup importer reads actual API browser keys and sealed OAuth/TLS files,
Webhook fixtures/service profiles and Toolbox workflow metadata. Closed LevelDB
acquisition holds read-only exclusive source handles and validates file/list
identities. A suspended child assigned to the existing owned process Job exports
only from a copied WebView2 directory, verified through COM before reading keys.
No legacy bootstrap runs on the original. Native DPAPI validation reuses the API
owner; unavailable secrets require reconnect. Raw copies and tickets are purged;
new previews supersede old staging while pending activation remains protected.

Domain merge preserves ordered duplicate headers, excludes transient/raw/HMAC
state, resolves supported ID/name conflicts, enforces capacity and records source
fingerprints. Store-qualified plan IDs avoid collisions across stores. Completed
receipts preserve later product edits on repeat import. SQLite accepts the intent;
CAS native writes, browser read-back and final acknowledgment activate it. This
is not a cross-store transaction: startup is gated until completion, restart can
resume or restore only recorded values, and unexpected edits block overwrite.

Focused portable validation: 141 tests PASS across the product importer, three

Product/shared frontend builds PASS. The pinned actual v0.7 executable fixture
