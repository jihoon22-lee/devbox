# v0.4.2 RC2 Acceptance, Stable Publication, and Release Close

## Overview

API Playground 0.3.2 보안 핫픽스의 두 번째 immutable release candidate를 공식 Windows
package로 만들고, release manifest와 실제 asset을 독립 검증한 뒤 packaged H1-A~D를
수행했다. RC1에서 발견한 Collection persistence schema 결함이 RC2에서 해결됐고 logical
storage·network·redirect 경계와 cleanup까지 통과했으므로, 같은 제품 코드에 문서만 더하는
`v0.4.2` stable preparation을 시작했다. 이후 docs-only preparation PR, annotated stable tag,
공식 release workflow, 독립 27-asset 검증과 exact stable portable H1까지 완료해 이 기록을
release-close 상태로 갱신했다.

## Official Build and Publication

Release workflow의 다음 job이 모두 성공했다.

1. `Build Windows installers` — 13개 앱을 per-app staging으로 순차 빌드하고 portable·NSIS
   installer를 만들었다.
2. `Publish release` — exact `v0.4.2-rc2` changelog section으로 public prerelease를 만들었다.
3. `Verify release assets against manifest` — 원격 release assets를 manifest와 대조했다.

Build job의 Node 20 action-runtime deprecation annotation은 GitHub가 action을 Node 24로
강제 실행한다는 유지보수 경고였다. build/publish/verify 결과에는 실패가 없었으므로 이 RC의
blocker로 분류하지 않고 v0.5.0 또는 CI 유지보수 backlog에서 action major update를 검토한다.

### Harness environment corrections

초기 diagnostic 실행에서는 제품 검증 전에 다음 하네스 환경 차이가 발견됐다.

1. Linux Node에는 `LOCALAPPDATA`가 없어 Windows app-data의 WSL mount path를 명시해야 했다.
2. WSL `spawn().pid`는 Windows application PID가 아니라 interop PID였다. Windows CIM으로
   새 API Playground process와 exact executable path/title을 선택하도록 바꿨다.
3. 종료 과정에서 초기 process-tree snapshot 뒤 재생성된 동일 app process가 남을 수 있었다.
   테스트 전 API process 0이라는 precondition 아래 exact API process를 반복 종료하고 새
   WebView2 descendant가 사라질 때까지 기다리도록 cleanup을 보강했다.
4. Windows WebView2 CDP listener는 WSL의 `127.0.0.1`에서 접근할 수 없었다. accepted run은
   Windows Node에서 실행해 app, CDP와 test server를 같은 loopback에 배치했다.

각 diagnostic 실패 뒤 API process 0, app-data absent, backup residue 0을 독립 확인한 다음에만
다시 실행했다. diagnostic failure를 제품 PASS로 세지 않았고 accepted Windows run만 최종
evidence로 사용했다.

### H1-A — DPAPI and backend-only resolution

- 실제 UI에서 secret environment variable을 저장했다.
- logical environment store에 secret metadata와 sealed value가 있고 원문·`plain:` prefix가
  없음을 확인했다.
- `${var1}` reference를 UI URL/auth와 backend URL, query, header key/value, body, auth 각
  field에서 전송했다.
- loopback server는 expected value 수신 여부만 boolean으로 확인했다.
- response wire, DOM, History와 logical localStorage에 fixture 원문이 없었다.

### H1-B — History v1 fail-closed migration

- direct fixture가 든 raw History v1을 seed하고 v2·marker를 제거한 뒤 reload했다.
- raw v1은 UI에서 사용되지 않고 logical storage에서 제거됐다.
- safe empty History v2와 migration marker가 raw delete/read-back 뒤 존재했다.
- v2 write, raw delete, marker write fault와 retry는 PR #225의 automated storage fault
  fixtures로 연결했다. Packaged LevelDB는 고의로 손상시키지 않았다.

### H1-C — Collection safe conversion

- reference와 direct credential이 함께 든 raw Collection v1을 seed했다.
- reference는 보존되고 direct secret은 제거됐으며 `requiresSecretReview`는 boolean으로
  유지됐다.
- Collection v2 write/read-back, raw v1 제거, marker 기록이 성공했다.
- 전체 logical localStorage에 fixture 원문이나 raw backup/quarantine이 없었다.

### H1-D — cURL, response, error, and redirect

- default cURL은 credential·query·body·auth 값을 마스킹하고 reference template을 보존했다.
- revealed cURL은 backend command가 만든 일회성 문자열로만 확인하고 즉시 폐기했다. React
  state, History, Collection과 localStorage에 저장되지 않았다.
- 정확한 multi-format clipboard 보존을 보장할 수 없어서 clipboard write는 수행하지 않고
  기존 clipboard를 건드리지 않았다.
- response header/body, nested sensitive key와 secret exact value는 redaction됐다.
- 307/308 cross-origin redirect는 method만 유지하고 credential, body, stale `Content-*`
  metadata를 destination에 보내지 않았다.
- 민감한 destination URL은 destination connection 전에 고정 오류로 차단됐다.
- 이 Windows host의 firewall은 미청취 IPv4·IPv6 loopback을 `ConnectionRefused`가 아니라
  timeout으로 처리했다. non-timeout generic transport-failure branch는 accept-and-reset
  server로, timeout branch는 1초 제한보다 늦게 응답하는 server로 별도 검증했다. 양쪽 오류는
  URL, port, token, fixture와 내부 transport 원문을 포함하지 않았다.
- 최종 logical localStorage scan에서 fixture 평문은 없었다.
