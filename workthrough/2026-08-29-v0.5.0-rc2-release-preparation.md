# v0.5.0-rc2 Release Preparation

## Summary

This workthrough records the transition from the published v0.5.0-rc1 checkpoint to a new
v0.5.0-rc2 preparation. RC1 remains immutable and is not overwritten. Its official release
workflow and independent 32-asset download verification succeeded, but a source audit found a
single-instance release-contract gap in 3 of 15 apps. Because that source failure was already known
and active life-log/WSL Desktop user processes prevented safe exact isolation, RC1 W4 was
intentionally not started.

The correction is now merged in `a5256fe252fb0c2115adfd02d303c277aaf7bccb` through PR #465 and
required CI 33178381902. RC2 must still be prepared, tagged, packaged, independently verified, and
run through the complete Windows W1-W4 matrix. No RC2 release, tag, package, stable promotion, or
post-release cleanup is claimed by this document.

## Source audit and correction

The RC1 source audit found that Port Manager, Developer Toolbox, and Webhook Lab lacked the
single-instance dependency or initialization required by the 15-app W4 contract. The resulting
source gap was **3/15**. RC1 W4 was intentionally not started: the known source failure made a
passing result impossible, and active user processes in life-log and WSL Desktop prevented exact
disposable isolation without unsafe intervention.

The correction adds the dependency and first-plugin initialization to those three applications and
adds a catalog invariant requiring every `release: true` app to contain both the exact dependency
and `tauri_plugin_single_instance::init`. The correction does not expand AppLink input handling or
interpret arbitrary second-instance arguments.

### Packaged-smoke safety review

The Windows runner was reviewed before any packaged application was launched. The resulting
source is fail-closed around the boundaries that can affect user state:

- Windows process inventory uses bounded PowerShell calls with terminating CIM errors; an empty or
  malformed inventory is a failure, never “no apps running.” Parent and descendant ownership uses
  PID, creation time, image name, and executable path. The second launch is sampled while alive and
  compared with a pre-launch process snapshot so a short-lived parent cannot hide a leaked child.
  A post-exit candidate discovered across the final polling boundary is never killed as owned; it
  makes cleanup uncertain, preserves generated data, and blocks release. Missing primary/secondary
  identity and incomplete creation/name/path identity are likewise fail-closed cleanup states.
- The runner refuses all pre-existing Devbox process names, passes only an explicit Windows
  environment allowlist, verifies the CDP listener belongs to the launched tree, requires exact
  renderer title/markers and bounded IPC shapes, and gates runtime/console/buffered log errors.
  Second-instance acceptance requires exit code 0, one persistent app image, native foreground
  restoration, visible/unminimized state, document focus, first-instance responsiveness, and no
  output. Orderly quit also requires exit code 0 and no signal.
- Actual `%LOCALAPPDATA%` paths use same-volume atomic backup names, an owner marker, a transaction
  journal, and quarantine. Restoration is attempted independently from generated-data deletion;
  unknown ownership, access errors, process-inventory uncertainty, backup/quarantine/journal
  residue, or cleanup ambiguity blocks the release and preserves recovery artifacts.
- A fixed per-user `%TEMP%` lock serializes harness runs independently of output location and is
  released by the top-level `finally` on normal errors or handled signals. Filesystem absence means
  `ENOENT` only; access-denied and other errors fail closed. Config IDs/process names/probes are
  shape-validated, and the independent verifier's config SHA-256 must equal the exact config used by
  the runner.
- Inputs/output/runtime must share a trusted E: scratch volume separate from the C: user-data
  volume; runtime must be new and sufficiently deep. Hard process termination, malicious
  concurrent writers, or a hostile Windows reparse race remain outside what a script can make
  atomic, so W4 still requires a quiescent user session, the reviewed config, and no force-closing
  of user applications.
- Knowledge Base is the only config entry with `isolatedKnowledgeRoot: true`, and config validation
  requires exactly that one app. Before launching it, the harness creates the bounded
  `Projects`/`Notes`/`Journal`/`Reference`/`Archive` layout below the new E: runtime root, refuses a
  pre-existing staged `data.db`, creates the SQLite settings database under the staged
  `com.devbox.knowledgebase` app-data directory, and writes then reads back the exact isolated vault
  root. The check therefore cannot reuse or silently point at the user's existing Knowledge SQLite
  root.
- Known Folder agreement is a preflight gate, not an assumption: `LOCALAPPDATA` must be absolute and
  must case-insensitively equal PowerShell's
  `[Environment]::GetFolderPath(LocalApplicationData)` result before any protected path is staged.
  The scratch runtime, verifier, assets, config, and output must also share one non-user-data volume;
  a mismatch or linked path fails closed.
- App-data preparation is marker-first and journaled. The harness creates a unique sibling staging
  directory, writes the `schemaVersion: 1`/run-token owner marker with no-replace semantics, and
  reads it back before moving an existing current directory to its backup and promoting staging to
  current. It then reads the marker back on current. Any existing marker-owned current or
  `.devbox-v050-*`/`.devbox-generated-v050-*`/`.devbox-staging-v050-*` sibling is rejected as stale
  acceptance state before launch; absence is treated as `ENOENT` only, never as a blanket I/O false.
- Final absence and restoration are explicit assertions. After owned process cleanup, the harness
  restores an existing original only after backup/current identity checks; if the path was originally
  absent, the generated current path must be absent. Backup, quarantine, staging, and transaction
  journal residue counts must all be zero. Unknown ownership, a changed vault, process uncertainty,
  or any non-`ENOENT` path error preserves recovery state and blocks the release.
- Non-path failures are recorded rather than collapsed into missing-path results. Process inventory,
  CDP/runtime/console/log errors, second-process exit or signal, SQLite setup/read-back, restore,
  quarantine, journal, and cleanup failures remain in the structured result/error fields (with fixed
  public messages and safe OS error codes, never raw paths); `dataErrorCount`, residue counts, and
  `releaseGateBlocked` keep an ambiguous run release-blocking.

## Cleanup and relocation checklist

The intended storage/relocation boundary is: keep packages, downloads, harnesses, and redacted
results on E: while acceptance runs. After all devbox work and cleanup finish, the user will move
the WSL distribution storage from C: to E:, then move projects from `/mnt/e/projects` to
`/home/jihoon/projects` inside that relocated WSL environment. These user-scheduled operations are
verified-copy boundaries, not release-automation tasks. They do not authorize early deletion,
broad cache cleanup, process termination, or rewriting user data.

- Preserve immutable RC1 release/tag and all evidence until RC2 records the historical result.
- Preserve dirty, unmerged, unique, orphan, active, locked, and host-owned state.
- Review clean/squash-superseded worktrees against main, patch-id/file diff, related PR, and owner
  intent before considering removal.
- Remove only verified clean merged/superseded worktrees, then run
  `git worktree prune`, delete the local branch, and delete a confirmed remote branch in that order.
- Never use force delete, reset, broad clean, blind recursive removal, or a dead PID as a cleanup
  authorization.
- Re-run `git worktree list`, local/remote branches, open PRs, tags/releases/workflows, main/origin
  SHA, `git status`, running devbox processes, and C:/E: capacity before declaring closeout.
